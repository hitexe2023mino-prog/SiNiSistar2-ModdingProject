# Refine Refactor Plan

リファクタ計画を鵜呑みにせず、各施策の動機、根拠、効果、副作用、検証方法をユーザーとのディベートで確定する。観点の羅列を、優先順位と受け入れ条件を持つ施策台帳へ改訂する。

## 責務境界

| スキル | 入力 | 主な成果物 |
|---|---|---|
| `create-specification` | 正本仕様がないアイデア、目的、要求、制約 | 新規仕様書 |
| `refine-specification` | 既存の仕様書、要件定義、設計書、RFC | 実装可能で検証可能な改訂仕様書 |
| `refine-refactor-plan` | リファクタ計画書、改善要項、負債の棚卸し | 採否と優先順位が確定した施策台帳 |
| `implement-refactor-plan` | 確定した施策台帳 | コード、テスト、計測結果 |
| `implement-from-spec` | 確定済み、または実装可能と判定された仕様 | コード、設定、移行、テスト |

このスキルは改善施策の採否、範囲、優先順位、検証方法を確定する。規範仕様（製品要件、ゲームルール、受け入れ条件）そのものは改訂しない。施策がゲームの遊び方や外部から観測できる挙動を変える場合は、施策台帳に「仕様変更を伴う」と記録し、対応する仕様書の改訂は `refine-specification` へ引き継ぐ。計画の確定までを担当し、ユーザーが実装も明示的に求めた場合だけ `implement-refactor-plan` へ進む。

## 基本原則

- 施策は「良さそうだから」では採用しない。解決する具体的な痛みと、改善を確認する方法を必ず対にする。
- リポジトリから判定できることをユーザーへ質問しない。先にコードと文書を読む。
- ユーザーの主張にも自分の主張にも同じ基準で反証を試みる。反証できなかった主張だけを台帳へ残す。
- 事実（コードで確認した）、推論、仮定、提案、未決事項を混同しない。
- 「実施済み」と書かれた施策も現状のコードで再確認する。文書の主張と実装が食い違う場合は実装を事実とする。
- ユーザーが指定した言語、専門度、文書形式で対話し、成果物を作る。

## 1. 対象と現状を把握する

1. 改訂対象のリファクタ文書を最後まで読み、参照された仕様書、Issue、変更履歴を確認する。
2. 施策が対象とするコードを実際に読む。対象が特定できない施策は、その事実を欠落として記録する。
3. 既存の制約を把握する。少なくとも次を確認する。
   - `docs/specifications/` の正本仕様と、その受け入れ条件
   - `docs/implementation/` のトレーサビリティ（要件と実装の対応）
   - `docs/CHANGELOG.md` のMOD単位の版と互換性の前提
   - `Directory.Build.props`（`TreatWarningsAsErrors` や `Nullable` などの全体設定）
   - `tests/` に既存テストがある範囲と、テストが無い範囲
4. 各MODが独立して動作し個別に更新できるという前提を壊す施策（共通化のための強い結合など）を特に警戒する。
5. 出力先を確定する。既定は入力文書そのものの改訂とし、既存の章立てを維持する。

正本となる計画書が存在せず、改善のアイデアしかない場合も、このスキルで最初の台帳を作ってよい。ただし製品要件の新規定義が必要になった時点で `create-specification` へ引き継ぐ。

## 2. 施策を分類する

各施策を次の2軸で分類し、以降の扱いを変える。

**外部から観測できる挙動への影響**

- `振る舞い保存`: 可読性、重複排除、保守性、再利用性、拡張性など、既存テストが通り続けることが正しさの条件。
- `性能`: 挙動は保存するが、効果は計測でしか確認できない。計測方法と基準値が無ければ採用しない。
- `仕様変更`: ゲーム難易度、プレイ体験、敵の出現規則など、遊び方が変わる。規範仕様の改訂が先に必要。

**確定度**

- `Blocking`: 決まらないと他の施策の設計が分岐する。
- `Important`: 品質、互換性、作業量に大きく影響する。
- `Minor`: 後から安全に決められる。
- `Resolved`: コードまたは文書ですでに確定している。

分類の結果、`仕様変更` に該当する施策は本スキルで設計を確定させない。解決したい体験上の課題と、影響する既存仕様を特定するところまで進め、引き継ぎ先を明示する。

## 3. ディベートする

施策の採否を決める前に、賛成側と反対側の主張を必ず両方立てる。手順、反論の類型、決着条件は [references/debate-protocol.md](references/debate-protocol.md) を読む。

最低限、各施策について次を突き合わせる。

- この施策が解決する痛みは、実際にコード上で起きているか。再現できる箇所を示せるか。
- 施策を実施しなかった場合に何が悪化するか。何も悪化しないなら採用しない。
- 改善したと言える条件は何か。それは観測できるか。
- 何を壊し得るか。テストが無い範囲を触るなら、テストの追加が施策の一部になる。
- より小さい代替手段で同じ痛みを消せないか。

ユーザーの提案を無条件に採用しない。反証が成立した場合は根拠を示して差し戻し、成立しなかった場合は自分の反対意見を取り下げてその旨を記録する。ディベートは勝敗ではなく、台帳へ残る根拠を作るために行う。

## 4. 質問を設計する

依存関係の上流かつ影響度の高い論点から質問する。既定では一度に1〜3個の意思決定だけを扱う。各番号付き質問は、1つの選択または1つの自由回答だけで完結させる。

各質問には必要に応じて次を短く含める。

1. コードまたは文書で確認した観察事実
2. なぜ今決める必要があるか
3. 2〜3個の現実的な選択肢と主なトレードオフ
4. 根拠のある推奨案、または根拠が弱いことを明示した暫定案
5. 自由回答も可能であること

性能目標、閾値、行数、複雑度などの数値を推奨するのは、計測値、プラットフォーム制約、または確認済みの目標から根拠を示せる場合だけにする。根拠が無い数値は `検証前の暫定案` と明記し、確定方法を添える。

## 5. 回答を統合して反復する

各回答後に次を行う。

1. 決まった内容を簡潔に言い換える。
2. 影響を受ける施策、優先順位、受け入れ条件、未決事項を更新する。
3. 回答によって成立しなくなった施策、または新たに必要になった施策を検出する。
4. 次の最重要質問へ進む。

毎回台帳全文を再掲しない。対話中は変更点、決定、残る重要論点だけを示す。ユーザーが判断を委ねた場合は、既存の制約に最も整合する案を選び、理由と仮定を記録する。不可逆な影響があり判断材料が不足する場合は推測しない。

## 6. 台帳へ落とす

確定した内容を [references/refactor-plan-template.md](references/refactor-plan-template.md) の形式へ整理する。観点の見出しだけを残さず、各観点の下に検証可能な施策を置く。

- 施策に安定したIDを付ける（例: `RF-001`）。実装とテストから参照できるようにする。
- 施策を、依存順に並べた小さな単位へ分ける。1つの施策が複数MODへまたがる場合は分割する。
- 却下した施策も理由付きで残す。同じ議論を繰り返さないため。
- 実施済みと再確認できた施策は、確認方法と確認日を添えて `確認済み` にする。
- 優先順位は、痛みの大きさ、影響範囲、実施コスト、可逆性から決め、根拠を1行で書く。

## 7. 完成判定を行う

次を満たすまで計画を完成扱いにしない。

- `Blocking` の未決事項がない。
- すべての施策に、解決する痛み、対象、受け入れ条件、検証方法、優先順位がある。
- `性能` 施策に計測方法と基準値がある。
- `仕様変更` 施策に、影響する既存仕様と引き継ぎ先が明記されている。
- テストが無い範囲を触る施策に、テスト追加が含まれている。
- 却下した施策と理由が追跡できる。
- 未定義語、対象不明の施策、互いに矛盾する施策がない。

ユーザーが対話を終了した場合は無理に続けない。未解決箇所を `TBD` として影響付きで列挙し、「完成」ではなく「現時点の作業版」として渡す。

## 8. 成果物を生成する

既定では入力文書を改訂し、観点の構造を保ったまま施策台帳を組み込む。最終回答には次を含める。

- 改訂した計画本文または差分の要約
- 採用した施策と優先順位、その根拠
- 却下した施策と理由
- ディベートで確定した主要な判断
- 明示的な前提と非目標
- 引き継ぎが必要な仕様変更（なければ「なし」）
- 残るリスクと未検証の仮定

計画本文には対話の経緯を混ぜず、決定結果を規範的かつ一貫した表現で記述する。

## 終了条件

次のいずれかで対話を終了する。

- 完成判定を満たし、最終計画を提示した。
- ユーザーが未決事項を承知して作業版の出力を求めた。
- 必須資料、計測環境、または外部の意思決定がなく進行不能で、必要な入力を明示した。
