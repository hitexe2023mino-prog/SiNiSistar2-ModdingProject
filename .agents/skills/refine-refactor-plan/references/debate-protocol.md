# ディベート手順

施策の採否を決める前に、賛成側と反対側の主張を両方立てて突き合わせる。目的は勝敗ではなく、台帳へ残す根拠を作ることである。

## 進め方

1. **主張を1文にする** — 「何を、なぜ、どう変えるか」を1文で書く。1文にできない施策は、まだ分割されていない。
2. **根拠を提示する** — コードの該当箇所、テストの有無、計測値、仕様の条項、変更履歴のいずれかを示す。示せない場合は `根拠未確認` と明記する。
3. **反論を作る** — 下の類型から該当するものを最低1つ試す。自分の提案にも同じ強さで適用する。
4. **反論へ応答する** — 反論を否定できる事実があれば示す。無ければ施策を縮小、分割、延期、または却下する。
5. **決着を記録する** — 採用・条件付き採用・延期・却下のいずれかと、決め手になった根拠を1行で残す。

同じ論点を2往復しても新しい事実が出ない場合は、ユーザーの判断を仰いで打ち切る。

## 反論の類型

| 類型 | 問い |
|---|---|
| 痛みの不在 | その問題は実際に起きているか。再現できる箇所を示せるか。 |
| 効果の測定不能 | 改善したと言える条件は何か。外部から観測できるか。 |
| 代替手段 | より小さい変更で同じ痛みを消せないか。 |
| 副作用 | 何が壊れ得るか。守っているテストはあるか。 |
| 過剰な一般化 | 将来の要求を先取りしていないか。現在の利用箇所は何件か。 |
| 結合の増加 | 独立して更新できるはずの単位を結び付けていないか。 |
| 責務の越境 | それは計画の変更ではなく仕様の変更ではないか。 |
| 順序の誤り | 先に別の施策を終えないと設計が確定しないのではないか。 |
| コストの過小評価 | 影響ファイル数、移行、再テストの量を見積もったか。 |

## 決着の種別

- `採用`: 痛み、効果、検証方法がそろい、反論に応答できた。
- `条件付き採用`: 先行する施策、計測、またはテスト追加が済んだ場合に実施する。条件を明記する。
- `延期`: 施策は正しいが、いま実施する理由が弱い。再検討の条件を明記する。
- `却下`: 反論に応答できなかった。理由を残し、同じ議論を繰り返さない。

## やらないこと

- 反論のための反論を作らない。応答できた反論は取り下げる。
- ユーザーの提案だからという理由で反論を省略しない。
- 反論できなかったことを、根拠が示されたことと混同しない。両者は台帳で区別して書く。
