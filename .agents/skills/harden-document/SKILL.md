# Harden Document

自分が出力した文書を、他人が書いた欠陥文書として扱い直す。文書の表現ではなく、文書が主張する事実を攻撃する。最優先の指摘が0件になるまで、レビューと修正を反復する。

## 責務境界

| スキル | 入力 | 主な成果物 |
|---|---|---|
| `create-specification` | 正本仕様がないアイデア、目的、要求、制約 | 新規仕様書 |
| `refine-specification` | 既存の仕様書、要件定義、設計書、RFC | 実装可能で検証可能な改訂仕様書 |
| `refine-refactor-plan` | リファクタ計画書、改善要項、負債の棚卸し | 採否と優先順位が確定した施策台帳 |
| `harden-document` | 自分が作成・改訂した直後の文書 | 指摘0件まで反復した堅牢化済み文書、レビュー台帳 |
| `implement-from-spec` / `implement-refactor-plan` | 確定した仕様・施策 | コード、テスト、対応記録 |

このスキルは**文書の正しさ**を対象とする。ユーザーと合意した決定内容そのものを覆さない。決定を変える必要が生じた場合は、修正せずエスカレーションする。

`refine-specification` との違いは駆動方法である。あちらはユーザーとの対話で未決事項を確定する。こちらは既に確定した内容が正しく書けているかを、ユーザーを止めずに自力で検証する。ユーザーを止めるのは、自力で決められない論点に達したときだけである。

## 基本原則

- 自分が書いたことを根拠にしない。文書の主張は、リポジトリ、コード、実行結果、一次資料で再確認する。
- 指摘には必ず、確認した場所と、その指摘が正しければ何が壊れるかを添える。
- 「良く書けている」は成果ではない。反証を試みて成立しなかったことだけが成果である。
- 指摘数を稼がない。表現の好みを最優先へ昇格させない。
- 修正が新しい欠陥を生んでいないかを、次の巡で必ず再確認する。
- ユーザーの決定を、レビューを理由に静かに書き換えない。

## 1. 対象と基準を固定する

1. 対象文書と、その文書が参照する一次資料（仕様、コード、テスト、ログ、コミット）を特定する。
2. 文書の役割を確認する。規範文書か、計画か、報告か。役割によって「正しい」の意味が変わる。
3. 直前の対話でユーザーが下した決定を列挙する。これらは検証対象であり、変更対象ではない。
4. 検証に使える手段を確認する。読み取り可能なコード、実行可能なテスト、参照可能なログのどれがあるか。
5. 巡回の記録先を決める。3巡を超える見込み、または指摘が5件を超える場合は [references/review-ledger-template.md](references/review-ledger-template.md) を使う。

対象文書が自分の出力でない場合、または未確定事項が多く残る作業版の場合は、このスキルではなく `refine-specification` / `refine-refactor-plan` を使う。

## 2. 敵対的にレビューする

文書を肯定的に読まない。次の姿勢で1巡する。

- この文書だけを読んだ実装者が、誤ったコードを書ける箇所はどこか。
- 著者が確認せずに書いた文はどれか。確認した文と区別できるか。
- 参照している名前（ファイル、シンボル、テスト、要件ID、URL）は実在するか。
- 数値、閾値、件数、行数は、どこで数えた値か。再現できるか。

観点の一覧と使い分けは [references/adversarial-lenses.md](references/adversarial-lenses.md) を読む。全項目を機械的に適用せず、対象文書の役割に該当する観点だけを使う。

各指摘は次を満たさなければ記録しない。

1. 文書中の該当箇所（節、行、表のセル）
2. 反証に使った一次資料と、そこで確認した内容
3. この指摘が正しい場合に起きる具体的な失敗

再現も反証もできない疑いは、指摘ではなく `未確認` として分けて保持する。

## 3. 指摘を格付けする

| 格 | 定義 | 扱い |
|---|---|---|
| `P1`（最優先） | 文書のとおりに実装・判断すると誤った結果になる、または作業が停止する。事実誤り、矛盾、実在しない参照、検証不能な受け入れ条件、責務境界の逸脱、根拠のない断定 | このスキルの終了条件。0件になるまで反復する |
| `P2` | 品質、保守性、追跡性に影響するが、実装は正しく進む。冗長、重複、優先順位の根拠不足、粒度の不揃い | P1 が0件になった後、コストが小さいものから直す |
| `P3` | 表現、用語、体裁 | まとめて直す。単独で巡を回さない |

格付けで迷った場合は下げる。P1 を水増しすると終了条件が意味を失う。

**P1 に昇格させてよい典型**

- 参照先（ファイル、テスト名、要件ID、シンボル）が実在しない。
- 同じ対象について文書内の2箇所が異なることを述べている。
- 「実装済み」「テスト済み」「確認済み」の根拠が示されていない、または示された根拠が存在しない。
- 受け入れ条件が観測方法を持たない。
- 計測値・件数が、再現手順なしに書かれている。
- ユーザーが下した決定と、文書の記述が食い違っている。

**P1 にしてはならない典型**

- より良い書き方の提案。
- 網羅性の不足のうち、文書の役割上そもそも対象外のもの。
- 自分の好みと異なる構成。

## 4. 修正する

P1 から順に直す。1巡で扱う修正は、互いに独立した範囲に限る。

- 事実誤りは、一次資料で確認した内容へ置き換え、確認した場所を文書へ残す。
- 矛盾は、どちらが正しいかを一次資料で決めてから片方を直す。両方を残した折衷にしない。
- 実在しない参照は、実在する名前へ直すか、参照ごと削除する。存在しないものを存在するかのように書き直さない。
- 検証不能な受け入れ条件は、観測方法へ変換する。変換できない場合は `P1` のままエスカレーションへ回す。
- 根拠のない断定は、根拠を付けるか、断定を下げる（`確認済み` → `未確認`）。

修正で決定内容が変わる場合は修正しない。5章へ回す。

## 5. ユーザーの意思決定が必要なら停止する

次のいずれかに該当する指摘は、自力で直さずエスカレーションし、**タスクを止める**。

- 製品判断、スコープ、優先順位、受け入れ基準そのものを変える必要がある。
- 相反する制約があり、どちらを優先するかが文書と一次資料から決まらない。
- 修正が不可逆、または文書の外（コード、設定、公開契約）へ影響する。
- 検証に必要な情報がリポジトリ外にしかない（実機計測、外部仕様、第三者の判断）。
- 同じ指摘が2巡続けて解消できず、修正案が互いに対立している。
- ユーザーが下した決定と一次資料が矛盾している。

エスカレーションは次の形で提示する。

1. 観察事実と、確認した一次資料
2. なぜ自力で決められないか
3. 2〜3個の現実的な選択肢とトレードオフ
4. 根拠のある推奨案、または根拠が弱いことを明示した暫定案
5. この判断が決まるまで停止する範囲

一度に扱うエスカレーションは1〜3件までとする。回答を待たずに周辺を書き換えない。回答が出るまで停止する範囲を明示し、影響しない P1 があればそれは先に直してよい。

## 6. 反復と収束

1巡ごとに次を行う。

1. 前巡の修正箇所を最初にレビューする。修正が新しい P1 を作っていないかを確認する。
2. 前巡で見た観点と異なる観点を少なくとも1つ加える。同じ読み方を繰り返すと同じものしか見えない。
3. 指摘、格、対処、結果を記録する。

**終了条件**

次の両方を満たしたとき、堅牢化を完了とする。

- P1 が0件である。
- 直近2巡で新しい P1 が1件も出ていない。

1巡で P1 が0件でも、その巡が最初の巡なら終了しない。1回のレビューで見落としがないと仮定しない。

**停止条件（完了ではない停止）**

- エスカレーションの回答待ち。
- 5巡しても P1 が0件にならない。文書の構造そのものに問題がある可能性が高いため、反復を止めて構造の問題として報告する。
- 検証手段が無く、残る P1 が確認不能である。未確認として明示し、影響を添えて渡す。

同じ箇所を3巡以上書き換えている場合は、修正ではなく揺り戻しが起きている。書き換えを止め、どの表現が正しいかをエスカレーションする。

## 7. 完了を報告する

最終報告は簡潔に、次を含める。

- 実施した巡回数と、各巡で出た P1 の件数
- 解消した P1 の内容と、根拠にした一次資料
- 残した P2 / P3 と、残した理由
- エスカレーションした論点と、その決着
- 未確認のまま残る主張と、その影響
- 修正によって変わった文書の箇所

「レビューした」ではなく「何を反証し、何が反証できなかったか」を書く。指摘が0件で終わった場合は、どの観点で攻めた結果0件だったかを示す。示せない場合、その巡は実施していないのと同じである。
