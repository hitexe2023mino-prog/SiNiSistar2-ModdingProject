# 敵対レビューの観点

対象文書の役割に該当する観点だけを使う。全項目を機械的に適用しない。1巡ごとに、前巡と異なる観点を少なくとも1つ加える。

## 攻め方の原則

文書の表現ではなく、文書が主張する事実を攻める。「読みにくい」ではなく「この行は嘘である」を探す。

各観点は「疑い」ではなく「確認手順」として使う。確認できなければ指摘にせず `未確認` として分ける。

## 観点1: 参照の実在（最も費用対効果が高い）

文書が挙げる名前は、書いた時点では正しくても、その後の改名で嘘になる。

| 参照の種類 | 確認手順 |
|---|---|
| ファイルパス | 実際に存在するか。相対パスが文書の位置から解決するか |
| テスト名 | `tests/` を検索して一致するか。**一致がその文書の中だけなら実在しない** |
| コードのシンボル | `src/` を検索して実在するか。改名前の旧名が残っていないか |
| 要件ID（`FR-*`、`AC-*`、`DEC-*`） | 正本仕様に存在するか。撤回記録へ移っていないか |
| 他文書の節番号 | 参照先の見出しが実在し、内容が一致するか |

この観点は機械的に実行でき、見つかる欠陥は例外なく `P1` である。最初の巡で必ず行う。

## 観点2: 主張と根拠の対応

| 問い | 確認手順 |
|---|---|
| 「実装済み」の根拠は何か | 該当コードを読む。コミットを確認する |
| 「テスト済み」の根拠は何か | そのテストを実際に見つける。名前だけの記載を信用しない |
| 「確認済み」は誰がいつ何で確認したか | ログ、実機記録、一次資料のいずれかがあるか |
| 数値・件数・行数はどこで数えたか | 同じ手順で数え直して一致するか |
| 「〜のため」の因果は成立するか | 原因と結果が入れ替わっていないか |

根拠のない断定は `P1` である。断定を下げる（`確認済み` → `未確認`）だけでも解消できる。

## 観点3: 文書内の整合

| 問い |
|---|
| 同じ対象について、2箇所が異なることを述べていないか |
| 表の値と本文の記述が一致しているか |
| 既定値・閾値が、仕様本文・設定表・実装の3箇所で一致しているか |
| 用語が同じ意味で使われているか。同義語が混在していないか |
| 見出しの主張と、その節の中身が一致しているか |

## 観点4: 検証可能性

| 問い |
|---|
| 受け入れ条件は外部から観測できるか。「正しく動作する」で終わっていないか |
| 何をもって完了とするかが、読み手によらず同じ判定になるか |
| 性能・品質の主張に、計測方法と基準値があるか |
| 「改善する」の対象が、改善前の状態とともに書かれているか |

## 観点5: 失敗と境界

| 問い |
|---|
| 正常系だけを書いていないか。失敗、取消、再試行、同時実行、復旧はあるか |
| 境界値（0、上限、空、未設定、不可読）の扱いがあるか |
| 「できない場合」の縮退動作が決まっているか |
| 前提が崩れたときに何が起きるかが書かれているか |

## 観点6: 責務と越境

| 問い |
|---|
| この文書の役割を超えた決定を含んでいないか（計画文書が仕様を決めていないか） |
| ユーザーが下した決定を、無断で変更・拡張していないか |
| 引き継ぐべき事項が、引き継がずに本文へ混ざっていないか |
| スコープ外と将来課題が混同されていないか |

## 観点7: 実装者の視点

この文書だけを読んだ実装者を想定する。

| 問い |
|---|
| 対象ファイルが特定できるか。「関連箇所」で終わっていないか |
| 依存する先行作業が明示されているか |
| 複数の解釈が成立する文はどれか |
| 書かれていないことを、実装者が推測で埋める必要があるか |

## 観点8: 自己バイアス

自分が書いた文書には、書いた時点の思い込みがそのまま残る。

| 問い |
|---|
| 調べずに「そうだろう」と書いた箇所はどこか |
| 直前の対話で得た情報だけに依存し、一次資料で確認していない主張はどれか |
| 推奨案の根拠が、自分の推奨であること以外にあるか |
| 都合の悪い事実を、脚注や条件節へ退避させていないか |
| 一度書いた結論を守るために、後から根拠を足していないか |

この観点は最も見落としやすい。2巡目以降に必ず1回は使う。
