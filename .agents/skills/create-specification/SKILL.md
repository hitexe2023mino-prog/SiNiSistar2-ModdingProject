# Create Specification

新しいアイデアや要求を批評的に設計し、設計者、実装者、検証者が同じ解釈で使える最初の正本仕様を作成する。根拠のない要件を発明せず、要件、設計判断、受け入れ条件の対応関係を保つ。

## 責務境界

| スキル | 入力 | 主な成果物 |
|---|---|---|
| `create-specification` | 正本仕様がないアイデア、目的、要求、制約 | 新規仕様書 |
| `refine-specification` | 既存の仕様書、要件定義、設計書、RFC | 実装可能で検証可能な改訂仕様書 |
| `implement-from-spec` | 確定済み、または実装可能と判定された仕様 | コード、設定、移行、テスト |

アイデアの重要な未決事項はこのスキル内で対話して確定する。正本となる既存仕様を発見した場合、または既存仕様の意味変更が主目的なら `refine-specification` へ引き継ぐ。

## 基本原則

- 提案された解決策より先に、解決すべき問題、対象利用者、期待する変化を確認する。
- アイデアを肯定するための理屈を作らない。不要な機能、成立しない前提、過剰な複雑さを根拠と影響で指摘する。
- `ユーザーの決定`、`資料からの事実`、`推論`、`提案`、`仮定`、`未決事項`を混同しない。
- リポジトリや資料から調査できる事項は先に安全な読み取り調査を行い、ユーザーへ質問しない。
- 低影響で可逆的な仮定は明示して進める。主要UX、データ、安全性、互換性、コストを左右する判断は黙って補完しない。
- ユーザーが指定した言語、読者、文書形式、出力先に従う。
- 仕様書の生成までを担当する。ユーザーが実装も明示的に求めた場合だけ、完成後に `implement-from-spec` へ進む。

## 1. 入力と成果物を確定する

1. ユーザーの依頼、指定資料、既存仕様を最後まで読む。
2. リポジトリ内の `AGENTS.md`、開発規約、関連コード、テスト、類似仕様を確認する。
3. 解決する問題、対象利用者、期待する成果、対象範囲、主要制約、正本となる情報源、想定読者、期待する出力先を特定する。
4. 新規文書の作成依頼であることを確認する。特定の既存仕様の批評や改訂は `refine-specification` を使用する。
5. 情報を `確定事項`、`資料からの事実`、`推論`、`提案`、`未決事項` に分ける。

不足情報をリポジトリや指定資料から安全に判定できる場合は先に調査する。低影響で可逆的な文書上の仮定だけを明示して採用する。製品の振る舞い、主要UX、公開契約、データ意味論、互換性を左右する未決事項は、依存関係の上流から一度に1〜3件だけ質問する。

各質問には必要に応じて、観察した問題、今決める理由、2〜3個の現実的な選択肢とトレードオフ、根拠のある推奨案を短く含める。選択肢で探索を狭める場合は自由回答も可能にする。回答後は、決定、影響を受ける設計、要件、受け入れ条件、残る論点を更新してから次へ進む。

## 2. 根拠を収集する

仕様へ影響する範囲だけを調査する。

- 既存のアーキテクチャ、公開インターフェース、データ、設定
- 類似機能と既存の命名・文書構造
- テストで保証されている現在の契約
- 外部ソフトウェア、ファイル形式、プロトコル、プラットフォーム制約
- 互換性、移行、運用、セキュリティ、性能上の制約

資料の事実、コードからの推論、ユーザーが確定した判断、作成時の仮定を区別する。変更され得る外部仕様や正確な引用が必要な資料は一次情報を確認し、出典を記録する。コードの現状を無条件に望ましい仕様とみなさない。

## 3. アイデアを批評して設計する

新しい解決案、複数コンポーネント、外部連携、または高リスクな変更では、[references/idea-review-checklist.md](references/idea-review-checklist.md) を読む。全項目を機械的に質問せず、該当する観点だけを使用する。

1. 提案された解決策より先に、問題、対象利用者、現在の回避策、期待する変化を確認する。
2. 機能が目的と成功判定へ因果的につながるか検証し、不要な機能を除く。
3. 主要な振る舞い、UX、アーキテクチャ、データ、運用が未確定なら、実現可能な案を2〜3個比較する。
4. 各案の価値、複雑さ、コスト、依存関係、互換性、可逆性、失敗時の影響、検証方法を比較する。
5. 根拠に基づく推奨案を示す。根拠がない数値や偽の選択肢を発明しない。
6. 回答を要件、設計判断、受け入れ条件、未決事項へ反映し、重大な矛盾がなくなるまで反復する。

ユーザーが判断を委ねた場合は、確認済みの目的と制約に最も整合する案を選び、理由と仮定を記録する。重大または不可逆な影響があり判断材料が不足する場合は推測しない。

論点を `Blocking`、`Important`、`Minor`、`Resolved` に分類し、設計を分岐させる `Blocking` から扱う。ユーザーが早期終了を求めた場合は、残る論点と影響を `TBD` として列挙し、「完成仕様」ではなく「作業版」として渡す。

## 4. 要件と設計を構成する

既存テンプレートまたはユーザー指定形式を優先する。形式がない場合は [references/specification-template.md](references/specification-template.md) を読み、該当する節だけを使用する。

次の順で構成する。

1. 問題、目的、成功の判定方法を定義する。
2. 対象、非対象、前提、制約、用語を定義する。
3. アクター、主要フロー、状態、ルール、境界値、副作用を記述する。
4. 正常系だけでなく、失敗、取消、再試行、復旧、並行操作を必要に応じて定義する。
5. データ、入出力、外部依存、互換性、移行を定義する。
6. 性能、セキュリティ、可観測性、運用性など重要な非機能要件を観測可能にする。
7. 各必須要件へ安定したIDを付け、受け入れ条件から参照する。
8. 採用した主要設計と代替案、判断理由、見直し条件を記録する。

規範的な要件には一貫した表現を使う。「適切に」「高速に」「必要に応じて」など判定不能な語は、条件と期待結果へ変換する。根拠のない数値目標を発明せず、必要なら測定方法と確定責任者を延期事項として記録する。

## 5. 文書を作成する

出力先が指定されていれば従う。指定がなく、リポジトリに `docs/specifications/` と `SPECNNN.md` の慣例がある場合は、未使用の次番号で作成する。既存ファイルを暗黙に上書きしない。ほかの慣例がある場合はそれを優先する。

一つの統合仕様書を既定とする。読者や更新周期が異なる場合だけ成果物を分割し、正本を明示して重複を避ける。仕様本文には調査や対話の経緯ではなく、確定した結果を記述する。

図は、コンポーネント関係、処理順序、状態遷移を文章より明確にできる場合だけ使用する。

## 6. 完成度を検証する

次を確認する。

- 問題、目的、対象利用者、成功判定がつながっている。
- 対象と非対象、前提と確定事項、要件と実装詳細を区別している。
- 主要フロー、状態、例外、データ、依存関係を記述済み、または非該当としている。
- すべての必須要件に観測可能な受け入れ条件がある。
- 要件ID、設計判断、受け入れ条件の参照が整合している。
- 未定義語、孤立した要件、解消されていない矛盾、重大な未決事項がない。
- 前提、延期事項、残存リスク、採用しなかった主要案を追跡できる。

重大な未決事項が残る場合は「完成仕様」とせず、影響付きの作業版として提示する。以後その文書を改訂する作業には `refine-specification` を使用する。

## 7. 完了を報告する

最終報告に次を含める。

- 作成した仕様書への参照
- 仕様化した範囲と主要な設計判断
- 使用した主要な根拠と明示した仮定
- 検証結果
- 延期事項、残存リスク、精緻化への引き継ぎ（なければ「なし」）
