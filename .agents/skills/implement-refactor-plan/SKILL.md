# Implement Refactor Plan

確定したリファクタ計画を、施策単位でコードへ反映する。計画そのものは設計し直さず、施策・変更・検証の対応関係を維持する。

## 責務境界

| スキル | 入力 | 主な成果物 |
|---|---|---|
| `create-specification` | 正本仕様がないアイデア、目的、要求、制約 | 新規仕様書 |
| `refine-specification` | 既存の仕様書、要件定義、設計書、RFC | 実装可能で検証可能な改訂仕様書 |
| `refine-refactor-plan` | リファクタ計画書、改善要項、負債の棚卸し | 採否と優先順位が確定した施策台帳 |
| `implement-refactor-plan` | 確定した施策台帳 | コード、テスト、計測結果、対応記録 |
| `implement-from-spec` | 確定済み、または実装可能と判定された仕様 | コード、設定、移行、テスト |

このスキルは既存の挙動を保ったままコードの内部品質を改善する。外部から観測できる挙動、ゲームルール、受け入れ条件は変更しない。計画に `仕様変更` 種別の施策が含まれる場合、それは実装せず引き継ぐ。新機能や仕様に基づく挙動変更は `implement-from-spec` の担当である。

## 1. 入力と実装レディネスを確定する

1. 指定されたリファクタ計画と、参照された仕様書、トレーサビリティ、変更履歴を最後まで読む。
2. リポジトリ内の `AGENTS.md`、開発規約、対象ディレクトリ固有の指示を確認する。
3. 実施対象の施策、範囲、優先順位、依存順を特定する。ユーザーが施策IDを指定した場合はそれだけを扱う。
4. 依頼が分析、計画、実装、レビューのどこまでを含むか判定する。実装を求められている場合は、計画だけで終了しない。
5. 次の実装レディネスを確認する。

- 施策の対象（ファイル、シンボル、MOD）が特定できる。
- 各施策に、外部から観測できる受け入れ条件と検証方法がある。
- 施策の種別（`振る舞い保存` / `性能` / `仕様変更`）が判別できる。
- 施策間の依存順が矛盾していない。

レディネスを満たさない場合は次のように引き継ぐ。

- 観点の羅列しかなく施策が確定していない: `refine-refactor-plan` へ引き継ぐ。
- 施策が外部挙動やゲームルールを変える: 該当施策の実装を止め、`refine-specification` で仕様を確定してから `implement-from-spec` へ渡す。
- 正本仕様がない機能を新設する必要がある: `create-specification` へ引き継ぐ。

満たす施策と満たさない施策が混在する場合は、満たす施策だけを実装し、止めた施策と理由を報告する。

## 2. 変更前の基準を固定する

改善の前に、何が壊れていないかを判定する基準を作る。

1. 対象範囲の既存テストを実行し、変更前の結果を記録する。
2. テストが対象の挙動を守っていない場合は、リファクタ前に特性テストを追加する。挙動を変えない改善では、このテストが唯一の安全網になる。
3. `性能` 施策では、計画に定めた方法で変更前の値を計測して記録する。基準値なしに最適化を始めない。
4. 生成物や配置先（`BepInEx/plugins/` 配下の DLL など）の更新経路を確認し、手編集しない。
5. 作業ツリーの差分を確認し、ユーザーの未コミット変更を保持する。無関係な変更を修正、整形、破棄しない。

対象コードの現状を仕様だと決めつけない。仕様と実装の不一致を見つけた場合は記録し、このスキル内でどちらかを勝手に合わせない。

## 3. 施策単位で実装する

依存順に、1施策ずつ完結させる。1つの施策の中でも、挙動を変えない編集と挙動を変える編集を混ぜない。

1. 変更を小さく一貫した単位に保ち、施策の範囲外へ広げない。
2. 既存のアーキテクチャ、公開 API、型、命名、エラー処理、テスト方法に合わせる。
3. 共通化は、実際に重複している箇所が現存する場合だけ行う。将来の利用を見込んだ抽象を先に作らない。
4. MOD が互いに独立して動作し個別に更新できる前提を壊さない。共通化のために MOD 間へ新しい依存を作る場合は、その必要性を報告に含める。
5. 公開されている契約（設定ファイル、HTTP エンドポイント、ログ形式、保存データ）を変える場合は、互換性の扱いを明示する。
6. 各施策の後に差分を見直し、施策に不要な変更が入っていないことを確認する。

発見した既存不具合が現在の施策を妨げる場合は、最小限の修正を含めて理由を報告する。妨げない場合は範囲を広げず、別の所見として記録する。

## 4. 挙動が変わっていないことを検証する

検証は施策の種別とリスクに比例させる。判定の観点は [references/behavior-preservation.md](references/behavior-preservation.md) を読む。

可能な限り次の順で行う。

1. 変更箇所に近いテスト
2. ビルド、静的解析、型検査（`TreatWarningsAsErrors` のため警告は失敗として扱う）
3. 関連する MOD の回帰テスト
4. `性能` 施策では、変更後の計測と基準値との比較
5. 実機やゲーム内でしか確認できない範囲は、確認手順を提示してユーザーへ依頼する

各施策を `実施済み`、`テスト済み`、`未検証`、`対象外`、`ブロック中` のいずれかに更新する。テストが実行できない場合は、実行していない事実、理由、代替確認、残るリスクを明記する。テストを通すために受け入れ条件を弱めない。既存テストを変更した場合は、なぜその変更が挙動の変化ではないのかを説明する。

## 5. 対応記録を残す

複数施策、複数 MOD、または段階的な移行を伴う作業では、施策IDと実装・検証の対応を残す。既存の `docs/implementation/` にあるトレーサビリティの形式に合わせ、計画文書と同じIDで参照できるようにする。

小さな変更では、同じ項目を作業メモとして簡潔に保持してよい。

外部から見える挙動が変わった場合は、その事実を隠さず報告し、`docs/CHANGELOG.md` の更新要否をユーザーへ確認する。

## 6. 完了を報告する

最終報告は簡潔に、次を含める。

- 実施した施策IDと、それぞれの変更内容
- 変更した主要ファイル
- 実行した検証と結果（変更前後の比較を含む）
- 採用した重要な仮定と設計判断
- 実装せず引き継いだ施策と引き継ぎ先
- 未完了、未検証、既知の制約、残るリスク

完了と言う前に、対象施策のすべてが実装または明示的に処理され、変更前に固定した基準に照らして挙動が保たれていることを確認する。
