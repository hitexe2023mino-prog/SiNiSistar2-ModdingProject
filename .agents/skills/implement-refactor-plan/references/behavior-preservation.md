# 挙動保存の判定

`振る舞い保存` 種別の施策では、「テストが通った」だけでは不十分な場合がある。次の観点で、変更が外部から観測できる挙動を変えていないかを確認する。

## 観測面ごとの確認

| 観測面 | 変わっていないことの確認方法 |
|---|---|
| 公開 API・型 | シグネチャ、既定値、null 許容性、例外の種類が同じか |
| 設定ファイル | 受け付ける鍵、既定値、無効値の扱いが同じか |
| 永続データ | 保存形式、鍵の意味、旧データの読み込み結果が同じか |
| ログ・診断出力 | 下流が解析している形式（JSON Lines など）の構造と項目が同じか |
| HTTP・IPC | 経路、要求形式、応答形式、失敗時の応答が同じか |
| 実行順序 | 初期化順、イベント発火順、副作用の順序が同じか |
| 失敗経路 | 例外時、未接続時、再試行時の結果が同じか |
| 数値計算 | 丸め、飽和、整数除算、浮動小数の評価順が同じか |

上の面に変更が及ぶ場合、それは内部改善ではない。施策を止め、仕様側の判断へ引き継ぐ。

## 特性テスト

既存テストが対象の挙動を守っていない場合、リファクタ前に現在の挙動を固定するテストを追加する。

- 正常系だけでなく、境界値、失敗経路、順序依存を含める。
- 現在の挙動が望ましくないと分かっていても、そのまま固定する。修正は別の施策として分離する。
- 追加したテストは施策完了後も残す。

## 既存テストを変更するとき

既存テストの変更は、挙動が変わった疑いの合図である。次のどれに該当するかを明記する。

- `参照更新`: 名前空間、クラス名、シグネチャの変更に伴う機械的な追随。
- `重複整理`: 同じ検証の統合。検証している条件の集合は減っていない。
- `不備修正`: テスト自体が誤っていた。誤りの内容と、正しい期待値の根拠を示す。
- `挙動変更`: 期待値が変わった。これは `振る舞い保存` ではない。施策を止めて引き継ぐ。

## 性能施策

- 変更前の値を、計画に定めた方法で計測してから着手する。
- 同じ手順、同じ条件で変更後を計測し、両方の値を報告する。
- 改善が基準に届かない場合、変更を残す理由を別に示す。示せない場合は元へ戻す。
- 可読性や保守性を落とす最適化は、計測で効果を示せた場合だけ採用する。
