## 1. この文書の範囲

自動テストは59件が通っている。ここに書くのは**自動テストでは原理的に確認できないもの**に限る。

| 確認できないもの | 理由 |
|---|---|
| IL2CPP ネイティブ実装の意味論 | interop アセンブリにメソッド本体がない |
| パッチが正しい呼び出し経路に当たっているか | ゲームの実行が要る |
| セーブデータへの波及の有無 | セーブ・ロードの一巡が要る |
| EDI 連動 MOD との同時動作 | 両 MOD とゲームの起動が要る |
| フレーム時間への影響 | 実プレイが要る |

以下は**再実施しなくてよい**。自動テストが毎回確認している。

- 設定検証（未知名、負値、`Defilement` 拒否、`Off`、占有率警告、既定値の無変更性）
- 窓のスケジューリング（開始・終了・期間・レベル係数・ジッタ・長フレーム追従）
- 復帰窓の一回限りの開閉と置換
- 台帳の解除と失敗記録
- 再入ガード
- 禁止シンボルの不参照（穢れ軸、拘束ゲージ数値、拘束成立条件、EDI 依存面、保存値）

## 2. 準備

```bash
dotnet test SiNiSistar2.Edi.sln -c Release
```

```bash
dotnet build SiNiSistar2.Edi.sln -c Release
```

1. ゲームを一度起動して終了し、`BepInEx/config/community.sinisistar2.difficulty.cfg` を生成させる。
2. この時点では既定値が無変更相当（FR-128）なので、ゲームの挙動は MOD 導入前と一致していなければならない。一致しない場合、以降の測定はすべて無効である。
3. 測定用のセーブを2つ用意する。**難易度 `Normal` で開始したもの**と、**`穢れ` を十分に蓄積したもの**。

> `Tier=Off` は全パッチを止める。以下で「MOD 無効時」と書いた比較対象は `Tier=Off` での起動を指す。

## 3. 付録A の実測

調整値を確定する前に行う。各項目は SPEC002 付録A に対応する。結果はこの文書へ追記する。

### 3.0 起動 self-check（実測結果あり）

マネージャ初期化後の最初のフレームで、プラグインが1行出す。

```
Self-check: the game reports IsHardMode=..., checkValue=...; the save still holds ...
```

| 読み方 | 意味 |
|---|---|
| `IsHardMode=True` かつ `checkValue=Hard` | 報告値の差し替えが両方効いている |
| `IsHardMode=False` または `checkValue` が `Hard` でない | その経路は効いていない。9章のパッチ欠落として扱う |
| 3つ目が選択した難易度と一致 | MOD が保存値へ触れていない（A-1 の一次証拠） |
| 3つ目が `Hard` になっている | **保存値が汚染されている。** 直ちに `ForceHardData=false` にし、バックアップから復旧する |

**確定した実測（2026-08-08、ログ観測）** — `PlayerStatusManager.get_s_GameDifficultyForCheck` は**フィールドアクセサであり Harmony でパッチできない**。BepInEx ログに `is a field accessor, it can't be patched` が出る。実装は getter のパッチをやめ、静的フィールドの値を直接上書きする方式へ変更済み。`IsHardMode` は通常のメソッドでパッチが成立する。

### 3.1 難易度の報告と保存値（A-1、A-2）— 最優先

セーブ汚染は不可逆であり、他のどの測定よりも先に否定する必要がある。

| 手順 | 期待結果 | 判定 |
|---|---|---|
| 1. `Normal` のセーブをバックアップする | — | — |
| 2. `Tier=Nightmare` / `ForceHardData=true` で起動し、`Normal` のセーブを読み込む | 起動ログに `reportHard=True` が出る | A-2 |
| 3. `HardOverwrite` を持つ敵の攻撃、または `HardOnly` 配置のある区画へ到達する | `Hard` 側のデータが有効になっている | A-2 / **AC-102** |
| 4. セーブし、ゲームを終了する | — | — |
| 5. MOD を取り外して起動し、同じセーブを読み込む | **難易度が `Normal` のままである** | A-1 / **AC-104** |
| 6. セーブファイルをバックアップと比較する | 難易度に相当する差分がない | A-1 |

手順5または6が期待どおりでない場合、報告値の差し替えは保存値へ波及している。**`ForceHardData=false` を既定とし、FR-105 の縮退動作へ移る。** バックアップからセーブを復旧する。

### 3.2 状態異常の付与（A-3、A-4、A-5、A-6、A-15、A-16）

`Diagnostics.LogInterventions=true` で実施する。

| # | 手順 | 見るもの | 対応 |
|---|---|---|---|
| A-3 | `AbnormalRateMultiplier=3.0` にして、状態異常を持つ敵の攻撃を30回受ける | MOD 無効時より付与頻度が明らかに高い | 高くない場合、付与判定は `DamageManager.OneDamage` の外にある。当該機構を無効化し、介入点を再特定する |
| A-4 | 同上で `AbnormalRateMultiplier` を 1.5 / 3.0 / 10.0 と変えて比較する | 頻度の伸びが 10.0 で頭打ちになるか | 頭打ちなら値域は 0-100。`AbnormalRateScaling.AssumedMaximum` を確定する |
| A-5 | HP1 で発動する状態異常（`AddAbnormalConditionType.HP1`）を持つ敵で同じ測定をする | 倍率が効かない | 効かないのが正常。`HP1` 経路は確率を持たない旨を記録する |
| A-6 | 多段ヒットの攻撃を受ける | 起動ログに倍率の二重適用を示す異常な付与率が出ない | 出る場合、再入ガードの位置が誤っている |
| A-15 | `LevelBonus=2` にして、最大レベルでない状態異常を受ける | レベルが2段多く進み、立ち絵と UI が正しく追従する | 追従しない場合、`_IncrementLevel` が通知経路でない |
| A-16 | 同時付与数の上限に達した状態でさらに受ける | クラッシュせず、上限の挙動が MOD 無効時と一致する | — |

**AC-106 はここで確認する** — 同じ測定を、プレイヤーが敵へ状態異常を与える側で行い、頻度とレベルが MOD 無効時と一致することを確かめる。一致しない場合、非対称性が破れている。

### 3.3 拘束と無力化窓（A-7〜A-10）

`NullificationIntervalSeconds=4` / `NullificationDurationSeconds=1.5` / ジッタ0 で実施する。

| # | 手順 | 見るもの | 対応 |
|---|---|---|---|
| A-7 | 快楽系の状態異常を付けた状態で拘束され、抵抗キーを連打し続ける | 拘束ゲージが上がらない時間帯が周期的に現れる | 現れない場合、`GachaGachaSystem.Execution` は入力1回あたりの反映ではない |
| A-9 | 無力化窓の内側で連打を止める／続ける | どちらでもゲージが**減少**する | 減少しない場合、減衰は `Execution` 側にあり、DEC-103 が成立しない |
| A-8 | 快楽系を付けず、`穢れ` だけを蓄積した状態で拘束される | 無力化窓が発生しない。脱出difficultyは MOD 無効時と一致する | **AC-112 / AC-113**。一致しない場合、穢れ軸へ干渉している |
| A-10 | （参考）`PauseHoldUIAndGachaMsv` の挙動を調べる | 減衰も止まるか | 止まるなら現行実装（`Execution` の抑止）が正しい選択であることの裏付けになる |

あわせて確認する。

- **AC-111** — 快楽系が1つも有効でない拘束では、無力化窓が一度も発生しない。
- **AC-115** — 窓の内側でも拘束ゲージの UI が表示され続け、入力してもバーが伸びないことが画面から見える。
- **AC-116** — 窓の内側でイベントによる強制解放が起きると、拘束が解ける。

### 3.4 離脱と復帰遅延（A-11〜A-14）

`RecoveryPenaltySeconds=3` / `RecoveryMoveSlowRate` を実測で決める。

| # | 手順 | 見るもの | 対応 |
|---|---|---|---|
| A-11 | 身重系の状態異常を付けて拘束され、自力で脱出する | 脱出直後に移動が遅くなる | ならない場合、離脱の検出（`Lelia.IsHold` の立ち下がり）が全経路を捉えていない |
| A-11b | イベントによる強制解放、敵の撃破による解放、シーン遷移による解放でも同じ確認をする | いずれでも窓が開く。開かない経路を記録する | — |
| A-13 | `RecoveryMoveSlowRate` を 0.2 / 0.5 / 0.8 と変える | 値の意味（倍率か減算か）と実用域が分かる | 既定値を確定する |
| A-12 | 復帰遅延中にもう一度拘束され、脱出する | 移動速度が二重に遅くならない。窓の終了後、速度が MOD 無効時と一致する | **AC-119 / AC-120**。戻らない場合、寄与の解除漏れ |
| A-14 | 脱出直後の無敵時間を MOD 有無で比較する | 現状は差がない（未適用） | 短縮の適用先が特定できたら実装し、この行を更新する |

あわせて確認する。

- **AC-118** — 身重系が有効でない離脱では、移動が遅くならない。
- **AC-121** — 復帰遅延中でも、拘束の成立条件そのものは MOD 無効時と変わらない（すり抜けや異常な吸い込みが起きない）。

### 3.5 状態異常の分類（A-17）

既定の快楽系・身重系（SPEC002 6.1）が実際のゲーム内表現と合っているかを、プレイしながら見直す。合わない種別は設定から外す、または加える。分類は推論であり、ここで直すことを前提にしている。

## 5. 調整値の確定

3章の実測が済んだら、`BepInEx/config/community.sinisistar2.difficulty.cfg` へ値を記入し、起動ログで反映を確認する。確定した値と根拠を SPEC002 6章の表へ反映し、付録A の該当行を解消済みとして更新する。

実測が済んでいない項目の値は変更しない。無変更相当のまま残すのが FR-128 の意図である。
