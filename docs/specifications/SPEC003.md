## 1. 概要

### 1.1 背景と問題

本作の拘束は、HPを削られ、HP0でゲームオーバーになる形で決着する。したがって拘束の敗北条件は体力管理の一部であり、拘束そのものが何を意味するかとは結び付いていない。捕食や暴力を行う敵と、性的な行為を行う敵が、同じ「HPを削る」という一つの経路で処理されている。

その結果、次が成立しない。

- 性的な行為を受け続けたことの蓄積が、ゲーム上の状態として存在しない。回復すれば元に戻る。
- 敵の性質の違いが、拘束中の脅威の質の違いとして現れない。
- 拘束からの敗北が、体力ではなく「どれだけ受け入れてしまったか」で決まる設計になっていない。

本MODは、拘束中の敗北条件をHPから切り離し、**快楽**と**絶頂回数**という別の軸へ置き換える。あわせて、受け続けたことが戻らない形で蓄積する**堕落**を導入する。

v1.0 はこの置き換えを「HPが `0` へ達することだけを止める」形で実装した。HPは `1` で停止し、ダメージそのものは従来どおり通していた。実プレイの結果、切り離しは完了していないことが分かった。

- 性的な行為を受けている間もHPは削られ続け、HPゲージは依然として拘束中の脅威を映す計器だった。プレイヤーは快楽ではなくHPを見て危険を判断できた。
- 絶頂限界に達したあとの決着は、HPの残量と敵の次の一撃に委ねられていた。敗北の瞬間を決めていたのは絶頂回数ではなくHPであり、限界到達時にHPが満量であれば、その後もしばらく死ななかった。

v1.1 は切り離しを完成させる。性的な攻撃はHPを一切削らず、HPは非性的な脅威の計器としてのみ残る。そして絶頂限界への到達を、HPの残量を問わない即時の致死とする。

v1.0 の機構とその設計判断は、仕様として誤読されないよう本文から取り除き、[SPEC003-withdrawn.md](SPEC003-withdrawn.md) に非規範の記録として移した。同文書にあるものはすべて撤回済みであり、実装対象ではない。

イベントでしか発生しない上位デバフ（`AbnormalType.BreastSuper`）は、ローカライズもセリフも揃った完成済みの状態異常でありながら、通常プレイでは到達しない。本MODはこれを新しい蓄積系の到達点として通常プレイへ開放する。

### 1.2 目的

- 性的な攻撃がHPを削る経路を撤廃する。性的な行為を受けたことの帰結を、HPではなく快楽と絶頂回数だけで表す。
- 非性的な脅威（捕食、暴力、罠、スリップダメージ、環境ダメージ）のHPダメージは従来どおり残す。それによってHPが `0` へ達した場合のゲームオーバーは、絶頂回数を参照せず従来どおり成立させる。拘束中であっても同じである。
- 性的な攻撃を行う敵に対してのみ上昇する快楽ゲージを追加する。捕食・暴力を行う敵では上昇させない。
- 快楽が上限に達したとき絶頂させ、画面演出で明示する。
- 絶頂回数が限界に達した時点で、HPの残量、拘束の継続、敵の次の行動を問わずHPを `0` にし、ゲームオーバーを成立させる。限界回数はプレイヤーのステータスに応じて増える。
- 絶頂回数を、セーブポイントのアクティベートでリセットできるようにする。
- 受け続けたことが戻らない形で蓄積し、絶頂しやすくなる堕落を追加する。デバフの治療で減らない。
- `BreastSuper` を通常プレイでも到達し得る状態異常にする。
- SPEC001・SPEC002 と同一ゲームルートで共存し、いずれの動作も壊さない。
- ゲームのセーブデータを書き換えず、MODを取り外せば痕跡を残さない。

### 1.3 成功条件

1. 拘束中に性的な攻撃を受けてもHPが1点も減らない。ダメージ表示、被弾演出、状態異常の付与は従来どおり発生する。
2. 拘束中に非性的な攻撃、スリップダメージ、環境ダメージでHPが `0` になった場合、絶頂回数を参照せずゲームオーバーが成立する。拘束外のHP0によるゲームオーバーはMOD導入前と変わらない。
3. 性的な攻撃を行う敵に拘束されている間だけ快楽が上昇し、捕食・暴力のみを行う敵では上昇しない。
4. 快楽が上限に達すると絶頂が発生し、画面演出で識別でき、快楽が0へ戻り、絶頂回数が1増える。
5. 絶頂回数が限界に達したその瞬間に、HPが満量であってもHPが `0` になり、ゲームオーバーが成立する。
6. 限界回数がプレイヤーのステータスに応じて増える。
7. セーブポイントをアクティベートすると絶頂回数が0へ戻る。堕落は戻らない。
8. 堕落は絶頂と性的攻撃の被弾で増加し、いかなる操作でも減少しない。デバフを治療しても減らない。
9. 堕落が高いほど、同じ攻撃で快楽がより多く上昇する。
10. `BreastSuper` が通常プレイ中に発生し得る。
11. 堕落と絶頂回数がセーブ・ロードをまたいで保存され、ロード後に保存時点の値へ戻る。
12. MODを取り外したとき、ゲームのセーブデータに本MOD由来の差分がない。
13. SPEC001・SPEC002 が同時に動作している状態で、いずれの動作も停止しない。

## 2. スコープ

### 2.1 対象

- 拘束中の性的被弾に限ったHP減算の無効化。
- 快楽ゲージの導入、上昇条件、減衰、上限。
- 性的攻撃と非性的攻撃の判別。
- 絶頂の発生、画面演出、絶頂回数の加算。
- 絶頂限界回数の算出と、限界到達時のHPの `0` 化。
- セーブポイントでの絶頂回数リセット。
- 堕落の蓄積、快楽上昇への反映、減少の禁止。
- 通常プレイ中の `BreastSuper` 付与。
- 堕落と絶頂回数のセーブスロット単位の永続化と、ゲームのセーブ・ロードとの同期。
- BepInEx `ConfigEntry` による調整値。
- SPEC001・SPEC002 との共存条件。

### 2.2 非対象

- 性的被弾の**HP減算以外**の作用の停止。ダメージ表示、被弾演出、状態異常の付与、ノックバック、無敵時間は従来どおり発生する。撤廃するのはHPが減ることだけである。
- 非性的な被弾、スリップダメージ、環境ダメージ、落下によるHP減少への介入。拘束中であっても介入しない。
- 拘束外のHP0によるゲームオーバー、ゲームオーバー後の復帰処理、ペナルティの変更。
- ゲームオーバー処理そのものの呼び出し。MODが行うのはHPを `0` にすることまでであり、その後の経路はゲームのものである。
- ゲームのセーブデータファイル、`SaveFlagAndVariable`、`GameAssembly.dll`、`global-metadata.dat`、ゲームアセットの書き換え。
- ゲーム本体の演出資産の改変、新規スプライト・アニメーションの追加。
- 快楽・堕落・絶頂回数のゲーム内設定画面。調整はBepInEx設定で行う。
- 敵のAI、行動パターン、拘束の開始条件の変更。
- SPEC002 の3機構（状態異常の強化、無力化窓、復帰遅延）の変更。
- 既存セーブへの遡及。MOD導入前の被弾履歴は堕落に反映しない。
- `BreastSuper` 以外のイベント限定コンテンツの開放。

### 2.3 前提と制約

- MODはBepInEx 6 IL2CPP環境で動作し、HarmonyXを実行基盤として利用できる。
- 介入はすべて実行時パッチ、`MultiSettingValue` への寄与登録、またはMOD側ファイルへの書き込みに限る。ゲームバイナリとアセットを改変しない。これはSPEC001のEDI連動MODが `GameAssembly.dll` と `global-metadata.dat` のSHA-256を照合するため、共存の必須条件である。
- ゲームのHPは `SiNiSistar2.Obj.BattleMainParameter` として実装され、`PlayerStatusManager.HP` から到達できる。減算を止める `DontSub`、全損させる `SubAll(bool)`、現在値を書く `SetCurrentValue(int, bool)`、回復する `Recover(int, bool)` を公開している。HP減算を止める手段とHPを `0` にする手段はいずれもゲーム自身のものであり、MODはHPの値を自分で計算しない。
- `SiNiSistar2.Damage.DamageManager.OneDamage(DamageStack)` は1件の被弾を解決する地点であり、本MODは既にここで被弾と付与された状態異常を観測している。したがって被弾単位の前後で介入する縫い目が既に存在する。
- ゲームは被弾を無害化する機構を複数持つ（`StatusCondition.RemainHp1Msv`、`StatusCondition.IsInvincibleMsv`、`PlayerStatusManager.DamageInvincibleMsv`、`DamageStack.BrinkOfDamageOverrider.ForceRemainHP1`）。いずれも**被弾そのもの**または**HPの下限**に作用するもので、「HPの減算だけを止め、状態異常と演出は通す」用途には合わない。採否は4.5にある。
- `SiNiSistar2.Obj.LeliaDeadState` は `Live` / `HP0` / `GameOver` の3値であり、ゲームオーバーはHP0とは別の状態である。`Lelia.IsHP0` はHP0以降で真になる。
- 快楽・絶頂・堕落に相当する概念はゲーム側に存在しない。ゲージ、演出、保存はすべてMOD側で構成する。
- ゲームのフラグ変数システム（`SaveFlagAndVariable`）は `VariableType` の固定カテゴリと起動時に確定する固定長配列で構成され、新しい変数名を追加する手段がない。未使用インデックスの占有は、未使用であることを確認する手段がなく、ゲーム更新で進行状態を破壊し得るため採用しない（DEC-206）。
- `SiNiSistar2.Manager.SaveData` は `OnAfterLoadMainSaveData`、`OnBeforeSaveMainSaveData`、`OnAfterSaveMainSaveData` を UniRx `Subject` として公開する。`MainSaveData` は `SelectID` と `LoadedFileName` を持つ。MODはこれらを購読・参照して随伴ファイルを同期できる。
- `AbnormalType.BreastSuper` は実在し、ローカライズ（`ID_Ab_BreastSuper`）とセリフ（`Talk_BreastSuper_01`）を持つ完成済みの状態異常である。イベント限定であるのはコンテンツ側の都合であり、API上の制約ではない。
- 「性的な攻撃」の判別基準はゲーム側に存在しない。攻撃が付与する状態異常（`DamageParameter.m_AbnormalTypes`）からの推論であり、設定で上書きできる形にする。
- 拘束中の攻撃の一部は、ゲージ上の被弾として観測できない可能性がある。快楽の上昇契機は実測で確認する（付録A）。

## 3. 用語

| 用語 | 定義 |
|---|---|
| 快楽 | 拘束中に性的な攻撃を受けることで上昇する `0` 以上 `1` 以下のMOD側の値。上限に達すると絶頂する。 |
| 絶頂 | 快楽が上限へ達したときに発生する一回性のイベント。快楽を `0` へ戻し、絶頂回数を1増やし、堕落を増やし、画面演出を再生する。 |
| 絶頂回数 | 直近のリセット以降に発生した絶頂の回数。セーブスロットごとに保存する。 |
| 絶頂限界 | 拘束によるゲームオーバーが成立する絶頂回数。プレイヤーのステータスから算出する。 |
| 堕落 | 受けた性的な攻撃と絶頂によって蓄積する `0` 以上のMOD側の値。単調非減少であり、いかなる操作でも減少しない。快楽の上昇量に乗じる。 |
| 敵識別子 | 分類カタログが敵を名指すために用いる文字列。拘束相手から5.3.1の順序で解決する。`None` は敵識別子ではない。 |
| 表示名 | ゲームがその敵に与えている表記名（例「大口のワーム」）。ゲームのローカライズから取得する。判別には用いず、編集画面の表示とカタログの可読性のためにのみ用いる。 |
| 性的攻撃 | 快楽を上昇させる攻撃。判別は5.3による。 |
| 非性的攻撃 | 快楽を上昇させない攻撃。捕食、暴力、罠などが該当する。 |
| 随伴ファイル | 堕落と絶頂回数を保存するMOD側のファイル。ゲームのセーブスロット1つにつき1つ対応する。 |
| スロットキー | 随伴ファイルとセーブスロットの対応に用いる識別子。`MainSaveData.SelectID` と `LoadedFileName` から構成する。 |
| 絶頂演出 | 絶頂の発生をプレイヤーへ示すMOD側の画面表示。ゲームの演出資産を使用しない。 |
| 性的ダメージ無効化 | 拘束中の性的被弾について、HPの減算だけを行わせない制御。被弾そのもの、状態異常の付与、演出は通す。5.1による。 |
| 致死化 | 絶頂回数が絶頂限界へ達したことを契機に、MODがプレイヤーのHPを `0` にすること。5.5による。 |

## 4. 採用設計

### 4.1 全体構成

```
BepInEx (IL2CPP)
  └ community.sinisistar2.pleasure          ← 本MOD
      ├ PleasurePlugin (BasePlugin)          設定読込、パッチ適用、巻き戻し
      ├ Harmonyパッチ群                      ゲームへの介入点
      ├ PleasureOverlay (MonoBehaviour)      快楽ゲージと絶頂演出の描画
      ├ EnemyCatalogEditor                   敵別分類のゲーム内編集画面（F10）
      └ SiNiSistar2.Pleasure.Core            純粋ロジック（ゲーム参照なし・単体テスト対象）
          ├ PleasureProfile                  設定の検証済み表現
          ├ SexualAttackClassifier           攻撃の性的／非性的判別
          ├ EnemyAttackCatalog               敵別分類の保持と編集
          ├ EnemyAttackCatalogStore          分類カタログの読み書きと検証
          ├ PleasureMeter                    快楽の上昇・減衰・上限到達
          ├ ClimaxLedger                     絶頂回数、絶頂限界、リセット
          ├ CorruptionTrack                 堕落の単調蓄積
          └ SidecarDocument                  随伴ファイルの読み書きと検証

  └ community.sinisistar2.difficulty        ← SPEC002（本MODは依存しない）
  └ community.sinisistar2.edi               ← SPEC001（本MODは依存しない）
```

`Core` はUnityにもIL2CPPにも依存しない。快楽の増減、絶頂の判定、限界の算出、堕落の蓄積、随伴ファイルの直列化はすべて `Core` に置き、時刻を注入して単体テストで検証する。`Plugin` はゲームの値を読み、`Core` へ渡し、返った決定を適用するだけの層とする。SPEC001・SPEC002 と同じ構成である。

3つのMODは相互に参照せず、BepInExの依存宣言も行わない。いずれか1つだけを配置した構成も正当である。

### 4.2 拘束中の敗北条件の置き換え

```
【MOD導入前】
  拘束 ──> HPダメージ ──> HP0 ──> ゲームオーバー

【MOD導入後（v1.1）】
  被弾 ──> 性的攻撃か？（5.3、被弾ごとに評価）
            │
            ├─ いいえ（捕食・暴力・罠）
            │     └─> HPダメージ ──> HP0 ──> ゲームオーバー（絶頂回数を参照しない）
            │           ※拘束中でも同じ。スリップ・環境・落下も同じ
            │
            └─ はい かつ 拘束中
                  ├─> HPは1点も減らない（当該被弾の減算のみ無効化）
                  ├─> 状態異常・ダメージ表示・被弾演出はそのまま通る
                  └─> 快楽 +（基準量 × 堕落係数）
                        │
                        └─> 快楽が上限 ──> 絶頂
                                            ├─ 快楽を0へ
                                            ├─ 絶頂回数 +1
                                            ├─ 堕落 +（増分）
                                            ├─ 演出
                                            └─> 絶頂回数 ≧ 絶頂限界
                                                  └─> HPを0にする（致死化）
                                                        └─> ゲーム自身の死亡・ゲームオーバー経路
```

2つの敗北経路は独立している。**HPは非性的な脅威だけの計器**であり、性的な攻撃はそこへ一切書き込まない。**絶頂回数は性的な脅威だけの計器**であり、非性的な攻撃はそこへ一切書き込まない。どちらの計器が先に尽きてもゲームオーバーになる。

v1.0 は前者の経路を「HP `1` で停止」として塞いでいたが、これは計器を残したまま針を止める処置であり、拘束中の危険がHPゲージから読めるままだった。v1.1 は性的被弾がHPへ触れないようにすることで、計器の分離そのものを行う（DEC-256）。

同時に、致死化はHPの残量に依存しない。限界到達の瞬間にHPを `0` にするため、「あと1発耐えられるか」ではなく「あと1回絶頂させられるか」が敗北の判断になる（DEC-257）。

### 4.3 3つの値の関係

| 値 | 範囲 | 増加 | 減少 | 保存 |
|---|---|---|---|---|
| 快楽 | `0`〜`1` | 拘束中の性的攻撃 | 拘束外で時間減衰、絶頂で `0` | しない（セッション内） |
| 絶頂回数 | `0` 以上の整数 | 絶頂 | セーブポイントのリセットのみ | する |
| 堕落 | `0` 以上 | 絶頂、性的攻撃の被弾 | **しない** | する |

快楽は保存しない。拘束から解放された時点の高ぶりを次のセッションへ持ち越す意味がなく、保存すると「ロードした瞬間に絶頂する」状態を作れてしまう。

堕落は減少しない。これは要求そのものであり、治療・回復・セーブポイント・リセットのいずれの経路にも減少手段を設けない。堕落を下げる方法は、そのセーブを使わないこと以外に存在しない。

### 4.4 永続化

随伴ファイルはゲームのセーブスロットごとに1つ持ち、ゲームのセーブ・ロードに同期して読み書きする。

```
OnAfterLoadMainSaveData  ──> スロットキーを決定 ──> 随伴ファイルを読む ──> 堕落・絶頂回数を復元
OnAfterSaveMainSaveData  ──> スロットキーを決定 ──> 随伴ファイルを原子的に書く
```

これにより、ロードし直したときの挙動がゲームのセーブと一致する。セーブ時点へ戻れば絶頂回数も堕落もその時点の値へ戻る。堕落が「一方通行」であるのは1つのプレイ進行の中での話であり、過去のセーブへ戻る操作まで禁じるものではない。

ゲームのセーブデータへは書き込まない。フラグ変数システムを使う案は、新しい変数名を追加する手段がなく、未使用インデックスの占有がゲーム更新で進行状態を破壊し得るため採用しない（DEC-206）。

### 4.5 代替案とトレードオフ

| 論点 | 採用 | 採用しなかった案 | 理由 |
|---|---|---|---|
| 性的被弾のHP減算を止める範囲 | 当該被弾の解決の間だけ（被弾単位） | 拘束が成立している間ずっと止める | 同じ敵が混ぜてくる非性的攻撃まで無害になる。5.3は既に被弾ごとに判別しており、`Sexual` 宣言の敵ではどちらの案も同じ結果になる。差が出るのは `Auto` の敵だけであり、そこはゲーム側の情報に従うのが既定である |
| 同上 | HPパラメータの減算を止める（`DontSub`） | `IsInvincibleMsv` / `DamageInvincibleMsv` への寄与 | 無敵は被弾そのものを消す。状態異常が付かず、被弾が観測できず、快楽も上がらない。快楽機構の入力を断つ手段は採れない |
| 同上 | HPパラメータの減算を止める | `DamageStack.BrinkOfDamageOverrider.ForceRemainHP1` を立てる | 「HPを `1` で止める」ものであり「HPを減らさない」ものではない。v1.0 と同じ問題が被弾単位で再現するだけである |
| 同上 | HPパラメータの減算を止める | 減った分を直後に回復して戻す | HPゲージが1回の被弾ごとに揺れ、回復演出が出る。「受けていない」ではなく「受けて即座に治った」に見える。ただし減算を止められないことが判明した場合の代替として残す（FR-275） |
| 限界到達の表現 | MODがHPを `0` にする | HP0抑止の寄与を外して敵に殺させる（v1.0） | **v1.1 で撤回。** 性的被弾がHPを削らなくなった以上、抑止を外しても何も起きない。加えて敗北の瞬間がHPの残量で決まってしまう（CHG-003、DEC-257） |
| 同上 | `HP.SubAll` でHPを `0` にする | `GameOverLabel.ExecutionOne` を自前の `GameOverParameter` で呼ぶ | 復帰処理・ペナルティ・演出・セーブの再現責任をMODが負う。DEC-209 の判断はv1.1でも維持する |
| 同上 | `HP.SubAll` でHPを `0` にする | `Lelia.RequestCommonDead` を立てる | HPが減らないままゲームオーバーになるため、要求文「HPを0にする」と一致せず、HPゲージの表示も残る。到達を確認できない場合の代替としてのみ残す（FR-275） |
| 致死化の判定契機 | 絶頂が成立した瞬間のみ | 毎フレーム「限界以上か」を掃き取る | 限界以上のまま保存されたセーブをロードした瞬間に死ぬ。事象契機にすれば、ロード直後は死なず次の絶頂で死ぬ（DEC-258、FR-274と同じ思想） |
| 敗北条件 | 絶頂回数の限界 | 快楽ゲージ自体を敗北条件にする | 1回の拘束で決着し、「何度も絶頂させられた末に」という蓄積が表現できない |
| 性的攻撃の判別 | 付与する状態異常からの自動判別＋設定上書き | 敵IDの列挙のみ | 全敵を調べる工数が大きく、漏れた敵が無反応になる。自動判別なら未知の敵にも既定の答えが出る |
| 絶頂演出 | MOD独自のオーバーレイ | ゲームの演出資産の流用 | 流用可能な資産があるか実機調査が必要で、無ければ成立しない。独自描画は確実に出せる |
| 永続化 | セーブスロット単位の随伴ファイル | ゲームのフラグ変数システム | 新規変数名を追加できず、未使用インデックスの占有はゲーム更新で進行状態を破壊し得る（DEC-206） |
| 同上 | 随伴ファイル | セッション限定（保存しない） | 堕落が「一方通行で蓄積する」という要求が実質成立しない |
| 堕落の減少 | 手段を設けない | 高難度の治療手段を用意する | 要求が明示的に一方通行を求めている。逃げ道を作ると蓄積の意味が薄れる |

## 5. 制御仕様

### 5.1 性的ダメージ無効化

#### 5.1.1 適用条件

無効化は、次のすべてを満たす被弾についてだけ行う。

1. 受け側がプレイヤーである。
2. プレイヤーの拘束が成立している。
3. 5.3により性的攻撃と判定される。
4. `SuppressSexualHpDamage` が真である。
5. 快楽が上昇し得る設定である（`PleasureGainPerHit` が正）。

条件5は安全弁である。快楽が上がらない設定でHP減算だけを止めると、性的な拘束が何の代償もない状態になる。無効化はゲージという代替の代償があってはじめて成立する（FR-278）。

#### 5.1.2 無効化の内容

- 当該被弾はプレイヤーのHPを1点も減少させない。
- 抑止するのはHPの減算だけである。被弾の成立、ダメージ表示、被弾演出、状態異常の付与、ノックバック、無敵時間には介入しない。
- **MPの消費には介入しない。** MPを消費する性的攻撃があれば、MPは従来どおり減る。撤廃するのはHPという敗北の媒体であり、MPは敗北条件ではない（A-52、利用者決定 2026-08-09）。
- 抑止は**当該被弾の解決の間だけ**有効とし、解決後はゲーム側の状態を元へ戻す。拘束が続いていても、抑止を跨いで維持しない。
- 実現手段は次の順で試す。手段が変わっても上記の観測可能な結果は同じでなければならない（FR-275）。
  1. 被弾の解決の間だけ `PlayerStatusManager.HP.DontSub` を真にし、解決後に元の値へ戻す。
  2. 1が減算を止めないことが実測で判明した場合、被弾前のHPを記録し、解決後に減った分を `HP.Recover` で戻す。
- 手段1で立てた `DontSub` は、例外が起きた経路でも必ず元へ戻す。戻せなかった場合はこの機構を無効化し、対象と理由を記録する。

#### 5.1.3 介入しない範囲

- 非性的と判定された被弾。拘束中であっても介入しない。
- 攻撃以外によるHP減少（状態異常のスリップダメージ、環境ダメージ、落下、SPEC002由来の継続的な削り）。拘束中であっても介入しない。
- 拘束外のあらゆるHP減少。
- 上記によってHPが `0` へ達した場合のゲームオーバー。絶頂回数を参照せず、従来どおり成立する。

したがって、性的な敵に拘束されていることはHPの安全を意味しない。毒を抱えたまま捕まればHPは尽き、噛みつきを混ぜてくる敵は拘束中でもHPを削る。

#### 5.1.4 v1.0 の機構の撤去

- MODは `StatusCondition.RemainHp1Msv` へ寄与しない（FR-277）。他のMODやゲーム自身が同じ値へ寄与することは妨げない。
- HPが `1` で停止する状態は存在しなくなる。拘束から脱出したときのHPは、その拘束中に受けた**非性的な**ダメージだけで決まる。MODはHPを回復しない。

### 5.2 快楽ゲージ

- 快楽は `0` 以上 `1` 以下のMOD側の値とし、プレイヤーに対してのみ保持する。
- 上昇の条件は次のすべてを満たすことである。
  1. プレイヤーの拘束が成立している。
  2. プレイヤーが受けたダメージが5.3により性的攻撃と判定される。
- 1回の被弾による上昇量は `PleasureGainPerHit × (1 + 堕落 × CorruptionGainScale)` とする。
- 拘束が成立していない間、快楽は毎秒 `PleasureDecayPerSecond` の割合で減少し、`0` を下限とする。拘束中は減衰しない。
- 快楽はセーブしない。ゲームの起動ごとに `0` から始まる。
- 快楽が `1` に達した時点で5.4の絶頂が発生する。

### 5.3 性的攻撃の判別

敵ごとの宣言は、設定ファイルとは別の**分類カタログ**（6.2）に持つ。宣言は `Auto`・`Sexual`・`NonSexual` の3値であり、既定はすべて `Auto` である。

判別は次の順で行い、最初に一致した規則を採用する。

1. 拘束相手の**敵識別子**の宣言が `NonSexual` の場合、非性的攻撃とする。
2. 拘束相手の**敵識別子**の宣言が `Sexual` の場合、性的攻撃とする。
3. 受けたダメージの `DamageParameter.m_AbnormalTypes` が `SexualAbnormalTypes` のいずれかを含む場合、性的攻撃とする。
4. いずれにも当たらない場合、非性的攻撃とする。

- 宣言が `Auto` の敵は規則1と2に当たらず、規則3の状態異常判定へ進む。すなわち `Auto` は「ゲーム側の情報に任せる」であって「非性的」ではない。
- 既定は「判別できなければ非性的」とする。捕食・暴力を行う敵で快楽が上昇することは、要求に対する明確な誤りであり、無反応より重い。
- 拘束相手を特定できない場合、規則1と2を適用せず規則3へ進む。
- 判別結果は被弾ごとに評価する。同じ敵でも攻撃によって性的・非性的が分かれることを許す。
- 分類器はカタログを参照で保持する。編集は次の被弾から効き、再起動を要しない（DEC-212）。

#### 5.3.1 敵識別子の解決

拘束相手から次の順に解決し、最初に得られたものを敵識別子とする（DEC-260）。

拘束相手は2つの経路で得る。`Bind.BinderEnemy`（型は `EnemyObject`）と、`Bind.Binder`（型は `IBinder`）である。**後者が正であり、前者はそのうち `EnemyObject` であるものだけを指す。** `IBinder` は `SiNiObject` が実装しており、`EnemyObject` を継承しない拘束者（`ParasiteTentacle`、`ParasiteBullet`、`StoneEye`）が実在するため、`BinderEnemy` だけを見ると**それらの拘束は拘束相手が存在しないものとして扱われる**。

| 順 | 参照先 | 得られる識別子の例 |
|---|---|---|
| 1 | `m_GalleryEnemyID` が `None` 以外 | `GaID_Mimic` |
| 2 | `m_EnemyID` が `None` 以外 | `EnmID_MeatWorm1` |
| 3 | 拘束相手のオブジェクト名（正規化後、接頭辞 `obj:` を付す）。ただし構造名は除く | `obj:EnemyMeatWorm1`、`obj:ParasiteTentacle` |
| 4 | 拘束相手のコンポーネント型名（接頭辞 `obj:` を付す） | `obj:StoneEye` |
| 5 | いずれも得られない | 敵識別子は**無い**ものとする |

- 順1と順2の参照先は `BinderEnemy`、それが無い場合は `Binder` を `EnemyObject` として解釈できたときのその値とする。順3と順4の参照先は `BinderEnemy`、無ければ `Binder` そのものとする。
- したがって `EnemyObject` でない拘束者は順3か順4で名指される。名指せるかどうかが分類できるかどうかであり、`EnemyObject` かどうかは分類の可否と関係がない。
- `Root` や `Base` のような構造名も敵識別子ではない。このビルドでは拘束判定や攻撃判定が全キャラクターの `Root` という名のオブジェクトにぶら下がっており（実測ログのシーン階層）、そこに居合わせた拘束者どうしが1行を共有してしまう。`None` と同じ害であり、同じ理由で退ける。構造名だった場合は順4のコンポーネント型名へ進む。
- `None` は敵識別子ではない。`None` を識別子として扱ってはならず、カタログへ書いてもならない。`GalleryEnemyID` と `EnemyID` はいずれも `None` を列挙子として持つが、それは「未設定」を意味する値であって特定の敵を指さない。順5に至った場合は5.3の規則1と2を適用せず、規則3の状態異常判定へ進む。
- 順3の正規化は、末尾の `(Clone)` の繰り返し、末尾の ` (N)` 形式の連番、および前後の空白を除去する。Unityの実体名は複製と生成のたびにこれらが付くため、同じ敵が別の識別子として現れないようにする。
- 解決順は上から固定する。同じ敵が文脈によって別の識別子で現れてはならない。両方の列挙子が設定されている敵は常に順1で解決し、その敵の `EnmID_` 行は使われない。
- 順2以降は、`m_GalleryEnemyID` が `None` のまま拘束してくる敵を名指せるようにするためにある。順1だけではこれらがすべて `None` の一行へ潰れ、個別に宣言できない。実測（2026-08-09）では、拘束中の被弾3件で拘束相手が `None` と解決され、そのときの加害側の名はそれぞれ `EnemyMeatWorm1 (2)`（ゲーム内表記名「大口のワーム」）、`EnemyMeatTentacleCluster1`、`EnemyMeatWombBaby(Clone)(Clone)` であった。加害側が拘束相手と同一であるとは限らないため、拘束相手そのものの `m_EnemyID` の有無は A-53 で確かめる。**実測（2026-08-09、改訂後のビルド）で `EnmID_MeatTentacleCeiling` などが解決されることを確認済みであり、順2は実際に機能する。**

### 5.4 絶頂

- 快楽が `1` に達したとき、MODは次を1回だけ行う。
  1. 快楽を `0` へ戻す。
  2. 絶頂回数を1増やす。
  3. 堕落を `CorruptionPerClimax` だけ増やす。
  4. 絶頂演出を開始する。
  5. 5.5の限界判定を行い、限界以上であれば致死化する。
- 絶頂演出の間、快楽は上昇しない。演出の長さは `ClimaxOverlaySeconds` とする。
- 絶頂演出はMODが描画する。ゲームの演出資産、アニメーション、スプライトを使用しない。
- 絶頂演出はゲームの進行を停止させない。`Time.timeScale` を変更しない。
- 絶頂演出が描画できない場合でも、1から3および5.5の判定は行う。演出の欠落を理由に絶頂を成立させないことはしない。

### 5.5 絶頂限界と致死化

#### 5.5.1 限界の算出

- 絶頂限界 `N` は `ClimaxLimitBase + floor(耐久の最大値 × ClimaxLimitPerDurability)` とする。
- 耐久の最大値は `PlayerStatusManager.m_MaxDurability` から読む。読めない場合は `ClimaxLimitBase` のみとし、その旨を記録する。
- `N` が `0` 以下になる設定は設定エラーとし、この機構を無効化する。

#### 5.5.2 致死化の契機

- 契機は**5.4の絶頂が成立し、その結果として絶頂回数が `N` 以上になったこと**だけである。
- 毎フレームの掃き取りで「限界以上か」を判定して致死化してはならない。限界以上のまま保存されたセーブをロードした瞬間に死ぬ経路を作らないためである。そのような状態でロードした場合、プレイヤーは死なず、**次の絶頂**で死ぬ（DEC-258）。
- 絶頂回数が `N` 未満の間、絶頂は致死化を引き起こさない。
- `EnableClimaxGameOver` が偽の場合、致死化しない。限界以上になった事実を記録し、快楽・絶頂・堕落はそのまま継続する（FR-279）。
- 拘束の継続、HPの残量、敵の次の行動は条件ではない。絶頂が成立した瞬間に判定し、その場で致死化する。

#### 5.5.3 致死化の内容

- MODはプレイヤーのHPを `0` にする。手段は次の順で試す。
  1. `PlayerStatusManager.HP.SubAll` を1回呼ぶ。
  2. 1でHPが `0` へならない場合、`HP.SetCurrentValue(0, …)`。
  3. 2でも `Lelia.IsHP0` が真にならない場合、`Lelia.RequestCommonDead` を真にする。
- いずれの手段でもHP `0` または死亡要求に到達しなかった場合、その事実を記録し、ゲームを不整合な状態に残さない（HPを勝手に別の値へ書き換えない）。
- MODはゲームオーバー処理そのものを呼ばない。`GameOverLabel` を呼ばず、`GameOverParameter` を組み立てない。HPが `0` になったあとの死亡判定、演出、リトライ、ペナルティ、セーブはすべてゲームの既存経路に委ねる（DEC-209はv1.1でも維持する）。
- HPが `0` を経由するため、SPEC001の `game-over` トリガーは従来どおり `Lelia.IsHP0` で成立する。
- 二重発火を防ぐ。`LeliaDeadState` が `Live` でない場合、または当該の絶頂について既に致死化した場合は行わない。1回の絶頂につき最大1回とする。
- 致死化は絶頂演出の開始を妨げない。5.4の1〜4を先に行い、そのうえで致死化する。演出が描画できない場合でも致死化は行う。

### 5.6 絶頂回数のリセット

- セーブポイントまたはオベリスク（聖なる像）がアクティベートされたとき、絶頂回数を `0` へ戻す。
- 堕落は戻さない。
- 検出は `SavePointAsyncLabel.ExecutionOneAsync` の実行とする。当該ラベルの `IsObeliskLabel` により、オベリスクか通常のセーブポイントかを区別できる。
- `ResetAtObeliskOnly` が真の場合、`IsObeliskLabel` が真のときだけリセットする。偽の場合はいずれでもリセットする。既定は偽とする。`SavePointSelector.m_ChangeObeliskInHardMode` により、難易度によってはセーブポイントがオベリスクへ置き換わるため、オベリスク限定にすると難易度によってリセット地点が消える構成があり得る。
- セーブの完了を契機としない。オートセーブでリセットされることを避けるためであり、`MainSaveData.IsAutoSave` による区別に依存しないためでもある。
- リセットは随伴ファイルへ反映する。

### 5.7 堕落

- 堕落は `0` 以上のMOD側の値とし、単調非減少とする。
- 増加の契機は次の2つである。
  1. 絶頂したとき、`CorruptionPerClimax` だけ増やす。
  2. 拘束中に性的攻撃を受けたとき、`CorruptionPerSexualHit` だけ増やす。
- MODは堕落を減少させる経路を持たない。状態異常の治療、回復、休息、セーブポイントのアクティベート、絶頂回数のリセットのいずれでも減少させない。
- 堕落は `CorruptionCap` を上限とする。上限は成長の頭打ちであり、減少ではない。
- 堕落は快楽の上昇量に5.2の式で作用する。

### 5.8 通常プレイ中の `BreastSuper`

`BreastSuper` は完成済みの状態異常であり、イベント限定であるのはコンテンツ側の都合である。MODはこれを **`Breast` の上位ペナルティ**として通常プレイへ開放する。

**遷移の条件。** `Breast` が既に最大レベルにある状態で、さらに `Breast` の付与が `BreastSuperAfterApplications` 回到達したとき、`BreastSuper` へ遷移する。

- **最大レベル未満の付与は数えない。** その付与にはまだ行き先があり、レベルを上げることがゲーム自身の段階表現だからである。数えてしまうと、通常の進行が終わらないうちに上限側の演出が来る。最大レベルの `Breast` が吸収できなくなった打撃だけが、`Breast` の表現を超えた証拠になる。
- `BreastSuperCorruptionThreshold` を満たさない間は回数を保持したまま遷移を保留する。破棄はしない。閾値を満たした次の付与で遷移する。
- 既に `BreastSuper` がある場合は数えず、回数を `0` へ戻す。上位が存在しないため、治療後に再び膨乳したときは初めから積み直す。
- 遷移時、`BreastSuperReplacesBreast` が真なら `Breast` を除去する。`BreastSuper` の付与を先に行い、除去を後に行う。逆順は両方が存在しないフレームを作り、身体表現と立ち絵が状態異常一覧から駆動されるためである。
- 付与はゲームの状態異常付与経路（`AbnormalList.AddAbnormal(AbnormalType, int, DamageStack)`）で行い、`AbnormalList.Has` が真を返す実体のある状態として成立させる。偽の状態を報告させてはならない。`AbnormalSaveData` は `m_Type` と `m_Level` を持つため、ゲーム自身のセーブに乗る。MODの随伴ファイルへは書かない。
- 回数は随伴ファイルへ保存する。ロードで白紙に戻ると、上限付近まで積んだ状態が失われる（FR-222）。
- 付与の出所は問わない。敵の攻撃、アイテムの使用、author されたイベントのいずれも同じく数える。膨乳を付与するアイテムの多重使用で遷移させられることは、デバッグ手段として必要である（FR-244）。
- `BreastSuperAfterApplications` の既定は `0` とし、遷移が起こらない状態で出荷する（FR-233）。
- `BreastSuperCountBelowMaxLevel` を真にすると最大レベル未満の付与も数える。デバッグ専用であり、既定は偽である。

**実測（2026-08-08）。** `Breast` の `MaxLevel` は `1` である。したがって `Breast` は付与された時点で最大レベルにあり、以後の付与はすべて計数対象になる。`BreastSuperAfterApplications = 3` は「膨乳した状態でさらに3回」を意味する。

**治療。** MODは治療手段を新設しない。ゲームが持つ治療経路が `BreastSuper` へ届くかどうかを実測し（付録A A-14）、届かない場合にのみ最小の介入を行う。

- 静的調査で確認できたのは次である。`Breast` の治療は `ChoiceLocalizeID.ID_Choice_CureBreast` の選択肢から `DramaID.ID_CureBreast_Player`（自身で搾乳）と `ID_CureBreast_Haanja1` / `ID_CureBreast_Haanja2`（ハーニャによる搾乳）へ分岐する。搾乳の映像は `SceneID.Ga_Player_Other_1_Breast2` として存在する。
- 治療イベントを出す条件がどの値を見ているかは、シーンとプレハブに author されたデータ側にあり、静的には読めない。`OneConditionCheckType` には `AbnormalCondition`（型とレベルの一致）と `PhysicalCondition`（`PhysicalConditionFlag` の一致）と `HasHaanjaCureableStatus` があり、どれで書かれているかで結論が変わる。
- `BreastSuper` が `PhysicalConditionFlag.Breast` を持ち、治療イベントが `PhysicalCondition` で書かれている場合、**MODの介入なしに既存の治療がそのまま届く**。これが最良の結末であり、最初に確認する。
- 届かない場合の最小の介入は `AbnormalData.m_HaanjaCanCure` を真にすることである（`BreastSuperMakeHaanjaCurable`）。これはゲーム自身の治療イベントに「この状態異常も対象である」と伝えるだけで、治療処理そのものはゲームが行う。セッション限りの変更とし、アンロード時に戻す。
- **MODから搾乳シーンを再生する案は採らない。** `GaTakePlayer.Play` と `DramaManager.PlayDrama` は公開されているが、前者はギャラリー用のシーンと `GaTakePlayer` の実体が読み込まれていることを要求し、フィールド上で満たせない。ギャラリーモードへ入れる案は `GalleryManager.IsActive` が `LabelEvent.DisableWhenGallery` をはじめ広範な挙動を切り替えるため、進行中のランを壊す危険が実利を上回る。後者は台詞だけを再生するもので、映像を伴わない。詳細は DEC-213。

### 5.9 永続化と同期

- 随伴ファイルはスロットキーごとに1つとし、堕落、絶頂回数、書き込み時点のゲームビルド識別子、スキーマ版を保持する。
- スロットキーは `MainSaveData.SelectID` と `LoadedFileName` から構成する。両方を保持し、照合に用いる。
- `OnAfterLoadMainSaveData` で随伴ファイルを読み、堕落と絶頂回数を復元する。対応するファイルがない場合は初期値（堕落 `0`、絶頂回数 `0`）とする。
- `OnAfterSaveMainSaveData` で随伴ファイルを原子的に書く。部分書き込みを残さない。
- スキーマ版が非対応の随伴ファイルは読まず、初期値で開始し、既存ファイルを上書きしない。
- ゲームビルド識別子が異なる随伴ファイルは、値を読んだうえで不一致を記録する。値の破棄は行わない。
- 随伴ファイルの読み書きに失敗しても、ゲームと本MODの他の機構は継続する。

### 5.10 巻き戻し

- プラグインの `Unload`、シーン遷移、例外による中断のいずれでも、5.1の無効化のために変更したゲーム側の状態（`HP.DontSub` など）を元へ戻す。被弾の解決が例外で中断した場合も戻す。
- 巻き戻すべき状態を跨いで保持しない。5.1の抑止は被弾の解決の間に限るため、通常はフレームを越えて残らない。
- 解除に失敗した介入は、対象と理由を記録し、当該機構を無効化する。
- 全機構を無効化した設定で起動した場合、Harmonyパッチを適用せず、随伴ファイルも書かない。

### 5.11 分類カタログの編集画面

拘束中の敵が性的攻撃を行うかどうかは、画面に映っているものを見て下す判断である。その判断ができる唯一の場所はその敵の前であり、セッションの合間に記憶を頼りにテキストを編集する形では正しく下せない。したがってMODはゲーム内に編集画面を持つ。

- `F10` で開閉する。ゲームプレイ中、拘束中、タイトル画面のいずれでも開ける。
- 一覧はゲームが定義する `GalleryEnemyID` と `EnemyID` の全件（`None` を除く。それぞれ108件）を対象とし、これに拘束によって発見した `obj:` 形式の識別子を加える。**拘束された経験のある敵を先頭**に、その中は識別子順に並べる。
- 各行は敵識別子を表示する。表示名が既知であれば併記する。未知の行は識別子のみとする。表示名は並び順に影響しない。
- 上下キーとホイールで移動し、`Space`・左右キー・クリックで `Auto` → `Sexual` → `NonSexual` → `Auto` と巡回する。
- `Tab` は「拘束された経験のある敵のみ」と「全件」を切り替える。
- `Enter` で保存して閉じる。`Escape` は開いた時点の内容へ戻して閉じる。
- 現在プレイヤーを拘束している敵を画面上部に表示し、開いた時点でその行を選択する。
- 描画は本MODのオーバーレイと同じ即時モードGUIで行い、ゲームのUI階層へオブジェクトを追加しない。`Time.timeScale` を変更せず、ゲームを停止させない。

編集画面はゲームの入力を奪わない。IMGUIのイベント消費はIMGUIの内部にとどまり、ゲームは独自に入力を読むため、画面を開いている間のクリックやキー入力はゲーム側にも届く。したがって拘束中に開く場合は、キーボード操作のみで完結できる経路（上下キーと `Space`）を用意する。

### 6.1 性的とみなす状態異常の既定集合

`AbnormalType` の列挙子名からの推論であり、ゲーム側にこの分類は存在しない。設定で変更できる。

`Lustfull`、`Lustfull_Forever`、`LustMarkCurse`、`Defilement`、`Semen`、`Semen_mucus`、`Pregnant`、`Pregnant_Demi`、`Breast`、`BreastSuper`、`Milk`、`WetNurse`、`MindControl`、`MindIntegration`、`Infertility`、`InfertilityBlessing`

SPEC002 の快楽系集合とは目的が異なるため一致させない。SPEC002 は「抵抗の意思が損なわれる状態」を、本仕様は「性的な行為を受けたことを示す状態」を指す。`Defilement` は SPEC002 では意図的に除外されるが、本仕様では性的攻撃の指標として含める。

### 6.2 敵別分類カタログ

敵ごとの宣言は `BepInEx/config/community.sinisistar2.pleasure/enemy-attacks.json` に持つ。`ConfigEntry` のカンマ区切り文字列ではなくファイルとする理由は3つある。対象が200件を超えて1行に収まらないこと、判断が敵ごとに独立していて差分として読めるべきこと、そしてゲーム内の編集画面が書き戻す先を必要とすることである。

```json
{
  "schemaVersion": 1,
  "note": "...",
  "enemies": [
    { "id": "GaID_PictureFrameBig", "kind": "Sexual", "seen": true, "displayName": "大きな額縁", "note": "..." },
    { "id": "EnmID_MeatWorm1", "kind": "Sexual", "seen": true, "displayName": "大口のワーム" },
    { "id": "GaID_MeatWormVore", "kind": "Auto", "seen": false }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `id` | 敵識別子（5.3.1）。`GalleryEnemyID` の列挙子名、`EnemyID` の列挙子名、または `obj:` を接頭辞とする正規化済みオブジェクト名のいずれか。`None` は現れない。 |
| `kind` | `Auto`・`Sexual`・`NonSexual`。認識できない語は `Auto` として扱う。 |
| `seen` | この敵に拘束された経験があるか。編集画面の並び順にのみ使う。判別には影響しない。 |
| `displayName` | ゲーム内表記名。任意フィールドであり、拘束時に取得できたときにだけ現れる。判別には影響しない。 |
| `note` | 由来の記録。MODは読み書きするだけで解釈しない。 |

- 起動時にファイルが無ければ、`SexualEnemyIds` / `NonSexualEnemyIds` を種として作成する。既存の設定が更新で失われないようにするためである。
- 起動時に、ゲームが定義する `GalleryEnemyID` と `EnemyID` の列挙子（`None` を除く）のうちファイルに無いものを `Auto` として追加する。遭遇前の敵を分類できるようにするためである。`obj:` 形式の行は列挙できないため、拘束によって発見したときにのみ追加する。
- 読み込み時、`id` が `None` の行は破棄する。5.3.1により `None` は敵識別子ではなく、この行は判別に用いられない。その行の `kind` が `Auto` 以外であった場合は、宣言を引き継げなかった事実を1回記録する。
- `schemaVersion` は `1` のまま据え置く（DEC-263）。追加は `id` の名前空間の拡大と任意フィールド1つだけであり、旧版のMODが読んでも既存の `GaID_` 行の意味は変わらない。
- 書き込みは原子的に行う。読めないファイルと非対応スキーマ版のファイルは読まず、上書きもしない。破損したファイルは退避して新規から開始する。随伴ファイル（5.9）と同じ規律とする。
- 書き込みの契機は、初回の拘束、表示名が変化した拘束、編集画面の保存、プラグインの終了の4つとする。被弾ごとに書かない。

## 7. 他MODとの互換性

### 7.1 破ってはならない前提

| 対象 | 制約 | 理由 |
|---|---|---|
| `GameAssembly.dll`、`global-metadata.dat` | 改変しない | SPEC001がSHA-256を照合し、不一致ならデバイス出力を無効化する |
| `Time.timeScale` | 変更しない | SPEC001がポーズ検出に使用する |
| `Animator` の状態、再生クリップ、`GalleryEnemyID`、take名 | 変更しない | SPEC001がトリガー同定に使用する |
| `Lelia.IsHold`、`Bind.BinderEnemy` | 意味を変えない | SPEC001が `hold` トリガー判定に使用する |
| `AbnormalList.Has` | 偽の状態異常を報告させない | SPEC001がfiller選択に使用する。5.8の `BreastSuper` は実体のある付与であり、これに反しない |
| `GachaGachaSystem.CurrentValue`、`GachaGachaParameter` | 触れない | SPEC002の無力化窓が管理する |
| `PlayerStatusManager.MoveSlowRateMsv` | 触れない | SPEC002の復帰遅延窓が寄与を登録する |
| `PlayerStatusManager.IsHardMode`、`s_GameDifficultyForCheck` | 触れない | SPEC002が管理する |
| ゲームのセーブデータ、`SaveFlagAndVariable` | 書き込まない | 2.2、DEC-206 |

### 7.2 許容される観測可能な差分

- **`hold` トリガーの継続時間の延長** — 拘束中にHPで決着しなくなるため、SPEC001の `hold` トリガーが有効な時間が延びる。トリガーの同一性は変わらない。
- **`BreastSuper` の新規出現** — 5.8により通常プレイで発生し得るようになる。SPEC001はこれを状態異常として観測し、`mappings.json` に該当ルールがなければ既定fillerを選ぶ。必要なら利用者がルールを追加する。
- **`game-over` トリガーの契機の変化** — 性的な拘束によるゲームオーバーは、HPが尽きた時点ではなく絶頂限界に達した瞬間に起きる。5.5はHPを `0` にすることで発火するためHP0を経由し、SPEC001の `game-over` トリガーは従来どおり `Lelia.IsHP0` で成立する。トリガーの同一性と発生条件は変わらず、発生の時期だけが動く。
- **拘束中のHPゲージの停止** — 性的な攻撃を受けている間、HPゲージが動かなくなる。SPEC001はHPを読まないため影響しない。非性的な脅威では従来どおり動く。

### 7.3 SPEC002 との相互作用

両MODは拘束中に同時に作用する。設計上の干渉はないが、体感は重なる。

- SPEC002の無力化窓は脱出を難しくし、本MODは拘束の継続時間を延ばす。両方が有効な構成では拘束が大幅に長引く。
- SPEC002の復帰遅延窓は脱出直後の再拘束を招き、本MODでは再拘束が快楽の再上昇を意味する。
- SPEC002が強化した状態異常のスリップダメージは、本MODが介入しない減少である（5.1.3）。両方が有効な構成では、性的な拘束中もスリップダメージだけでHPが尽き得る。これは意図した挙動であり、拘束が安全地帯にならないための経路である。
- 3つのMODは相互に依存せず、ロード順序を仮定しない。いずれか1つだけの構成も正当である。

### 7.4 寄与キーの分離

v1.1 の本MODは `MultiSettingValue` へ寄与しない（FR-277）。将来 `MultiSettingValue` へ寄与する変更を入れる場合は、SPEC002 と同じ値へ登録する可能性に備え、寄与キーをプラグインGUIDで前置する。

`HP.DontSub` はゲームの寄与機構ではなく単一の真偽値であり、他の書き手と競合し得る。本MODはこれを**被弾1件の解決の間だけ**立て、元の値を記録して必ず戻す（5.1.2）。フレームを越えて保持しないため、他のMODやゲーム自身がフレーム境界で読む値には影響しない。

## 10. 非機能要件

### 10.1 性能

- MODの介入はメインスレッド上で完結し、待機によってフレーム処理を停止させない。
- 毎フレームの全 `SiNiObject` 走査を行わない。快楽の評価は被弾時、減衰の評価は拘束外のみとする。
- 随伴ファイルの入出力はセーブ・ロードの契機に限り、毎フレーム行わない。
- 絶頂演出の描画がフレーム処理を遅延させない。

### 10.2 安全性

- ゲームのデータへの書き込みは、状態異常の正規の付与、ゲーム自身が公開するHP操作（`DontSub`、`SubAll`、`SetCurrentValue`、`Recover`）、および読み取りの差し替えに限る。HPの値をMODが計算して書かない。
- HPへの書き込みは、5.1の抑止と5.5の致死化の2つの契機に限る。毎フレームHPへ書き込まない。
- 一時的に変更した状態の復元は例外経路でも実行する。
- `MultiSettingValue.AllClear` を呼ばない。
- ゲームのセーブデータへ書き込まない。

### 10.3 互換性

- 他MODとの共存条件は7章に従う。
- ゲーム更新でパッチ対象が変わった場合、当該機構だけを無効化し、他の機構とゲーム本体を継続させる。
- 随伴ファイルはスキーマ版を持ち、非対応版を読まない。

### 10.4 可観測性

- 起動時に、有効な機構、確定済み調整値、随伴ファイルの位置、適用パッチ数を記録する。
- 快楽・絶頂・堕落の変化は `LogTransitions` が有効なときに記録する。
- 致死化の成立条件を検出したが発火しなかった場合、その理由（`EnableClimaxGameOver` が偽、既に死亡状態、手段の失敗）を記録する。
- 性的被弾のHP減算を初めて抑止したとき、および抑止を行わない構成で起動したときに、その事実を1回記録する。

### 12.1 導入順序

1. `dotnet test` と `dotnet build` を実行し、プラグインDLLを実行位置へ配置する。
2. ゲームを一度起動し、設定ファイルを生成させる。この時点でゲームの挙動は何も変わらない（FR-233、FR-278）。v1.0 から更新する場合、`SuppressHp0WhileBound` は無視され、`SuppressSexualHpDamage` が追記される。
3. 付録Aの実測を行い、調整値、HP減算を止める手段（A-50）、HPを `0` にする手段（A-51）を確定する。
4. 設定ファイルへ確定した値を記入する。`PleasureGainPerHit` を正の値にした時点で性的ダメージ無効化が効き始める。
5. `EnableClimaxGameOver` を有効化し、致死化を確認する。

### 12.2 ロールバック

`BepInEx/plugins/community.sinisistar2.pleasure` を削除する。または `Enabled = false` を設定する。ゲームのセーブデータとアセットへの変更は残らない。随伴ファイルは残るため、再導入すれば続きから再開できる。不要なら `BepInEx/data/community.sinisistar2.pleasure` を削除する。 敵別分類カタログは `BepInEx/config/community.sinisistar2.pleasure` に残る。

## 13. 設計判断

撤回した判断は本文に残さない。[SPEC003-withdrawn.md](SPEC003-withdrawn.md) に非規範の記録として置いてある。この表にあるものはすべて有効な判断である。

| ID | 判断 | 理由 | 採用しなかった案 |

| DEC-256 | 性的被弾については、当該被弾の解決の間だけHPの減算を止める。被弾そのもの、状態異常、演出は通す。 | 性的な行為の帰結を快楽と絶頂回数だけで表すには、HPへの書き込みを0にするしかない。一方で被弾自体を消すことはできない。状態異常の付与、快楽の上昇、母乳ゲージ、堕落のすべてが被弾の解決を入力にしており、無敵化はその入力を断つ。範囲を被弾単位にするのは、5.3が既に被弾ごとに判別しており、同じ敵が混ぜてくる非性的攻撃を無害にしないためである。 | 無敵化（`IsInvincibleMsv` / `DamageInvincibleMsv`）、拘束単位での停止、`ForceRemainHP1`、`RemainHp1Msv` への寄与の継続 |

## 14. 前提、延期事項、残存リスク

### 14.1 明示的な前提

- `DamageManager.OneDamage(DamageStack)` が1件の被弾の解決を包み、その中でHPの減算が行われる。したがってその前後がHP減算を止める縫い目になる（A-50）。
- `BattleMainParameter.DontSub` が真の間、当該パラメータの減算が行われない（A-50）。
- `PlayerStatusManager.HP.SubAll` がHPを `0` にし、ゲーム自身の死亡判定がそれを拾う（A-51）。
- 拘束の成立と終了を `Lelia.IsHold` の遷移で検出できる。
- 拘束中の被弾を、受け側がプレイヤーであるダメージ解決として観測できる。
- `MainSaveData.SelectID` と `LoadedFileName` が、セーブスロットを一意に識別するのに十分である。
- `SaveData` のセーブ・ロードSubjectが、実際のファイル入出力と整合する順序で発火する。
- `AbnormalType.BreastSuper` を通常の付与経路で適用でき、ゲームが破綻しない。
- 性的・非性的の分類は状態異常名からの推論であり、実機のプレイ感で見直す。

### 14.2 延期事項

- 快楽・堕落・絶頂回数のゲーム内表示のデザイン改善。当面は最小限のオーバーレイとする。
- 絶頂演出の音響。
- 敵ごと・攻撃ごとの快楽上昇量の個別調整。当面は一律とする。
- 堕落が快楽以外へ与える影響（移動、抵抗、状態異常の付きやすさ）。
- 絶頂回数に応じた見た目やセリフの変化。
- 随伴ファイルのセーブファイル移動・コピーへの追随。
- `BreastSuper` 以外のイベント限定コンテンツの開放。
- 既存セーブへの堕落の遡及付与。

### 14.3 残存リスク
