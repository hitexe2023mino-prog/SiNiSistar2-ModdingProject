## 1. 概要

### 1.1 背景と問題

SiNiSistar2は、ゲーム内の拘束、ギャラリー、ゲームオーバーなどのアニメーションと外部デバイスを同期する標準インターフェースを提供していない。そのため、ゲーム状態を安全に観測し、対象イベントをEDIのギャラリー再生へ変換するMODが必要である。

EDIはIntiface Centralなどを介してデバイスを制御する独立プロセスである。本MODはデバイスへ直接命令せず、EDIのローカルREST APIへギャラリー名、再生位置、対象チャンネルを送信する。

本作のキャラクター表現は2Dピクセルであり、Humanoidアバターもスケルタルアニメーションも存在しない。演出は部位別スプライトのテクスチャ差し替えと微小なピクセル位置オフセットで構成される。したがってTransformの相対変位から運動を計測してfunscriptを自動生成することはできない。代わりに、MODは演出の段階遷移をトリガーとして検出することに専念し、`.funscript` はユーザーがオーサリングGUIで作成する。根拠は付録Cに記録する。

### 1.2 目的

- 対象アニメーションまたはイベントの開始、段階遷移、終了に合わせてEDIギャラリーを制御する。
- A10ピストンSAとU.F.O TWを、それぞれ対象部位に対応する独立したEDIチャンネルで動作させる。
- イベント再生中でないときは、プレイヤーの状態異常に応じたfillerを再生する。
- EDIの停止、通信失敗、設定不備がゲーム本体の進行やフレーム処理を妨げないようにする。
- 対応対象を推測で再生せず、明示的なマッピングと網羅性レポートによって管理する。
- 敵ごとに段数の異なる演出段階を、ユーザーの識別子入力なしに段階単位で列挙し、`.funscript` を割り当て可能なトリガーカタログとして提示する。
- ユーザーがゲームを起動したまま `.funscript` を作成・試聴・保存できるオーサリングGUIを提供する。

### 1.3 成功条件

1. 対象候補として収集された全トリガーと全状態異常が、マッピングファイル上で `mapped` または理由付き `ignored` に分類されている。
2. `mapped` トリガーでは、指定されたEDIギャラリーが指定チャンネルに送信され、アニメーションの開始位置とループ長に対応する。
3. `膨乳` 中の待機状態では、`breast` チャンネルで専用fillerが選択される。
4. 同一トリガーの重複通知、古い終了通知、通信断が発生しても、新しい再生を誤停止させたりゲームを停止させたりしない。
5. HTTP通信と再試行待機はゲームのメインスレッドをブロックしない。
6. 敵ごとの演出段階が、ユーザーによる識別子入力なしにトリガーカタログへ段階単位で列挙される。
7. ユーザーはオーサリングGUIから、カタログ上の任意の段階に対して `.funscript` を作成、試聴、保存でき、保存後は同じ段階の次回発生からEDIで再生される。

## 2. スコープ

### 2.1 対象

- BepInEx IL2CPPプラグインとしてのゲーム状態フック。
- 拘束、ギャラリー、ゲームオーバー、その他明示的に採用された演出イベントの段階遷移の観測。
- トリガーキーおよび状態異常識別子からEDIギャラリーへの明示的マッピング。
- `main` と `breast` の2つのEDIチャンネル。
- A10ピストンSA用とU.F.O TW左右用の `.funscript` バリアント。
- 待機中の通常fillerと、状態異常に応じたfillerの選択。
- 常時収集によるトリガーカタログの生成と網羅性レポートの生成。
- ゲーム側のデータ構造から静的に列挙できる演出段階の先読み登録。
- ループバック限定のローカルHTTPで配信する `.funscript` オーサリングGUI。
- オーサリングGUIからの実機試聴、保存、EDI登録、マッピング更新。
- EDI未起動、タイムアウト、無効な設定、欠落アセットからの安全な復旧。

### 2.2 非対象

- MODからIntiface Centralまたはデバイスへ直接送る低レベル命令。
- `.csv` をMODの入力制御ファイルとして再生する機能。
- ゲーム内アニメーションの運動を計測しての `.funscript` 自動生成。1.1および付録Cの理由により本作では成立しない。
- EDIが事前記録コンテンツしか再生できない制約を越えた、未登録トリガーの初回発生時の再生。`.funscript` が保存され登録されるまで、その段階は再生しない。
- EDIを別端末から利用するリモート接続。
- CelSector用MODとのバイナリ互換性。
- ゲーム内の設定画面、手動再生画面、ホットキー。オーサリングGUIはゲーム外のブラウザで動作する。
- A10ピストンSAとU.F.O TW以外のデバイス固有保証。EDI側で同じギャラリーとチャンネルを利用できるデバイスは動作し得るが、本仕様の受け入れ対象ではない。

### 2.3 前提と制約

- EDIはゲームと同じWindows端末上で起動し、既定では `http://127.0.0.1:5000` を使用する。
- デバイスの検出と物理制御はEDIおよびIntiface Centralの責務である。
- EDIに渡すコンテンツは、リポジトリ同梱またはユーザーがオーサリングGUIで作成してEDIへ登録したギャラリーであり、動的な生デバイス命令は使用しない。
- ゲームアセット内の識別子はビルド更新で変わり得る。対応ゲームビルドごとに診断収集と網羅性確認を行う。
- 対象ビルドのキャラクターAnimatorはHumanoidアバターを持たず、`GetBoneTransform` は全ボーンで `null` を返す。運動信号として利用可能なTransform変位は存在しない。
- 演出段階の識別子はゲームアセットだけから全て静的に確定できない。ギャラリーの段階配列は到達時に列挙し、拘束シーケンスの段階は観測時に追記する。ユーザーによる識別子の手入力を要求してはならない。
- `.funscript` の内容はユーザーがオーサリングGUIで決定する。MODは波形を生成も推測もしない。

## 3. 用語

| 用語 | 定義 |
|---|---|
| EDI | Easy Device Integration。ゲームからREST APIで制御する独立プロセス。 |
| ギャラリー | EDIが名前で再生する事前作成コンテンツ。イベント、reaction、fillerを含む。 |
| バリアント | 同じギャラリー名に対するデバイス別の `.funscript`。EDI側でデバイスへ割り当てる。 |
| チャンネル | EDI内の独立した再生ストリーム。指定しないAPI呼び出しは全チャンネルへ作用するため、本MODは常に明示する。 |
| filler | 対象イベントが再生されていないゲームプレイ中にループ再生する待機ギャラリー。 |
| トリガー | デバイス動作を切り替えるゲーム側の状態遷移。`context`、`actorId`、`animationId`、`phase`、`stageId` の5組で一意になる。本仕様で「イベント」と呼ぶものはトリガーと同義である。 |
| 段階 | 1つの敵または演出が持つ複数の演出フェーズ。ギャラリーではtake配列の要素、拘束シーケンスでは状態機械の状態に対応する。段数は敵により異なる。 |
| `stageId` | 段階を一意に識別する安定文字列。ギャラリーではtake名、取得できない場合はtake配列index。拘束シーケンスでは状態名。単一段階しか持たないトリガーでは `default`。 |
| トリガーカタログ | MODが観測または静的列挙したトリガーを段階単位で蓄積した機械可読ファイル。マッピングの入力であり、マッピングそのものではない。 |
| オーサリングGUI | MODがループバック限定のローカルHTTPで配信し、ユーザーがブラウザで操作する `.funscript` 作成画面。 |
| 試聴 | オーサリングGUIから編集中の `.funscript` をEDIへ送り、実機で確認する操作。 |
| desired state | 各チャンネルで最終的に成立させたい再生状態。通信中の一時状態ではなく、最新のゲーム状態を表す。 |
| 網羅性レポート | トリガーカタログと、マッピング上の `mapped` / `ignored` 判定を突合した成果物。 |
| セッションログ | 1回のゲーム起動で取得した全レコードを時系列順に追記するUTF-8 JSON Linesファイル。トリガー遷移と観測テキストの一次資料である。 |

## 4. 採用設計

### 4.1 全体構成

1. **Game Hook Adapter**
   - BepInEx IL2CPP上でゲームのライフサイクル、ギャラリー、拘束、状態異常を観測する。
   - 段階遷移は、可能な場合ゲーム側の状態通知を購読して取得し、Animatorのフレーム走査に依存しない。
   - Unityオブジェクトへのアクセスはメインスレッド上だけで行い、ワーカーへは不変のスナップショットを渡す。
2. **Mapping Repository**
   - 起動時にマッピングファイルを読み込み、重複、未知チャンネル、必須値欠落を検証する。
   - トリガーキーおよび状態異常識別子をEDIアクションへ変換する。
3. **Playback Coordinator**
   - チャンネルごとのdesired stateと世代番号を保持する。
   - トリガー、filler、停止、ポーズ、試聴の優先順位を解決し、重複命令と古い終了通知を破棄する。
4. **EDI Client**
   - 単一の再利用可能なHTTPクライアントを使い、チャンネルごとに命令順を直列化する。
   - HTTP処理、タイムアウト待機、再接続待機をメインスレッド外で行う。
   - ゲーム由来の再生とオーサリングGUI由来の試聴は、いずれもこのクライアントだけを経由する。
5. **Trigger Catalog Recorder**
   - 常時、トリガー遷移と観測テキストをセッションログへ追記する。
   - 観測または静的列挙した段階をトリガーカタログへ原子的に統合し、網羅性レポートを更新する。
   - 取得できる公開IL2CPP/Unity値の範囲で記録し、取得不能なカテゴリは能力情報と理由を保存する。
6. **Authoring Server**
   - ループバック限定のローカルHTTPでオーサリングGUIとカタログを配信する。
   - GUIが保存した `.funscript` をリポジトリへ原子的に書き込み、EDIへ登録し、マッピングを更新する。
   - GUIからの試聴要求をPlayback Coordinatorへ渡し、試聴終了時にゲーム側desired stateへ復帰させる。

### 4.2 チャンネルとデバイス

| EDIチャンネル | 対象 | EDIバリアント | 動作 |
|---|---|---|---|
| `main` | A10ピストンSA | `a10-main` | 股間向けのピストン制御 |
| `breast` | U.F.O TW 左 | `ufo-left` | 左側用の回転・振動パターン |
| `breast` | U.F.O TW 右 | `ufo-right` | 右側用の回転・振動パターン |

U.F.O TWの左右は同じ `breast` チャンネルで同じギャラリー名を同時に受信する。左右差はEDIで各物理デバイスへ割り当てる `ufo-left` / `ufo-right` バリアントによって表現する。左右を異なる時刻に開始・停止する機能は初版の対象外である。

### 4.3 スレッドモデル

- ゲームフックは、ゲーム状態の読み取り、トリガーキー生成、スナップショットのキュー投入だけを行う。
- Unity APIおよびIL2CPPオブジェクトをバックグラウンドワーカーから参照してはならない。
- EDI ClientはバックグラウンドでHTTP要求を実行する。
- Authoring ServerのHTTP受信とファイル書き込みはバックグラウンドで行う。ゲーム状態の読み取りが必要な応答は、メインスレッドで作成済みのスナップショットから構成する。
- 各チャンネルの命令は送信順を維持する。別チャンネルは互いを待たずに処理できる。
- キューが遅延した場合は中間状態を順番に再生せず、世代番号が最新のdesired stateへ収束させる。ただし、明示的に `reaction` とされた非ループトリガーはマッピングの指示に従う。

## 5. 制御仕様

### 5.1 状態と優先順位

各チャンネルは次の論理状態のいずれかを取る。

| 状態 | 説明 | EDI動作 |
|---|---|---|
| `Inactive` | タイトル、ロード、対象外シーン、終了処理 | `Stop` |
| `Filler` | 操作可能なゲームプレイ中で対象トリガーなし | 選択されたfillerを `Play` |
| `Event` | `mapped` トリガー進行中 | トリガーギャラリーを `Play` |
| `Preview` | オーサリングGUIから試聴中 | 試聴対象ギャラリーを `Play` |
| `Paused` | ゲームが一時停止中 | `Pause` |
| `Unavailable` | EDIへ到達不能 | ゲームは継続し、最新desired stateを保持 |

優先順位は `Inactive`、`Preview`、`Paused`、`Event`、`Filler` の順に評価する。`Unavailable` は通信状態であり、ゲーム側desired stateを上書きしない。

`Preview` は `Inactive` に次ぐ優先度とする。ユーザーが明示的に開始した確認操作であり、ゲーム側の自動再生に中断されてはならないためである。`Preview` 終了時は、その時点のゲーム状態から `Event`、`Filler`、`Paused`、`Inactive` を再評価する。

### 5.2 トリガー開始・更新・終了

1. `mapped` トリガー開始時、Coordinatorはマッピングに指定されたチャンネルを `Event` にする。
2. `seek` は、観測時点のアニメーション再生位置とクリップ長からミリ秒で算出する。開始位置を取得できないマッピングは `seek = 0` を明示する。
3. ループトリガーでは、対応するfunscriptのループ長をゲームのアニメーションループ長と一致させる。通常のループ折り返しだけを理由に `Play` を再送しない。
4. 同じトリガーキーと再生位置に対する重複通知は送信しない。
5. トリガー遷移時は新しいトリガーへ世代番号を進める。以前の世代の終了通知は新しい再生を停止してはならない。
6. トリガー終了時、まだ同じ世代が有効なら状態異常を再評価し、`Filler` または `Inactive` へ遷移する。
7. 段階が切り替わった場合は、`stageId` が異なる新しいトリガーとして扱い、世代番号を進めて対応するマッピングを再解決する。同じ `stageId` が継続する間は `Play` を再送しない。
8. マッピング未登録トリガーではEDIを開始せず、トリガーカタログへ追記して診断可能な警告を残す。ユーザーがオーサリングGUIで `.funscript` を保存し登録が完了した後、その段階の次回発生から再生する。

### 5.3 ポーズ、ロード、終了

- ゲームのポーズ開始時は対象チャンネルへ `Pause?untilResume=true` を送る。
- ポーズ解除時は単純な `Resume` に依存せず、現在のゲーム状態からギャラリーと `seek` を再計算して `Play` する。これによりEDI側の時計との差を持ち越さない。
- タイトル画面、ロード中、対象外シーンでは `Stop` を送る。
- MOD無効化、プラグイン破棄、ゲーム終了では、既知の全チャンネルに対してbest effortで `Stop` を送ってからワーカーを終了する。Authoring Serverも同時に停止する。
- `mapped` のゲームオーバー演出中は `Event` を維持し、演出終了後に `Inactive` へ遷移する。

### 5.4 filler選択

1. fillerは `Event`、`Preview`、`Paused`、`Inactive` のいずれでもない場合だけ再生する。
2. 状態異常ルールはマッピングファイルの記載順に評価し、最初に一致したルールをそのチャンネルへ適用する。
3. `膨乳` が有効な場合、`breast` は `filler-breast-swollen` を使用する。このギャラリーは通常の `breast` fillerより強い刺激となるようfunscript側で作成する。
4. 一致する状態異常ルールがない場合、`main` は `filler-main`、`breast` は `filler-breast` を使用する。
5. トリガー進行中に状態異常が変化しても再生中トリガーを中断しない。トリガー終了時に最新状態を評価する。
6. 同じfillerが継続する場合は `Play` を再送しない。

## 6. マッピングとアセット契約

### 6.1 正本

| ファイル | 書き手 | 役割 |
|---|---|---|
| `BepInEx/config/community.sinisistar2.edi/mappings.json` | オーサリングGUI（および同梱初期値） | 対応トリガーと状態異常の正本 |
| `BepInEx/diagnostics/community.sinisistar2.edi/catalog/{gameBuildId}/trigger-catalog.json` | MOD | 観測または列挙した全トリガーの派生カタログ |

マッピングの正本は `mappings.json` だけとする。トリガーカタログはマッピングの入力であり、それ自体が再生を許可することはない。MODはカタログを追記・更新するが `mappings.json` の判定内容を自動で書き換えてはならない。オーサリングGUIによる保存だけが `mappings.json` を更新でき、更新は原子的に行う。

MODの起動ログには両ファイルの解決後絶対パスを表示する。マッピングに存在しない暗黙の再生、名前だけによる再生フォールバックは禁止する。

マッピングファイルは次のトップレベル値を持つ。

| フィールド | 内容 |
|---|---|
| `schemaVersion` | ファイル構造の互換性を判定する版 |
| `mappingVersion` | 内容更新を追跡する版 |
| `targetGameBuild` | `GameAssembly.dll` と `global-metadata.dat` のSHA-256 |
| `events` | 6.2のトリガーエントリ配列 |
| `statusRules` | 6.3の状態異常エントリ配列。配列順が優先順位 |
| `defaultFillers` | `main` を `filler-main`、`breast` を `filler-breast` へ対応付ける値 |

### 6.2 トリガーエントリ

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | Yes | マッピング内で一意な安定ID |
| `context` | Yes | `hold`、`gallery`、`game-over`、`scripted-event` のいずれか |
| `actorId` | Yes | 敵、イベント、ギャラリーなどのゲーム内識別子 |
| `animationId` | Yes | クリップ名、Animatorハッシュの元名、または観測可能な安定識別子 |
| `phase` | Yes | `start`、`loop`、`reaction`、`end` のいずれか |
| `stageId` | Yes | 段階の安定識別子。単一段階のトリガーでは `default` |
| `disposition` | Yes | `mapped` または `ignored` |
| `gallery` | mapped時 | EDIへ渡すギャラリー名 |
| `channels` | mapped時 | `main`、`breast`、または両方。空配列は禁止 |
| `seekMode` | mapped時 | `animation-time` または `zero` |
| `ignoreReason` | ignored時 | 対象外とする観察可能な理由 |

`context + actorId + animationId + phase + stageId` は一意でなければならない。重複がある場合、MODはデバイス出力を開始せず設定エラーとして扱う。

`phase` は演出の役割、`stageId` は同一演出内の段階を表し、両者を混同してはならない。段数が敵により異なるため、`stageId` の値域を仕様で固定しない。

### 6.3 状態異常エントリ

| フィールド | 必須 | 内容 |
|---|---|---|
| `statusId` | Yes | 常時収集で取得したゲーム内識別子 |
| `displayName` | Yes | 人間向け名称。初版では少なくとも `膨乳` を含む |
| `disposition` | Yes | `mapped` または `ignored` |
| `channel` | mapped時 | 適用対象チャンネル |
| `fillerGallery` | mapped時 | 選択するfillerギャラリー名 |
| `ignoreReason` | ignored時 | デバイス制御へ影響させない理由 |

状態異常エントリの配列順を優先順位とする。全ての既知状態異常は `mapped` または理由付き `ignored` に分類する。

### 6.4 常時収集とセッションログ

1. 収集はユーザー設定を必要とせず常時有効とする。一次資料は `BepInEx/diagnostics/community.sinisistar2.edi/sessions/{gameBuildId}/{sessionId}.animation.jsonl` へ保存する。既存セッションを上書きまたは自動削除してはならない。
2. JSONLの各行は `schemaVersion`、`recordType`、`sessionId`、単調増加する `sequence`、`utc`、`realtimeMs`、`frameCount` を持つ。`recordType` は `session-start`、`event-transition`、`catalog-update`、`text-change`、`capture-warning`、`session-end` のいずれかとする。
3. `event-transition` はトリガーの開始、段階切替、終了ごとに1回記録し、遷移前後のトリガーキー、Scene、クリップ長、ループ可否、観測時のnormalizedTime、現在の状態異常、Unity時刻、timeScaleを含む。
4. `catalog-update` は、静的列挙または観測によってカタログへ新しい段階が追加されたときに記録し、追加された段階と列挙元を含む。
5. フレーム単位のTransform、Animatorレイヤー、ボーン姿勢は収集しない。本作にはボーンが存在せず、これらは運動信号として利用できないためである。取得を必要とする将来要件が生じた場合は、本節を改訂したうえで対象を限定して再導入する。
6. 画面テキストは取得可能なUI実装ごとに列挙し、階層パス、テキスト、active状態が変化した時に `text-change` として記録する。ゲームから直接得られるScene名、take名、actor名、clip名、layer名もテキストデータとして保持する。テキストは段階の人間向け表示名候補として利用する。
7. 対象ゲームビルドのinteropに公開getterがない、getterが例外を送出する、コンポーネントが存在しない等の理由で取得不能なカテゴリは、省略せず `available=false` と機械可読な `unavailableReason` を `session-start` または `capture-warning` に記録する。「全て取得」とは、このビルドで安全に呼べる生成済みUnity/IL2CPP公開getterの範囲を指し、未検証のネイティブメモリ走査は含まない。
8. Unityオブジェクトはメインスレッドだけで読み取り、不変DTOを追記ワーカーへ渡す。キュー詰まりやI/O失敗でレコードを黙って破棄してはならず、欠番、失敗範囲、未書込件数を `capture-warning` と通常ログに残す。
9. `coverage.json` とトリガーカタログはセッションログから得た派生成果物であり、遷移時系列の代用にしてはならない。
10. ゲーム更新後はビルド別ディレクトリへ分離して収集し、新規、消失、識別子変更を差分として確認する。

### 6.5 トリガーカタログ

1. カタログは段階単位のエントリ配列とし、各エントリは6.2のキー5要素、クリップ長、ループ可否、列挙元（`static-enumeration` または `observed`）、初回観測時刻、表示名候補、現在のマッピング判定を持つ。
2. ギャラリーの段階配列のように、到達時点でゲーム側から全段階を列挙できる場合は、未到達の段階も含めてカタログへ登録する。列挙元を `static-enumeration` とし、クリップ長が未取得の項目は欠落を明示する。
3. 拘束シーケンスのように状態機械として進行する段階は、遷移を観測した時点で追記する。列挙元を `observed` とする。
4. カタログの更新は原子的に行い、既存エントリを失ってはならない。同一キーの再観測では、欠落していた値の補完だけを行う。
5. 網羅性レポートは、カタログと `mappings.json` を突合して `mapped`、`ignored`、`unclassified` を機械判定できる形式で出力する。
6. カタログは再生可否を決定しない。`mappings.json` に `mapped` として存在しない段階は再生してはならない。

### 6.6 funscriptとバリアント

- MODが要求する入力アセット形式は `.funscript` とする。
- `.csv` はEDIが特定デバイス向けバンドルとして内部生成する場合があるが、本MODの入力契約ではない。
- 同じトリガーを複数デバイスで再生する場合、全バリアントで同じギャラリー名を使用する。
- `main` を対象とする各ギャラリーには `a10-main` バリアントを用意する。
- `breast` を対象とする各ギャラリーには `ufo-left` と `ufo-right` の両バリアントを用意する。
- fillerはEDI上でfiller種別かつループとして定義する。
- `.funscript` の波形はユーザーがオーサリングGUIで作成する。MODは波形を生成、補間、推測、複製してはならない。`ufo-left` と `ufo-right` を片側の自動反転で埋めることも禁止する。
- ギャラリー名はトリガーキーのSHA-256短縮値を含む安定名とし、ファイル名に未検証のゲーム文字列を直接使用しない。表示名はカタログの表示名候補を用い、ファイル名には使用しない。
- 保存先は `Edi/Gallery/a10-main`、`Edi/Gallery/ufo-left`、`Edi/Gallery/ufo-right` の対応ファイルとし、原子的に書き込む。
- ループ対象トリガーでは、`.funscript` の終端時刻とカタログ上のクリップ長の差が1フレーム相当を超える場合、保存時に検証エラーとして提示する。ユーザーが差異を承認した場合は、承認をマニフェストへ記録して保存を許可する。
- 必須バリアントまたはEDI定義が欠落するマッピングは起動前検証または診断でエラーにする。

### 6.7 オーサリングGUI

1. MODはループバックアドレス限定のローカルHTTPサーバでオーサリングGUIを配信する。待ち受けアドレスとポートは設定可能とし、非ループバックアドレスへの待ち受けは設定エラーとする。
2. GUIはトリガーカタログを段階単位で提示し、`actorId`、表示名候補、`stageId`、クリップ長、ループ可否、現在のマッピング判定、バリアントの有無を一覧できる。
3. GUIは選択した段階に対して、チャンネルとバリアントごとの `.funscript` を作成、編集、複製、保存できる。既存の段階から波形を複製して編集を開始する操作を提供する。
4. GUIは編集中の `.funscript` を試聴できる。試聴要求はMODのEDI Clientを経由し、対象チャンネルを明示する。試聴中は5.1の `Preview` 状態とし、終了時にゲーム側desired stateを再評価して復帰する。
5. 保存操作は、`.funscript` のリポジトリへの原子的書き込み、EDIのAssets APIによる再読込、`mappings.json` の原子的更新を一連の処理として行う。いずれかが失敗した場合は `mappings.json` を `mapped` へ更新せず、失敗理由をGUIとログへ提示する。
6. 各保存済みギャラリーに `BepInEx/diagnostics/community.sinisistar2.edi/generated/{gameBuildId}/{gallery}.manifest.json` を作成する。マニフェストはトリガーキー、カタログ上のクリップ長、ループ可否、作成日時、GUI版、ループ長差異の承認有無、各出力ファイルのSHA-256を持つ。
7. GUIはゲームプロセスの生存に依存する。ゲーム終了時にサーバを停止し、未保存の編集内容が失われることをGUI上で明示する。
8. GUIは秘密情報を扱わず、認証を持たない。ループバック限定であることを唯一の到達制御とし、この前提を10.2に記録する。

## 7. EDI RESTインターフェース

### 7.1 接続

- 既定のBase URLは `http://127.0.0.1:5000` とする。
- 初版はループバックアドレスのみ許可する。リモートURLは設定エラーとする。
- EDIの可用性およびチャンネル構成は `GET /Edi/Channels` で確認する。
- `main` と `breast` の両方が存在しない場合、デバイス出力を開始しない。

### 7.2 使用するAPI

| 操作 | HTTP要求 | 備考 |
|---|---|---|
| 再生 | `POST /Edi/Play/{name}?seek={milliseconds}&channels={channel}` | `{name}` とquery値をURLエンコードする |
| 停止 | `POST /Edi/Stop?channels={channel}` | 常にチャンネルを明示する |
| 一時停止 | `POST /Edi/Pause?untilResume=true&channels={channel}` | ゲームポーズ用 |
| 再開 | 現在状態から `Play` を再送 | 現在の `seek` を再計算する |
| 強度変更 | `POST /Edi/Intensity/{max}?channels={channel}` | 初版の自動制御では使用しない |

MODはチャンネル指定を省略してはならない。省略するとEDI上の全チャンネルに作用するためである。

オーサリングGUIからの試聴も同じAPIとチャンネル明示規約に従う。GUIがEDIへ直接要求を送ってはならない。

### 7.3 通信失敗

- HTTPタイムアウト、接続拒否、非成功ステータス、応答解析失敗を通信失敗として扱う。
- 通信失敗をUnity側へ例外として伝播させない。
- 同じdesired stateに対する無制限の即時再試行は禁止する。再接続確認はバックオフし、ログは障害状態の遷移時にまとめる。
- 再接続後は失敗中の全命令を再生せず、各チャンネルの最新desired stateだけを送信する。
- `Play` の結果が不明な場合、同じ要求を直ちに重複送信しない。

## 9. エラーと復旧

| 条件 | 動作 | 復旧 |
|---|---|---|
| EDI未起動・通信断 | `Unavailable` としてゲームを継続し、ログを集約 | EDI復帰後に最新desired stateへ同期 |
| 必須チャンネルなし | 出力を無効化し、不足チャンネルを表示 | EDI設定修正後に再起動または明示的再読込 |
| マッピング構文不正 | 出力を無効化し、ファイルと検証箇所を表示 | 設定修正後に再読込 |
| 重複トリガーキー | 出力を無効化する | 重複を解消して再読込 |
| 未登録トリガー | カタログへ追記し、再生しない | オーサリングGUIで作成・保存後、次回発生から再生 |
| 段階配列を列挙できない | 観測できた段階だけをカタログへ追記し、列挙不能の理由を記録 | 該当演出へ到達して観測を追加 |
| 段階の状態通知を購読できない | 理由を記録してAnimator観測へ縮退し、`stageId` を `default` としない | 購読可能なゲームビルドで再収集 |
| セッション書込失敗 | ゲームと既存再生は継続し、通常ログと可能ならJSONLへ欠番・未書込数を記録 | 書込可能になった新セッションで収集再開 |
| カタログ書込失敗 | 直前のカタログを保持し、失敗を記録。部分書き込みを残さない | 書込可能になった時点で再統合 |
| オーサリングGUIのポート使用中 | GUIを無効化し、ゲームとデバイス制御は継続。使用中ポートを表示 | ポート設定変更後に再起動 |
| `.funscript` 保存失敗またはEDI登録失敗 | `mappings.json` を更新せず、GUIとログへ理由を提示。未登録のまま再生しない | 原因解消後にGUIから再保存 |
| ループ長不一致 | 保存時に検証エラーを提示し、承認なしには保存しない | 波形を修正、または差異を承認して記録 |
| ギャラリー・バリアント欠落 | 対象アクションを再生せずエラー | EDIアセット追加後に定義を再検証 |
| ゲームフック失敗 | 該当フックを無効化し、ゲームを継続 | 対応ゲームビルド用フックへ更新 |
| 古い非同期応答 | 世代番号が一致しなければ破棄 | 最新desired stateを維持 |

## 10. 非機能要件

### 10.1 性能

- ゲームフックからHTTP完了を待ってはならない。
- 同じ状態のポーリングごとにHTTP要求または同内容ログを生成してはならない。
- セッションログはトリガー遷移と変化したテキストだけを記録し、フレーム単位のレコードを出力してはならない。1回のゲームセッションのログ量が、演出の発生回数ではなくプレイ時間に比例して増大してはならない。
- 段階遷移の検出は、可能な場合ゲーム側の状態通知の購読で行い、毎フレームのAnimatorおよびTransform走査を行わない。
- 収集ワーカーには設定可能な上限を設ける。上限到達時はゲームをブロックせず収集を停止し、破棄範囲と件数を明示する。
- オーサリングGUIの要求処理がゲームのフレーム処理を遅延させてはならない。
- 性能試験では、EDIの応答遅延中およびGUI操作中もゲームの更新が停止しないことを確認する。

### 10.2 安全性とセキュリティ

- EDI接続はループバックに限定する。
- オーサリングGUIの待ち受けもループバックに限定する。GUIは認証を持たないため、ループバック限定が唯一の到達制御である。
- MODは秘密情報、個人情報、ゲーム外の入力内容を送信しない。
- ログはテレメトリとして外部送信せず、ローカルに保存する。
- 無効な設定や未登録トリガーではfail closedとし、デバイスを推測動作させない。
- MODは波形を推測生成しない。再生されるのはユーザーが作成し保存した `.funscript` だけである。
- ゲーム終了時のStopはbest effortであり、最終的な物理停止機能はEDIおよびデバイス側にも必要である。

### 10.3 互換性と保守性

- 対応ゲームビルドをマッピングファイルまたは同梱メタデータに記録する。
- 異なるゲームビルドを検出した場合は警告し、網羅性確認なしに「対応済み」と表示してはならない。
- トリガーカタログはビルド別に分離し、ビルド間で自動的に流用しない。
- EDI API呼び出し、ゲームフック、マッピング解決、状態調停、オーサリングサーバを別コンポーネントとしてテスト可能にする。
- ファイル形式には `schemaVersion` を持たせ、未知のメジャー版は読み込まない。

### 10.4 可観測性

- ログレベルごとに、起動情報、マッピング検証、状態遷移、通信障害、未知識別子、GUI操作を区別する。
- 通常ログは状態変化だけを記録し、毎フレーム出力しない。
- セッション収集は常時有効とする。フレーム単位のデータは収集しない。
- 各セッションの遷移件数、カタログ追加件数、欠番、書込高水位、GUIからの保存成否と出力パスを終了時に要約する。

## 12. リポジトリ成果物と運用

### 12.1 リポジトリ常備成果物

- BepInEx IL2CPPプラグイン。
- オーサリングGUIの静的アセット。
- 対応ゲームビルドを明記したマッピングファイル。
- ビルド・セッション別の追記専用JSONL、ビルド別トリガーカタログ、派生網羅性レポート、保存マニフェスト。
- EDI用ギャラリー定義、同梱 `.funscript`、オーサリングGUIで作成した `.funscript` 一式。
- `a10-main`、`ufo-left`、`ufo-right` のEDI設定例。
- EDI起動順、Intiface Central接続、GUI利用手順、ログ採取、無効化手順。
- ハードウェアあり・なし両方の受け入れ試験記録。

### 12.2 導入順序

1. 対応するBepInEx IL2CPPをゲームへ導入する。
2. MODプラグインとマッピングファイルを所定位置へ配置する。
3. EDIへギャラリーとバリアントを配置する。
4. EDIで `main` と `breast` を作成し、各デバイスへチャンネルとバリアントを割り当てる。
5. Intiface Central、EDI、ゲームの順に起動する。
6. ギャラリーと通常プレイを一巡してトリガーカタログを蓄積する。
7. オーサリングGUIをブラウザで開き、段階ごとに `.funscript` を作成・試聴・保存する。
8. 診断ログとEDI定義検証を確認してからデバイスあり試験を行う。

### 12.3 ロールバック

MODプラグインと同梱設定を無効化または除去すれば、ゲーム本体はEDI連動なしで起動できなければならない。セーブデータおよびゲームアセットを変更する方式は禁止する。

## 14. 前提、延期事項、残存リスク

### 14.1 明示的な前提

- A10ピストンSAはEDI上でピストン対応デバイスとして認識される。
- U.F.O TWの左右要素はEDI上で別デバイスまたは別アクチュエータとして、異なるバリアントを割り当てられる。
- 対象トリガーのアニメーション識別子、再生位置、クリップ長、ループ可否をBepInEx IL2CPPから安定して観測できる。
- ギャラリーの段階配列をゲーム側から列挙できる。実機で未確認であり、列挙できない場合は観測による追記へ縮退する。
- 拘束シーケンスの段階遷移をゲーム側の状態通知として購読できる。実機で未確認であり、購読できない場合はAnimator観測へ縮退する。
- `膨乳` のゲーム内識別子は常時収集で一意に取得できる。
- ユーザーは対象段階に対して `.funscript` を作成する意思と時間を持つ。

### 14.2 延期事項

- 左右U.F.O TWの独立した開始・停止。
- 波形の自動生成および自動補完。
- ゲーム内UIおよびホットキー。
- 他デバイスの正式サポート。
- リモートEDI接続。
- 複数ユーザー間での `.funscript` 共有配布フロー。

### 14.3 残存リスク

| リスク | 影響 | 軽減策 |
|---|---|---|
| ゲーム更新でIL2CPPフックまたは識別子が変わる | トリガー欠落、誤分類 | ビルド判定、ビルド別カタログ、網羅性差分を互換性ゲートにする |
| 段階配列を列挙できず観測に頼る | 未到達段階がカタログに現れず、事前オーサリングできない | 列挙不能を明示的に記録し、ギャラリー一巡を収集手順に含める |
| 段階の状態通知を購読できない | 段階境界の検出が遅れる、または段階を判別できない | 縮退動作を定義し、縮退時は理由をカタログとログへ記録する |
| 段階数が多く手動オーサリングの工数が大きい | 対応範囲が広がらない | 既存段階からの複製編集を提供し、優先度の高い段階から着手できる一覧を出す |
| アニメーションとfunscriptの長さが一致しない | ループごとに同期がずれる | 保存時にクリップ長と比較して検証エラーを提示し、承認を記録する |
| EDI APIの互換性変更 | 制御不能 | 使用APIを限定し、EDI互換版をリポジトリ文書に記録する |
| 物理デバイスがStopを受信できない | 動作継続 | best effort Stopに加え、EDI・デバイス側の緊急停止手順を文書化する |
| オーサリングGUIが認証を持たない | 同一端末の他プロセスから操作され得る | ループバック限定を強制し、非ループバック設定を起動エラーにする |
| 診断プレイで到達しなかったトリガー | 網羅性レポートから漏れる | ゲーム内ギャラリー、通常プレイ、ゲームオーバー経路を含む収集手順とレビューを用意する |

## 付録C: 自動生成を撤回した根拠

対象ビルドで取得したセッションログ `20260805T000131663Z-3e3f8ba892314db6b6f060f7348e9bed.animation.jsonl` の実測結果を、CHG-014の根拠として記録する。

| 観測 | 値 | 含意 |
|---|---|---|
| `animator.isHuman` | `false` | Humanoidアバターが存在しない |
| `humanoidBone` | 対象Animator配下111 Transform全てで `null` | `GetBoneTransform` が全ボーンで解決しない。旧FR-023の取得対象が存在しない |
| `hasMotionCurves` / `hasRootMotion` / `applyRootMotion` | 全て `false` | モーションカーブおよびルートモーションによる変位がない |
| `localRotation` | 全Transform、全フレームで不変 | 回転を運動信号にできない |
| 変化するTransformチャンネル | 1110中29。振幅0.01〜0.03、値は0.01刻みの階段状 | 旧FR-025の射影対象として有意な変位がない |
| `lossyScale.x` | −1 が75件 | スプライトの左右反転による2D表現 |
| `localPosition.z` | 37種の細かい値 | 2Dの重ね順による層構成 |
| ギャラリー再生中の部位別テクスチャ名変化 | 122秒間で949件、16部位 | 演出の主体はテクスチャ差し替えであり、Transform変位ではない |
| `animation-sample` 1件のサイズ | 約323KB | 旧6.4の収集範囲では実用的なログ量に収まらない |

加えて、旧6.5が要求する解剖学的名称による候補選択は、本作のTransform名（`Root`、`Head`、`Chest`、`Body`、`Skirt1`、`RightArm`、`LeftLeg` ほか）に対して該当が0件であり、名称語彙を作り替えても射影対象そのものが存在しない。
