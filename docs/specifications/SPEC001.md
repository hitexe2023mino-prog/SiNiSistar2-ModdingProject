## 1. 概要

### 1.1 背景と問題

SiNiSistar2は、ゲーム内の拘束、ギャラリー、ゲームオーバーなどのアニメーションと外部デバイスを同期する標準インターフェースを提供していない。そのため、ゲーム状態を安全に観測し、対象イベントをEDIのギャラリー再生へ変換するMODが必要である。

EDIはIntiface Centralなどを介してデバイスを制御する独立プロセスである。本MODはデバイスへ直接命令せず、EDIのローカルREST APIへギャラリー名、再生位置、対象出力を送信する。

本作のキャラクター表現は2Dピクセルであり、Humanoidアバターもスケルタルアニメーションも存在しない。演出は部位別スプライトのテクスチャ差し替えと微小なピクセル位置オフセットで構成される。したがってTransformの相対変位から運動を計測してfunscriptを自動生成することはできない。代わりに、MODは演出の段階遷移をトリガーとして検出することに専念し、`.funscript` はユーザーがオーサリングGUIで作成する。根拠は付録Cに記録する。

### 1.2 目的

- 対象アニメーションまたはイベントの開始、段階遷移、終了に合わせてEDIギャラリーを制御する。
- 制御対象の物理デバイスを、それぞれ独立した**出力**として個別に制御する。ある出力の再生内容が他の出力の再生内容を変更してはならない。A10ピストンSA、U.F.O TW左、U.F.O TW右は別々の出力である。
- イベント再生中でないときは、プレイヤーの状態異常に応じたfillerを出力ごとに選択して再生する。
- EDIの停止、通信失敗、設定不備がゲーム本体の進行やフレーム処理を妨げないようにする。
- 対応対象を推測で再生せず、明示的なマッピングと網羅性レポートによって管理する。
- 敵ごとに段数の異なる演出段階を、ユーザーの識別子入力なしに段階単位で列挙し、`.funscript` を割り当て可能なトリガーカタログとして提示する。
- ユーザーがゲームを起動したまま `.funscript` を作成・試聴・保存できるオーサリングGUIを提供する。

### 1.3 成功条件

1. 対象候補として収集された全トリガーと全状態異常が、マッピングファイル上で `mapped` または理由付き `ignored` に分類されている。
2. `mapped` トリガーでは、指定されたEDIギャラリーが指定出力に送信され、アニメーションの開始位置とループ長に対応する。
3. `膨乳` 中の待機状態では、乳房側の各出力で専用fillerが選択される。
4. 寄生系と`膨乳`が同時に成立しても、ピストン側の出力と乳房側の各出力はそれぞれ自分の最優先ルールを適用し、互いの再生内容を変更しない。
5. ある出力へ送ったギャラリーが、台帳上その出力に属さない物理デバイスへ到達しない。到達し得る構成は起動時に検出され、当該出力だけが抑止される。
6. デバイスを動かさないことが、波形の内容ではなく制御状態として表現され、ログから判別できる。
7. 同一トリガーの重複通知、古い終了通知、通信断が発生しても、新しい再生を誤停止させたりゲームを停止させたりしない。
8. HTTP通信と再試行待機はゲームのメインスレッドをブロックしない。
9. 敵ごとの演出段階が、ユーザーによる識別子入力なしにトリガーカタログへ段階単位で列挙される。
10. ユーザーはオーサリングGUIから、カタログ上の任意の段階に対して `.funscript` を作成、試聴、保存でき、保存後は同じ段階の次回発生からEDIで再生される。

## 2. スコープ

### 2.1 対象

- BepInEx IL2CPPプラグインとしてのゲーム状態フック。
- 拘束、ギャラリー、ゲームオーバー、その他明示的に採用された演出イベントの段階遷移の観測。
- トリガーキーおよび状態異常識別子からEDIギャラリーへの明示的マッピング。
- マッピングファイルが宣言するデバイス台帳と、物理デバイス1台につき1つの出力。既定構成は `main`、`breast-left`、`breast-right` の3出力。
- A10ピストンSA用とU.F.O TW左右用の `.funscript` バリアント。
- 待機中の通常fillerと、状態異常に応じたfillerの、出力ごとの選択。
- 出力とEDI上の物理デバイスの束縛（チャンネル、バリアント）の起動時検証と、不一致時の出力単位の抑止。
- EDI本体の改修。7.4に列挙した範囲に限る。
- 常時収集によるトリガーカタログの生成と網羅性レポートの生成。
- ゲーム側のデータ構造から静的に列挙できる演出段階の先読み登録。
- ループバック限定のローカルHTTPで配信する `.funscript` オーサリングGUI。
- オーサリングGUIからの実機試聴、保存、EDIへの再走査要求、マッピング更新。
- EDI未起動、タイムアウト、無効な設定、欠落アセットからの安全な復旧。

### 2.2 非対象

- MODからIntiface Centralまたはデバイスへ直接送る低レベル命令。
- `.csv` をMODの入力制御ファイルとして再生する機能。
- ゲーム内アニメーションの運動を計測しての `.funscript` 自動生成。1.1および付録Cの理由により本作では成立しない。
- EDIが事前記録コンテンツしか再生できない制約を越えた、未登録トリガーの初回発生時の再生。`.funscript` が保存され登録されるまで、その段階は再生しない。
- EDIを別端末から利用するリモート接続。
- 7.4に列挙しないEDIの機能追加、UI変更、他ゲーム向け互換層。
- CelSector用MODとのバイナリ互換性。
- `schemaVersion` 1 のマッピングファイルの読み込みおよび自動移行。12.4の手動移行で置き換える。
- ゲーム内の設定画面、手動再生画面、ホットキー。オーサリングGUIはゲーム外のブラウザで動作する。
- A10ピストンSAとU.F.O TW以外のデバイス固有保証。台帳へ追加して束縛を成立させれば動作し得るが、本仕様の受け入れ対象ではない。

### 2.3 前提と制約

- EDIはゲームと同じWindows端末上で起動し、既定では `http://127.0.0.1:5000` を使用する。
- EDIはソースが手元にある改修可能な構成要素である。正本は表紙に記した `N:\Git\repository\Edi` であり、配置される `Edi/Edi.exe` は必ずこのソースからビルドしたものとする。バイナリとソースの対応はSHA-256で確認する。
- デバイスの検出と物理制御はEDIおよびIntiface Centralの責務である。MODはEDIのデバイス設定を書き換えない。MODは `GET /Devices` で状態を読み取り、期待と異なる場合は当該出力を抑止して理由を提示する。
- EDIに渡すコンテンツは、リポジトリ同梱またはユーザーがオーサリングGUIで作成しリポジトリへ保存したギャラリーであり、動的な生デバイス命令は使用しない。
- ゲームアセット内の識別子はビルド更新で変わり得る。対応ゲームビルドごとに診断収集と網羅性確認を行う。
- 対象ビルドのキャラクターAnimatorはHumanoidアバターを持たず、`GetBoneTransform` は全ボーンで `null` を返す。運動信号として利用可能なTransform変位は存在しない。
- 演出段階の識別子はゲームアセットだけから全て静的に確定できない。ギャラリーの段階配列は到達時に列挙し、拘束シーケンスの段階は観測時に追記する。ユーザーによる識別子の手入力を要求してはならない。
- `.funscript` の内容はユーザーがオーサリングGUIで決定する。MODは波形を生成も推測もしない。

## 3. 用語

| 用語 | 定義 |
|---|---|
| EDI | Easy Device Integration。ゲームからREST APIで制御する独立プロセス。 |
| ギャラリー | EDIが名前で再生する事前作成コンテンツ。 |
| バリアント | 同じギャラリー名に対するデバイス別の `.funscript`。EDI側でデバイスへ割り当てる。1つの出力は正確に1つのバリアントを使用する。 |
| チャンネル | EDI内の独立した再生ストリーム。1つのチャンネルは0台以上のデバイスを持ち、そのチャンネル宛の命令はチャンネル内の全デバイスへ同時に適用される。指定しないAPI呼び出しは全チャンネルへ作用するため、本MODは常に明示する。 |
| 出力 | MODが独立して制御する単位。物理デバイス1台と1対1で対応し、EDI上では専用チャンネル1つと専用バリアント1つで実現する。MOD、マッピングファイル、オーサリングGUIはチャンネルではなく出力を単位とする。 |
| デバイス台帳 | マッピングファイル上の出力定義配列。出力ID、表示名、EDI上のデバイス名、バリアントを持つ。存在する出力の集合はこの台帳だけが決め、実装に固定値を持たない。 |
| 束縛 | 出力とEDI上の物理デバイスの対応。出力IDと同名のチャンネルに、台帳が指名したデバイスだけが、台帳が指名したバリアントで所属している状態を「束縛が成立している」という。 |
| filler | 対象イベントが再生されていないゲームプレイ中に、出力ごとにループ再生する待機ギャラリー。EDIの `filler` 種別とは別概念であり、本MODはEDIの `filler` 種別を使用しない（DEC-023）。 |
| 無動作 | ある出力へ意図的に何も再生しない制御状態。波形の内容ではなく `Stop` の送信で表現する。 |
| トリガー | デバイス動作を切り替えるゲーム側の状態遷移。`context`、`actorId`、`animationId`、`phase`、`stageId` の5組で一意になる。本仕様で「イベント」と呼ぶものはトリガーと同義である。 |
| 段階 | 1つの敵または演出が持つ複数の演出フェーズ。ギャラリーではtake配列の要素、拘束シーケンスでは状態機械の状態に対応する。段数は敵により異なる。 |
| `stageId` | 段階を一意に識別する安定文字列。ギャラリーではtake名、取得できない場合はtake配列index。拘束シーケンスでは状態名。単一段階しか持たないトリガーでは `default`。 |
| トリガーカタログ | MODが観測または静的列挙したトリガーを段階単位で蓄積した機械可読ファイル。マッピングの入力であり、マッピングそのものではない。 |
| オーサリングGUI | MODがループバック限定のローカルHTTPで配信し、ユーザーがブラウザで操作する `.funscript` 作成画面。 |
| 試聴 | オーサリングGUIから編集中の `.funscript` をEDIへ送り、実機で確認する操作。 |
| desired state | 各出力で最終的に成立させたい再生状態。通信中の一時状態ではなく、最新のゲーム状態を表す。出力ごとに独立して保持する。 |
| 網羅性レポート | トリガーカタログと、マッピング上の `mapped` / `ignored` 判定を突合した成果物。 |
| セッションログ | 1回のゲーム起動で取得した全レコードを時系列順に追記するUTF-8 JSON Linesファイル。トリガー遷移と観測テキストの一次資料である。 |

## 4. 採用設計

### 4.1 全体構成

1. **Game Hook Adapter**
   - BepInEx IL2CPP上でゲームのライフサイクル、ギャラリー、拘束、状態異常を観測する。
   - 段階遷移は、可能な場合ゲーム側の状態通知を購読して取得し、Animatorのフレーム走査に依存しない。
   - Unityオブジェクトへのアクセスはメインスレッド上だけで行い、ワーカーへは不変のスナップショットを渡す。
2. **Mapping Repository**
   - 起動時にマッピングファイルを読み込み、デバイス台帳、重複、未知の出力ID、必須値欠落を検証する。
   - トリガーキーおよび状態異常識別子を、出力ごとのEDIアクションへ変換する。
3. **Playback Coordinator**
   - 出力ごとのdesired stateと、保持中のトリガー同一性を管理する。出力間で状態を共有しない。
   - トリガー、filler、無動作、停止、ポーズ、試聴の優先順位を出力ごとに解決し、重複命令と古い終了通知を破棄する。
   - 同一ギャラリーかつ同一seekの出力群を1回の命令へまとめ、同時開始を保証する。
4. **Binding Verifier**
   - 起動時および出力の有効化時に `GET /Devices` を照会し、台帳の各出力について束縛の成立を検証する。
   - 束縛が成立しない出力だけを抑止し、不成立の理由を1回だけログとオーサリングGUIへ提示する。
5. **EDI Client**
   - 単一の再利用可能なHTTPクライアントを使い、出力ごとに命令順を直列化する。
   - HTTP処理、タイムアウト待機、再接続待機をメインスレッド外で行う。
   - ゲーム由来の再生とオーサリングGUI由来の試聴は、いずれもこのクライアントだけを経由する。
6. **Trigger Catalog Recorder**
   - 常時、トリガー遷移と観測テキストをセッションログへ追記する。
   - 観測または静的列挙した段階をトリガーカタログへ原子的に統合し、網羅性レポートを更新する。
   - 取得できる公開IL2CPP/Unity値の範囲で記録し、取得不能なカテゴリは能力情報と理由を保存する。
7. **Authoring Server**
   - ループバック限定のローカルHTTPでオーサリングGUIとカタログを配信する。
   - GUIが保存した `.funscript` をリポジトリへ原子的に書き込み、EDIへ再走査を要求し、マッピングを更新する。
   - GUIからの試聴要求をPlayback Coordinatorへ渡し、試聴終了時にゲーム側desired stateへ復帰させる。

### 4.2 出力とデバイス

制御単位は物理デバイスである。1つの出力は、1台の物理デバイス、1つのEDIチャンネル、1つのEDIバリアントと1対1で対応する。既定構成は次の3出力であり、これは台帳の既定値であって仕様上の固定値ではない。

| 出力ID（＝EDIチャンネル名） | 対象デバイス | EDIデバイス名 | EDIバリアント | 動作 |
|---|---|---|---|---|
| `main` | A10ピストンSA | `Vorze Piston` | `a10-main` | 股間向けのピストン制御 |
| `breast-left` | U.F.O TW 左 | `Vorze UFO TW Rotate: 1` | `ufo-left` | 左側用の回転・振動パターン |
| `breast-right` | U.F.O TW 右 | `Vorze UFO TW Rotate: 2` | `ufo-right` | 右側用の回転・振動パターン |

出力IDはEDIチャンネル名を兼ねる。1チャンネルに複数デバイスを同居させないため、あるギャラリーが台帳外のデバイスへ届く経路が構造的に存在しない。

左右の同時開始は、チャンネルの共有ではなく命令のまとめ方で保証する。EDIは `channels` をカンマ区切りで受け取り、対象チャンネルへ並行に適用する。したがって同一ギャラリーかつ同一seekを複数出力へ送る場合は、1回の要求へまとめなければならない（FR-046）。

左右差は、同じギャラリー名に対する `ufo-left` / `ufo-right` バリアントで表現する。左右で異なるギャラリーを指定することも、片側だけを無動作にすることも可能であるが、異なるギャラリー名を指定した場合は要求が分かれるため同時開始は保証されない（5.5）。

### 4.3 スレッドモデル

- ゲームフックは、ゲーム状態の読み取り、トリガーキー生成、スナップショットのキュー投入だけを行う。
- Unity APIおよびIL2CPPオブジェクトをバックグラウンドワーカーから参照してはならない。
- EDI ClientはバックグラウンドでHTTP要求を実行する。
- Authoring ServerのHTTP受信とファイル書き込みはバックグラウンドで行う。ゲーム状態の読み取りが必要な応答は、メインスレッドで作成済みのスナップショットから構成する。
- 各出力の命令は送信順を維持する。別の出力は互いを待たずに処理できる。
- 同時開始のためにまとめた命令（5.5）は、含まれる全出力の順序列へ同一の位置で並び、**1回だけ送信される**。出力ごとに送信を直列化する構造は、まとめた命令を出力の数だけ重複送信してはならない（FR-053）。
- キューが遅延した場合は中間状態を順番に再生せず、各出力の最新のdesired stateへ収束させる。ただし、明示的に `reaction` とされた非ループトリガーはマッピングの指示に従う。
- 収束と競合解決は次の性質で判定する。実現手段は問わない。
  1. ある出力について、より新しいdesired stateが存在するとき、古いdesired stateを送信しない（最新優先）。
  2. あるトリガーの終了通知は、その出力が現在保持しているトリガーと同一である場合にだけ作用する（トリガー同一性による棄却）。
  3. 同一のdesired stateを繰り返し送信しない（重複排除）。

## 5. 制御仕様

### 5.1 状態と優先順位

各出力は、他の出力と独立に次の論理状態のいずれかを取る。同一時刻に異なる出力が異なる状態にあってよい。

| 状態 | 説明 | EDI動作 |
|---|---|---|
| `Inactive` | タイトル、ロード、対象外シーン、終了処理 | `Stop` |
| `Silent` | ゲームプレイ中だが、この出力には意図的に何も再生しない | `Stop` |
| `Filler` | 操作可能なゲームプレイ中で対象トリガーなし | 選択されたfillerを `Play` |
| `Event` | `mapped` トリガー進行中 | トリガーギャラリーを `Play` |
| `Preview` | オーサリングGUIから試聴中 | 試聴対象ギャラリーを `Play` |
| `Paused` | ゲームが一時停止中 | `Pause` |
| `Suppressed` | 束縛が成立していない、またはEDIが当該チャンネルを提供していない | 有効だった出力が遷移する場合はbest effortで `Stop` を送り、以後は何も送らない。起動時から抑止の出力へは何も送らない |
| `Unavailable` | EDIへ到達不能 | ゲームは継続し、最新desired stateを保持 |

優先順位は `Suppressed`、`Inactive`、`Preview`、`Paused`、`Event`、`Silent`、`Filler` の順に評価する。`Unavailable` は通信状態であり、ゲーム側desired stateを上書きしない。

`Suppressed` は最優先とする。束縛が成立していない出力へ命令を送ると、台帳外のデバイスが波形を受け取る可能性があるためである。抑止は出力単位であり、他の出力の動作を止めてはならない。

`Preview` は `Inactive` に次ぐ優先度とする。ユーザーが明示的に開始した確認操作であり、ゲーム側の自動再生に中断されてはならないためである。`Preview` 終了時は、その時点のゲーム状態から `Event`、`Silent`、`Filler`、`Paused`、`Inactive` を再評価する。

`Silent` と `Inactive` はいずれも `Stop` を送るが、意味が異なるため状態としては区別し、ログにも区別して記録する。`Silent` は「ゲームは進行中で、この出力は動かさないことが選ばれた」であり、`Inactive` は「制御対象の場面ではない」である。いずれも波形の内容で表現してはならない（FR-047）。

### 5.2 トリガー開始・更新・終了

1. `mapped` トリガー開始時、Coordinatorはトリガーエントリの `outputs` に列挙された出力だけを `Event` にする。`gallery` が `null` の出力は `Silent` にする。列挙されていない出力は現在の状態を維持し、再評価もしない。
2. `seek` は、観測時点のアニメーション再生位置とクリップ長からミリ秒で算出する。開始位置を取得できないマッピングは `seek = 0` を明示する。同一トリガーの全出力は同じ `seek` を使用する。
3. ループトリガーでは、対応するfunscriptのループ長をゲームのアニメーションループ長と一致させる。通常のループ折り返しだけを理由に `Play` を再送しない。
4. 同じトリガーキーと再生位置に対する重複通知は送信しない。
5. トリガー遷移時、対象となる各出力が保持するトリガー同一性を新しいトリガーへ更新する。以前のトリガーに対する終了通知は、新しい再生を停止してはならない（4.3の性質2）。判定は出力ごとに独立する。
6. トリガー終了時、その出力がまだ同じトリガーを保持している場合にだけ状態異常を再評価し、`Filler`、`Silent`、`Inactive` のいずれかへ遷移する。トリガーに参加しなかった出力は影響を受けない。
7. 段階が切り替わった場合は、`stageId` が異なる新しいトリガーとして扱い、保持中のトリガー同一性を更新して対応するマッピングを再解決する。同じ `stageId` が継続する間は `Play` を再送しない。
8. マッピング未登録トリガーではEDIを開始せず、トリガーカタログへ追記して診断可能な警告を残す。ユーザーがオーサリングGUIで `.funscript` を保存し登録が完了した後、その段階の次回発生から再生する。
9. 非ループギャラリーは、`Definitions.csv` が定める長さを過ぎた時点でEDIがデバイスを停止させる。これは再生長の管理であって状態の所有ではなく、DEC-023の「fillerの正本はMOD」と両立する。MODはこの停止を前提とし、トリガー終了の通知を受けた時点で改めて次のdesired stateを指示する。停止から通知までの間、その出力は無音になる。`reaction` の意図に合致するため、これを不具合として扱わない。

### 5.3 ポーズ、ロード、終了

- ゲームのポーズ開始時は抑止されていない全出力へ `Pause?untilResume=true` を送る。
- ポーズ解除時は単純な `Resume` に依存せず、現在のゲーム状態からギャラリーと `seek` を再計算して `Play` する。これによりEDI側の時計との差を持ち越さない。
- タイトル画面、ロード中、対象外シーンでは `Stop` を送る。`Stop` はデバイスを停止させる命令であり、fillerへ復帰させてはならない（7.4 E2、FR-045）。
- MOD無効化、プラグイン破棄、ゲーム終了では、台帳の全出力に対してbest effortで `Stop` を送ってからワーカーを終了する。Authoring Serverも同時に停止する。
- `mapped` のゲームオーバー演出中は `Event` を維持し、演出終了後に `Inactive` へ遷移する。

### 5.4 filler選択

1. fillerは `Suppressed`、`Event`、`Preview`、`Paused`、`Inactive` のいずれでもない場合だけ再生する。
2. filler選択は出力ごとに独立して行う。ある出力の選択結果が、他の出力の選択結果または再生中の内容を変更してはならない。
3. 状態異常は同時に複数成立する。ある出力について、成立中の状態異常に一致する `mapped` ルールのうち、その出力を含む要素の `priority` が最大のものを適用する。`priority` が等しく、同一出力に対して異なるギャラリー（`null` を含む）を指定するルールが複数一致する構成は、起動時の設定エラーとする（FR-043）。
4. `膨乳` が有効な場合、`breast-left` と `breast-right` は `filler-breast-swollen` を使用する。このギャラリーは通常の乳房側fillerより強い刺激となるようfunscript側で作成する。
5. 一致する状態異常ルールがない場合、`defaultFillers` がその出力に対して指定する値を使用する。値が `null` の出力は `Silent` とする。
6. ルールまたは既定値がその出力に `null` を指定した場合、その出力は `Silent` とし `Stop` を送る。静止波形のアセットで代用してはならない（FR-047）。
7. トリガー進行中に状態異常が変化しても再生中トリガーを中断しない。トリガー終了時に、その出力について最新状態を評価する。
8. 同じfillerが継続する場合は `Play` を再送しない。`Silent` が継続する場合も `Stop` を再送しない。

寄生系デバフと `膨乳` が同時に成立する場合、`main` は寄生系ルールの結果を、`breast-left` と `breast-right` は `膨乳` ルールの結果を、それぞれ同時に保持する。両者は別々の出力であり、どちらも他方の再生内容を変更しない（AC-037）。

### 5.5 命令のまとめ方

1. 1回の状態遷移で、同一ギャラリーかつ同一 `seek` の `Play` を受ける出力群は、1回の要求へまとめて送る。これが左右同時開始の唯一の保証手段である（FR-046、AC-003）。
2. `Stop`、`Pause` についても、同一遷移で同じ命令を受ける出力群は1回へまとめる。
3. 異なるギャラリー名を指定した出力は別々の要求になる。この場合、開始時刻の一致は保証されない。左右で異なる動作を与える場合は、異なるギャラリー名ではなく同一ギャラリー名の異なるバリアントで表現することを既定とする。
4. まとめた要求の `channels` 値は、対象出力IDをカンマで連結した文字列とする。抑止中の出力はこの連結に含めない。

## 6. マッピングとアセット契約

### 6.1 正本

| ファイル | 書き手 | 役割 |
|---|---|---|
| `BepInEx/config/community.sinisistar2.edi/mappings.json` | オーサリングGUI（および同梱初期値） | 対応トリガーと状態異常の正本 |
| `BepInEx/diagnostics/community.sinisistar2.edi/catalog/{gameBuildId}/trigger-catalog.json` | MOD | 観測または列挙した全トリガーの派生カタログ |

マッピングの正本は `mappings.json` だけとする。トリガーカタログはマッピングの入力であり、それ自体が再生を許可することはない。MODはカタログを追記・更新するが `mappings.json` の判定内容を自動で書き換えてはならない。オーサリングGUIによる保存だけが `mappings.json` を更新でき、更新は原子的に行う。

MODの起動ログには両ファイルの解決後絶対パスを表示する。マッピングに存在しない暗黙の再生、名前だけによる再生フォールバックは禁止する。

マッピングファイルは次のトップレベル値を持つ。

| フィールド | 内容 |
|---|---|
| `schemaVersion` | ファイル構造の互換性を判定する版。本仕様は `2` を要求する |
| `mappingVersion` | 内容更新を追跡する版 |
| `targetGameBuild` | `GameAssembly.dll` と `global-metadata.dat` のSHA-256 |
| `outputs` | 6.1.1のデバイス台帳。存在する出力の集合を決める唯一の定義 |
| `events` | 6.2のトリガーエントリ配列 |
| `statusRules` | 6.3の状態異常エントリ配列 |
| `defaultFillers` | 出力IDから既定fillerギャラリー名への対応。台帳の全出力にキーが必要。値に `null` を指定した出力は既定で `Silent`。キーの欠落は設定エラー（FR-056） |

`schemaVersion` が `2` でないファイルは読み込まず、設定エラーとして出力を無効化する。移行手順は12.4に置く。

#### 6.1.1 デバイス台帳

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | Yes | 出力ID。EDIチャンネル名を兼ねる。ファイル内で一意 |
| `displayName` | Yes | 人間向け名称。オーサリングGUIとログに使用する |
| `ediDeviceName` | Yes | EDIが `GET /Devices` で返すデバイス名 |
| `ediVariant` | Yes | この出力が使用するEDIバリアント名 |

台帳は次を満たさなければならない。満たさない場合は設定エラーとしてデバイス出力を無効化する。

1. `id`、`ediDeviceName`、`ediVariant` がそれぞれファイル内で一意である。同じデバイスまたは同じバリアントを2つの出力が共有してはならない。
2. 台帳が空でない。
3. `events`、`statusRules`、`defaultFillers` が参照する出力IDが全て台帳に存在する。
4. `defaultFillers` が台帳の全出力に対してキーを持つ（FR-056）。
5. リポジトリ内の全ギャラリーについて、そのバリアントが全て台帳のいずれかの `ediVariant` に一致する。一致しないバリアントは、対象出力集合を導出できないため設定エラーとする（DEC-026、FR-057）。
6. `膨乳` に対応する状態異常ルールが `mapped` として存在する。既定構成では、その `outputs` が `breast-left` と `breast-right` の両方に対して `filler-breast-swollen` を指定する（FR-011）。台帳を既定構成から変更した場合は、この検証の対象出力も台帳とあわせて更新する。

出力の集合を実装のコード上に固定してはならない。デバイスの追加または変更は、台帳の編集と対応する `.funscript` バリアントの追加だけで完了しなければならない（FR-048）。

台帳の既定値は4.2の3出力とする。既定構成での記述例を示す。値は例であり規範ではない。

```json
{
  "schemaVersion": 2,
  "outputs": [
    { "id": "main",         "displayName": "A10ピストンSA", "ediDeviceName": "Vorze Piston",             "ediVariant": "a10-main" },
    { "id": "breast-left",  "displayName": "U.F.O TW 左",   "ediDeviceName": "Vorze UFO TW Rotate: 1",   "ediVariant": "ufo-left" },
    { "id": "breast-right", "displayName": "U.F.O TW 右",   "ediDeviceName": "Vorze UFO TW Rotate: 2",   "ediVariant": "ufo-right" }
  ],
  "defaultFillers": {
    "main": "filler-main",
    "breast-left": "filler-breast",
    "breast-right": "filler-breast"
  },
  "statusRules": [
    {
      "statusId": "Breast", "displayName": "膨乳", "disposition": "mapped", "priority": 10,
      "outputs": [
        { "id": "breast-left",  "gallery": "filler-breast-swollen" },
        { "id": "breast-right", "gallery": "filler-breast-swollen" }
      ]
    },
    {
      "statusId": "Parasite", "displayName": "Parasite", "disposition": "mapped", "priority": 10,
      "outputs": [ { "id": "main", "gallery": "filler-main-parasite" } ]
    }
  ]

```

この2ルールが同時に成立した場合、`main` は `filler-main-parasite`、`breast-left` と `breast-right` は `filler-breast-swollen` を保持する。3出力は別々のEDIチャンネルであり、互いの再生内容を変更しない（AC-037）。

### 6.2 トリガーエントリ

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | Yes | マッピング内で一意な安定ID |
| `context` | Yes | `hold`、`gallery`、`game-over`、`scripted-event` のいずれか |
| `actorId` | Yes | 敵、イベント、ギャラリーなどのゲーム内識別子 |
| `animationId` | Yes | クリップ名、Animatorハッシュの元名、または観測可能な安定識別子 |
| `phase` | Yes | `start`、`loop`、`reaction`、`end` のいずれか |
| `stageId` | Yes | 段階の安定識別子。単一段階のトリガーでは `default` |
| `disposition` | Yes | `mapped` または `ignored` |
| `outputs` | mapped時 | 出力割当の配列。空配列は禁止 |
| `seekMode` | mapped時 | `animation-time` または `zero` |
| `ignoreReason` | ignored時 | 対象外とする観察可能な理由 |

`outputs` の各要素は次の形とする。

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | Yes | 台帳に存在する出力ID。同一エントリ内で重複禁止 |
| `gallery` | Yes | EDIへ渡すギャラリー名。`null` はこの出力を `Silent` にすることを意味する |

`context + actorId + animationId + phase + stageId` は一意でなければならない。重複がある場合、MODはデバイス出力を開始せず設定エラーとして扱う。

#### 6.2.1 拘束トリガーの `actorId`

`context` が `hold` のとき、`actorId` は拘束している側を指す。拘束者は `Lelia.Bind.Binder`（型は `IBinder`）から得る。`Bind.BinderEnemy` はそのうち `EnemyObject` であるものだけを指す**部分集合**であり、拘束者の正本ではない。

次の順に解決し、最初に得られたものを `actorId` とする（DEC-031）。

| 順 | 参照先 | 例 |
|---|---|---|
| 1 | 拘束者の `m_GalleryEnemyID` が `None` 以外 | `GaID_Mimic` |
| 2 | 拘束者の `m_EnemyID` が `None` 以外 | `EnmID_MeatWorm1` |
| 3 | 拘束者のオブジェクト名（末尾の `(Clone)` と ` (N)` を除去し、接頭辞 `obj:` を付す）。ただし構造名は除く | `obj:ParasiteTentacle` |
| 4 | 拘束者のコンポーネント型名（接頭辞 `obj:` を付す） | `obj:StoneEye` |
| 5 | いずれも得られない | `unidentified-binder` |

- **`None` を `actorId` にしてはならない。** `GalleryEnemyID` の `None` は「ギャラリー登録が未設定」を意味し、特定の敵を指さない。これを識別子として用いると、登録されていない敵がすべて同一のトリガー鍵を共有し、ある敵のために作成した `.funscript` が別の敵の拘束で再生される。
- **`Root` や `Base` のような構造名を `actorId` にしてはならない。** この対象ビルドでは、拘束判定や攻撃判定が全キャラクターの `Root` という名のオブジェクトにぶら下がっている（実測ログのシーン階層）。そこに居合わせた拘束者どうしが同じ鍵を共有するため、`None` と同じ害になる。構造名だった場合は順4のコンポーネント型名へ進む。
- **拘束者を `EnemyObject` として解釈できないことを理由に、拘束の観測を省いてはならない。** 観測できる拘束を観測しないことは、未登録トリガーとして警告する場合と違い、カタログにも診断にも何も残らない。順5の `unidentified-binder` はそのための受け皿である。
- **順5の `unidentified-binder` は、マッピングを持ってはならない。** この値は特定の拘束者を指さず、名指せなかった拘束者すべてを表す。ここに `.funscript` を割り当てると、それら全てが同じ波形を受け取り、「イベントごとに異なる刺激を与える」という本MODの目的（1.2）が破れる。したがってオーサリングGUIはこの鍵での保存を拒否し、再生側は手書きされたマッピングも解決してはならない。カタログには残す。**記録は残すが再生はしない**が順5の意味である。
- 順5は診断のための一時的な状態であり、恒常的な運用状態ではない。発生した場合は、その拘束者を名指せるようにすること自体が修正対象である。
- `context` が `game-over` のときの `actorId` も同じ順で解決し、拘束者が居ない場合にのみ `lelia` とする。

`outputs` に列挙されていない出力は、このトリガーの影響を受けない。列挙されていないことと `gallery: null` は異なる。前者は「この出力は関与しない（現在のfillerを継続する）」、後者は「この出力を止める」である。

`phase` は演出の役割、`stageId` は同一演出内の段階を表し、両者を混同してはならない。段数が敵により異なるため、`stageId` の値域を仕様で固定しない。

#### 6.2.2 敗北トリガー

`context` が `game-over` のトリガーは、ゲーム自身の死亡状態機械 `Lelia.LeliaDeadState`（`Live` / `HP0` / `GameOver`）から観測する。

| 規定 | 内容 |
|---|---|
| 観測条件 | `LeliaDeadState` が `Live` 以外である間 |
| 優先順位 | 拘束（`hold`）および `scripted-event` より**優先する** |
| `actorId` | 6.2.1と同じ順序で拘束者を解決し、拘束者が居ない場合にのみ `lelia` |
| `stageId` | `LeliaDeadState` の値（`HP0` または `GameOver`） |
| `animationId` | 段階に入った時点でのプレイヤーのクリップ名。読めない場合は `LeliaDeadState` の値 |
| `phase` | `reaction` |

- **HP0であることを観測条件にしてはならない。** `IsHP0` はヒットポイントについての値であり、ゲームが「敗北である」と決めたあとに走る演出は別の段階である。実測（対象ビルドのトリガーカタログ）では、`Dungeon_Swamp_Boss` の1回の敗北に対して `game-over/lelia/Damage3_Wall`、`Damage3_Wall_Down`、`Idle_Injured` の3行が記録されている。いずれも0.7秒前後の被弾クリップであり、ギャラリーに登録されている当該敵の敗北take（`GaID_SwampLeech_Adult` の `Go_End1` は5.85秒）とは別物である。**長く続く演出そのものはトリガーになっていなかった。**
- **敗北は拘束に優先する。** 拘束されたまま敗北する経路では、拘束を先に判定すると演出の間ずっと `hold` のトリガーが継続し、敗北のトリガーは一度も現れない。
- **鍵は段階の開始時に確定し、段階が変わるまで保持する。** 毎回アニメータを読み直すと、プレイヤーのアニメータが次のクリップへ移るたびに別の鍵になり、1回の敗北の途中で再生の開始と停止が繰り返される。上記の3行はこの現象の記録である。
- **プレイヤーのアニメータから読めないことを理由に観測を落としてはならない。** 敗北演出はシーン側のスクリプト演出で行われる場合がある。その場合も段階は起きており、`animationId` を状態名とした上でカタログへ残す。6.2.1の順5と同じ理由で、観測できる事象を無言で落とさない。
- 観測が中断した場合（シーン遷移、プレイヤーオブジェクトの喪失）、確定していた鍵は破棄する。次の敗北は改めて確定する。

### 6.3 状態異常エントリ

| フィールド | 必須 | 内容 |
|---|---|---|
| `statusId` | Yes | 常時収集で取得したゲーム内識別子 |
| `displayName` | Yes | 人間向け名称。初版では少なくとも `膨乳` を含む |
| `disposition` | Yes | `mapped` または `ignored` |
| `outputs` | mapped時 | 出力割当の配列。空配列は禁止 |
| `priority` | No | 同一出力内の優先度。数値が大きいほど優先する。省略時は `0` |
| `ignoreReason` | ignored時 | デバイス制御へ影響させない理由 |

`outputs` の各要素は6.2と同じ形とし、`gallery` はfillerギャラリー名または `null`（その出力を `Silent` にする）を取る。左右で異なるfillerを与える構成、片側だけを `Silent` にする構成のいずれも、この形で表現できる。

ある出力に対して、`priority` が等しく `gallery` の値が異なる `mapped` ルールが複数存在する場合、どちらを適用するかが宣言されていないため設定エラーとする。`null` も1つの値として比較する。`priority` が等しくても `gallery` が同一なら適用結果が一意に定まるため許容する。判定は出力単位で行う。全ての既知状態異常は `mapped` または理由付き `ignored` に分類する。

### 6.4 常時収集とセッションログ

1. 収集はユーザー設定を必要とせず常時有効とする。一次資料は `BepInEx/diagnostics/community.sinisistar2.edi/sessions/{gameBuildId}/{sessionId}.animation.jsonl` へ保存する。既存セッションを上書きまたは自動削除してはならない。
2. JSONLの各行は `schemaVersion`、`recordType`、`sessionId`、単調増加する `sequence`、`utc`、`realtimeMs`、`frameCount` を持つ。`recordType` は `session-start`、`event-transition`、`catalog-update`、`text-change`、`capture-warning`、`session-end` のいずれかとする。
3. `event-transition` はトリガーの開始、段階切替、終了ごとに1回記録し、遷移前後のトリガーキー、Scene、クリップ長、ループ可否、観測時のnormalizedTime、現在の状態異常、Unity時刻、timeScaleを含む。
4. `catalog-update` は、静的列挙または観測によってカタログへ新しい段階が追加されたときに記録し、追加された段階と列挙元を含む。
5. フレーム単位のTransform、Animatorレイヤー、ボーン姿勢は収集しない。本作にはボーンが存在せず、これらは運動信号として利用できないためである。取得を必要とする将来要件が生じた場合は、本節を改訂したうえで対象を限定して再導入する。
6. 画面テキストは取得可能なUI実装ごとに列挙し、階層パス、テキスト、active状態が変化した時に `text-change` として記録する。ゲームから直接得られるScene名、take名、actor名、clip名、layer名もテキストデータとして保持する。テキストは段階の人間向け表示名候補として利用する。
7. 対象ゲームビルドのinteropに公開getterがない、getterが例外を送出する、コンポーネントが存在しない等の理由で取得不能なカテゴリは、省略せず `available=false` と機械可読な `unavailableReason` を `session-start` または `capture-warning` に記録する。「全て取得」とは、このビルドで安全に呼べる生成済みUnity/IL2CPP公開getterの範囲を指し、未検証のネイティブメモリ走査は含まない。
8. Unityオブジェクトはメインスレッドだけで読み取り、不変DTOを追記ワーカーへ渡す。キュー詰まりやI/O失敗でレコードを黙って破棄してはならず、欠番、失敗範囲、未書込件数を `capture-warning` と通常ログに残す。
9. `coverage.json` とトリガーカタログはセッションログから得た派生成果物であり、遷移時系列の代用にしてはならない。
10. ゲーム更新後はビルド別ディレクトリへ分離して収集し、新規、消失、識別子変更を差分として確認する。

### 6.5 トリガーカタログ

1. カタログは段階単位のエントリ配列とし、各エントリは6.2のキー5要素、クリップ長、ループ可否、列挙元（`static-enumeration` または `observed`）、初回観測時刻、表示名候補、現在のマッピング判定を持つ。
2. ギャラリーの段階配列のように、到達時点でゲーム側から全段階を列挙できる場合は、未到達の段階も含めてカタログへ登録する。列挙元を `static-enumeration` とし、クリップ長が未取得の項目は欠落を明示する。
3. 拘束シーケンスのように状態機械として進行する段階は、遷移を観測した時点で追記する。列挙元を `observed` とする。
4. カタログの更新は原子的に行い、既存エントリを失ってはならない。同一キーの再観測では、欠落していた値の補完だけを行う。
5. 網羅性レポートは、カタログと `mappings.json` を突合して `mapped`、`ignored`、`unclassified` を機械判定できる形式で出力する。
6. カタログは再生可否を決定しない。`mappings.json` に `mapped` として存在しない段階は再生してはならない。

### 6.6 funscriptとバリアント

- MODが要求する入力アセット形式は `.funscript` とする。
- `.csv` はEDIが特定デバイス向けバンドルとして内部生成する場合があるが、本MODの入力契約ではない。
- 同じトリガーを複数出力で再生する場合、全バリアントで同じギャラリー名を使用する。
- **ギャラリーの対象出力集合は、そのギャラリーが持つバリアントの集合が決める。** 台帳が出力とバリアントを1対1で対応付けるため、両者は相互に導出できる。あるギャラリーを、そのギャラリーがバリアントを持たない出力へ送ってはならない。この規則はゲーム由来の再生にも試聴にも等しく適用する（FR-049）。
- したがって、ある出力を対象としないギャラリーには、その出力のバリアントファイルを置かない。対象外バリアントの静止アセットは作成しない。
- fillerはEDI上で `gallery` 種別かつループとして定義する。EDIの `filler` 種別は使用しない（DEC-023）。
- `.funscript` の波形はユーザーがオーサリングGUIで作成する。MODは波形を生成、補間、推測、複製してはならない。`ufo-left` と `ufo-right` を片側の自動反転で埋めることも禁止する。位置を変化させない静止波形も同様に作成してはならない。デバイスを動かさないことは `Silent` 状態と `Stop` で表現する（FR-047）。
- ギャラリー名はトリガーキーのSHA-256短縮値を含む安定名とし、ファイル名に未検証のゲーム文字列を直接使用しない。表示名はカタログの表示名候補を用い、ファイル名には使用しない。
- 保存先は `Edi/Gallery/{ediVariant}/{gallery}.funscript` とし、`{ediVariant}` は台帳が定める値を使う。書き込みは原子的に行う。
- ギャラリー定義（種別、ループ可否、開始・終了時刻）の正本は `Edi/Gallery/Definitions.csv` とする。EDIがアセットからファイル名を根拠に定義を自動生成した状態に依存してはならない。
- ループ対象トリガーでは、`.funscript` の終端時刻とカタログ上のクリップ長の差が1フレーム相当を超える場合、保存時に検証エラーとして提示する。ユーザーが差異を承認した場合は、承認をマニフェストへ記録して保存を許可する。
- 必須バリアントまたはEDI定義が欠落するマッピングは起動前検証または診断でエラーにする。

### 6.7 オーサリングGUI

1. MODはループバックアドレス限定のローカルHTTPサーバでオーサリングGUIを配信する。待ち受けアドレスとポートは設定可能とし、非ループバックアドレスへの待ち受けは設定エラーとする。
2. GUIはトリガーカタログを段階単位で提示し、`actorId`、表示名候補、`stageId`、クリップ長、ループ可否、現在のマッピング判定、バリアントの有無を一覧できる。
3. GUIは選択した段階に対して、出力ごとの `.funscript` を作成、編集、複製、保存できる。既存の段階から波形を複製して編集を開始する操作を提供する。
4. GUIは編集中の `.funscript` を試聴できる。試聴要求はMODのEDI Clientを経由し、対象出力を明示する。試聴中は5.1の `Preview` 状態とし、終了時にゲーム側desired stateを再評価して復帰する。
5. 試聴の対象出力は、対象ギャラリーがバリアントを持つ出力に限る。GUIはそれ以外の出力を選択肢として提示してはならず、要求された場合はMODが拒否して理由を返す。抑止中の出力についても同様に拒否する（FR-049、AC-036）。
6. 試聴は、対象ギャラリーがEDIに読み込まれていることを前提とする。EDIは名前で登録済みのギャラリーしか再生できないため、未保存の編集内容をそのまま試聴することはできない。GUIは試聴の前に保存を完了させ、保存経路が再走査（FR-044）まで終えてから試聴要求を送る。
7. 保存操作は、`.funscript` のリポジトリへの原子的書き込み、`Definitions.csv` の更新、EDIへの再走査要求、`mappings.json` の原子的更新を一連の処理として行う。いずれかが失敗した場合は `mappings.json` を `mapped` へ更新せず、失敗理由をGUIとログへ提示する。
8. 保存が `mappings.json` の `outputs` へ与える影響は加算的とする。対象出力に対応する要素を追加または更新するだけで、同じエントリの他の出力の要素を削除してはならない。左右のバリアントを別々に保存する運用で、先に保存した側が失われないようにするためである。
9. 各保存済みギャラリーに `BepInEx/diagnostics/community.sinisistar2.edi/generated/{gameBuildId}/{gallery}.manifest.json` を作成する。マニフェストはトリガーキー、カタログ上のクリップ長、ループ可否、作成日時、GUI版、ループ長差異の承認有無、各出力ファイルのSHA-256を持つ。
10. GUIは各出力の現在状態（`Suppressed` を含む）と、抑止されている場合はその理由を表示する。
11. GUIはゲームプロセスの生存に依存する。ゲーム終了時にサーバを停止し、未保存の編集内容が失われることをGUI上で明示する。
12. GUIは秘密情報を扱わず、認証を持たない。ループバック限定であることを唯一の到達制御とし、この前提を10.2に記録する。
13. MODはゲーム実行中に、既定のブラウザでGUIを開く手段をゲーム内から提供する。GUIはこのMODの唯一のオーサリング画面であり、それを開く方法が「起動ログからURLを読み取って手で入力する」しかない状態は、作業の入口として成立していない。
    - 開くための操作は設定可能なキー1つとし、既定を `F6` とする。`F7`〜`F11` は快楽MODの画面が使用しているため充てない。
    - 設定値が空、または `KeyCode` として解釈できない場合、キーによる起動を行わない。解釈できなかった場合はその旨を記録する。無反応なキーは機能の欠落と区別できないためである。
    - 起動時に自動で開く設定を持ってよいが、既定は無効とする。ゲームの起動はGUIを求める操作ではない。
    - ブラウザの起動に失敗しても、ゲームと他の機構は継続しなければならない。GUIはURLで到達可能なまま残る。
14. GUIは、ある段階の波形を他の段階でも再生させる操作を提供する。適用先は複数選択できる。方式は次の2つとし、どちらであるかを操作時に明示する。
    - **共有（リンク）**: 適用先のトリガーエントリの `outputs[].gallery` を、元の段階のギャラリー名にする。`.funscript` は複製せず、1つの波形を複数のトリガーが参照する状態にする。以後その波形を編集すると、参照している全段階に反映される。
    - **複製（コピー）**: 適用先ごとに独立したギャラリーを作成し、6.7-7の保存経路を通す。以後は別々に編集できる。
    - 共有を選ぶ理由は、拘束開始時の待機・歩行・落下といったプレイヤー側の状態によってゲームが別のイベントを選ぶ一方、画面上の動きはほぼ共通であることによる。段階ごとに同じ波形を作り直すと、修正のたびに全てを直す必要があり、片方だけ直し忘れた状態を検出する手段がない。
15. 共有に関する規定は次のとおりとする。
    - **1つのトリガーが参照するギャラリーは1つでなければならない。** GUIが編集・試聴の対象とするギャラリーは、そのトリガーのマッピングが名指すギャラリーとし、鍵から導出した自前の名前ではない。マッピングが複数のギャラリーを名指す場合、それはリンクではないため、GUIは自前のギャラリーを対象とする。
    - 適用先が `mapped` にできない段階（未再生の列挙済み段階、`unidentified-binder`）である場合は、保存と同じ理由で拒否しなければならない（FR-060）。
    - 適用先がループ対象で、そのクリップ長と共有する波形の長さの差が1フレーム相当を超える場合、FR-040と同じく検証エラーとして提示し、ユーザーの承認を得た場合にのみ適用する。承認はマニフェストへ記録する。
    - 適用先が既に自前の `.funscript` を持つ場合、そのファイルは削除しないが再生されなくなる。この事実を承認の対象に含める。
    - 共有中であること、および同じ波形を再生する段階の一覧は、編集画面と一覧の双方で提示しなければならない。1段階だけを直したつもりの編集が他の段階へ波及することを、編集の前に知る手段がない状態にしてはならない。
    - **リンクは解除できなければならない。** 解除は、共有していた波形をその段階専用のギャラリーとして書き出す操作とし、他の段階は共有していた波形を保持する。
    - リンクによる `outputs` の更新は置換とする。6.7-8の加算規則は、左右のバリアントを別々に保存する運用のためのものであり、「この段階はあの段階と同じものを再生する」という宣言とは両立しない。元の段階が持つ `gallery: null`（`Silent`）の割当もそのまま引き継ぐ。
16. GUIは、編集中の波形が各出力のデバイスでどのような物理動作になるかを再生表示するシミュレーションを、波形キャンバスの直下に常設する（FR-065、DEC-034）。
    - シミュレーションはブラウザ内で完結する。EDIにも実デバイスにも何も送らず、保存も必要としない。試聴（6.7-6）が保存済みギャラリーしか対象にできないのに対し、保存前の編集内容を確認できる唯一の手段がこれである。
    - 対象は台帳の全出力とする。編集中の波形（バリアント）を持つ出力はそのデバイス表現で動かし、持たない出力は停止状態として表示する。全出力は共通のタイムラインで同時に再生し、再生位置は波形キャンバス上の再生ヘッドとして重畳表示する。
    - デバイス表現は実機の命令解釈に従う。**ピストン（Position）**は到達可能トレース（`MinPistonSegmentMilliseconds` 未満の命令の先取り打ち切りと、`MaxPistonUnitsPerSecond` の移動上限。6.7の既存オーバーレイと同じ規則）を適用した位置を上下動で表示する。描いた線と実機の動きが乖離する場合、その乖離が動きにも現れる。
    - **UFO TW（Rotate）**は、区間の傾き |Δpos|/Δt を450 units/sで正規化した値を回転速度とし、回転方向は実機と同じ分布（500〜2500ミリ秒の一様乱数間隔）で擬似ランダムに反転させる。あわせて、波形が命じている強度（正規化速度）をゲージで併記する。反転の発生時刻は乱数であり実機とは一致しないことをGUI上に明示する。
    - ループは「繰り返し再生」の設定に従う。繰り返しでない場合は1回で停止し、以後デバイスが止まることをそのまま見せる（5.2.9に対応）。

## 7. EDI RESTインターフェース

### 7.1 接続

- 既定のBase URLは `http://127.0.0.1:5000` とする。
- 初版はループバックアドレスのみ許可する。リモートURLは設定エラーとする。
- MODは起動時に `POST /Edi/Reload` を送り、EDIに現在のギャラリールートを読み直させる。ファイル転送は行わない。同梱ギャラリー、オーサリングGUIが保存した `.funscript`、`Definitions.csv` はいずれもMODがリポジトリへ直接書いており（6.6、12.1）、EDIに必要なのは読み直しだけである。失敗した場合はゲームを継続し、警告を記録する。
- EDIの可用性は `GET /Edi/Channels` で確認する。この応答はチャンネル名の集合であり、デバイスの有無を表さないため、出力の可否判定には使用しない。ただし台帳の全出力IDがこの一覧に存在することは確認し、欠けている場合は `EdiConfig.Channels` と台帳の不一致として警告する。この2つは別々に設定されるため、片方だけを更新した構成を検出できるようにする。
- **デバイス出力の可否は出力単位で、束縛の検証によって判定する。** MODは `GET /Devices` を照会し、台帳の各出力について次を全て満たすときだけ、その出力を有効化する。
  1. `ediDeviceName` と同名のデバイスが存在する。
  2. そのデバイスの `Channel` が出力IDと一致する。
  3. そのデバイスの `SelectedVariant` が `ediVariant` と一致する。
  4. そのデバイスの `IsReady` が真である。
  5. 出力IDと同名のチャンネルに、台帳が指名していないデバイスが所属していない。
- 1つでも満たさない出力は `Suppressed` とし、不成立の条件を含む理由を1回だけログとオーサリングGUIへ提示する。他の出力の有効化を妨げてはならない。一部のデバイスのみを接続した構成は正当な運用形態である。
- **既に有効化していた出力が抑止へ移る場合、送信を止める前にその出力へbest effortで `Stop` を送る。** 送信を止めるだけでは、直前に指示したギャラリーがデバイス上でループし続ける。抑止は誤配送を防ぐための状態であり、動作を放置する状態ではない（FR-055）。
- 5の条件は、MODが送ったギャラリーが台帳外のデバイスへ届く構成を検出するためにある。この条件が無いと、EDI側の再接続処理でデバイスのチャンネルが既定値へ落ちた場合に、意図しないデバイスが他の出力の波形を受け取る（付録E）。
- 5の条件は、EDIが `EdiConfig.UnassignedDeviceChannel`（7.4 E4）を設定していることを前提に厳格とする。この設定が無いEDIでは、台帳と無関係なデバイスを接続しただけで先頭出力が抑止され得る。この場合の警告は7.4.3で記録する。
- MODはEDIのデバイス設定を書き換えない。検証は読み取りのみで行い、不一致は運用者が修正する。
- 抑止中の出力は、確認期間内に束縛が成立すれば有効化する。確認期間は起動時の `GET /Devices` 成功から60秒とし、期間内はバックオフ付きで再検証する。期間を過ぎても成立しない出力は、そのセッションの間抑止したままとし、不足内容とゲーム再起動が必要である旨を1回だけログへ記録する。
- 抑止中の出力を対象とする再生要求は、ゲーム由来か試聴かを問わず送信しない。試聴要求の場合は、対象出力が利用できない理由をオーサリングGUIへ返す。

### 7.2 使用するAPI

| 操作 | HTTP要求 | 備考 |
|---|---|---|
| 能力照会 | `GET /Edi/Info` | EDIの版と、7.4のフラグの実効値。起動時の能力ネゴシエーション（7.4.3）に使用する |
| デバイス照会 | `GET /Devices` | 束縛検証の唯一の入力。`Name`、`Channel`、`SelectedVariant`、`IsReady` を読む |
| チャンネル照会 | `GET /Edi/Channels` | EDIの到達性確認にのみ使用する。出力の可否判定には使用しない |
| 再生 | `POST /Edi/Play/{name}?seek={milliseconds}&channels={outputs}` | `{name}` とquery値をURLエンコードする。`{outputs}` は出力IDのカンマ連結 |
| 停止 | `POST /Edi/Stop?channels={outputs}` | 常に対象を明示する。デバイスを停止させる（7.4 E2） |
| 一時停止 | `POST /Edi/Pause?untilResume=true&channels={outputs}` | ゲームポーズ用 |
| 再開 | 現在状態から `Play` を再送 | 現在の `seek` を再計算する |
| 再走査 | `POST /Edi/Reload` | 現ギャラリールートの読み直し。ファイル転送を伴わない（7.4 E3）。`POST /Edi/Assets` は使用しない |
| 強度変更 | `POST /Edi/Intensity/{max}?channels={outputs}` | 使用しない。無動作は `Stop` で表現する |

MODは `channels` 指定を省略してはならない。省略するとEDI上の全チャンネルに作用するためである。

オーサリングGUIからの試聴も同じAPIと明示規約に従う。GUIがEDIへ直接要求を送ってはならない。

### 7.3 通信失敗

- HTTPタイムアウト、接続拒否、非成功ステータス、応答解析失敗を通信失敗として扱う。
- 通信失敗をUnity側へ例外として伝播させない。
- 同じdesired stateに対する無制限の即時再試行は禁止する。再接続確認はバックオフし、ログは障害状態の遷移時にまとめる。
- 再接続後は失敗中の全命令を再生せず、各出力の最新desired stateだけを送信する。
- `Play` の結果が不明な場合、同じ要求を直ちに重複送信しない。
- 再接続後は束縛を再検証してから出力を有効化する。EDIの再起動やデバイスの再接続で束縛が変わり得るためである。

### 7.4 EDI本体の改訂

本仕様はEDI本体の次の改訂を要求する。改訂範囲はここに列挙したものに限る。実装は表紙に記したソース正本に対して行い、ビルド成果物を `Edi/Edi.exe` へ配置する。

#### 7.4.1 既存挙動を変える改訂は設定で切り替える

E1、E2、E4はEDIの既存挙動を変更する。無条件に変更すると、同じEDIを使う他のゲーム構成が影響を受ける。したがってこれらは設定で切り替え可能とし、**既定値は現行挙動を維持する値**とする。本MODの構成でだけ有効化する。E3、E5、E6、E7は追加のみで既存挙動を変えないため、設定を持たない。

この方式が成立する根拠は、EDIの設定スコープにある。`EdiConfig` と `GalleryConfig` は `[GameConfig]` 属性を持ち、`ConfigurationManager` はこれらをゲーム側の `EdiConfig.json` から読み込む。`[UserConfig]` 属性を持つ設定だけが `%LocalAppData%\Edi\UserConfig.json` で共有される。つまり新しいフラグはゲームごとに独立し、本MODの `Edi/EdiConfig.json` で有効化しても他のゲーム構成の挙動は変わらない。

既存の単体テスト `PlayerGalleryFlowTests.ExplicitStopDuringReactionResumesMainGallery` と `NonLoopingGalleryReturnsToCurrentFiller` は現行の復帰挙動を明示的に検証している。既定値を維持することでこれらは変更なしに成立し、フラグ有効時の挙動は新規テストで検証する。

#### 7.4.3 能力ネゴシエーション

起動時の順序は次のとおりとする。前段が成立しない限り次へ進まない。

1. **EDIへの到達確認。** 応答が得られるまでバックオフ付きで再試行する。接続拒否、タイムアウト、名前解決失敗は「EDI未起動」であり、能力不足ではない。7.3の `Unavailable` として扱い、再試行を続ける。
2. **能力確認。** `GET /Edi/Info` を照会する。HTTPで応答が返った時点で判定し、再試行しない。
3. **束縛検証。** 7.1の手順を実行する。60秒の確認期間はこの段階の最初の `GET /Devices` 成功から起算する。

能力確認の判定は次のとおりとする。

| 観測 | 判定 | 動作 |
|---|---|---|
| `GET /Edi/Info` が404 | 7.4未適用のEDI | デバイス出力を有効化せず、必要なEDIの版と `POST /Edi/Reload` の不在を提示する |
| `StrictVariantResolution` が偽 | 誤配送が無警告になる | デバイス出力を有効化しない。FR-050が成立しない旨を提示する |
| `StopClearsFiller` が偽 | 停止が成立しない | デバイス出力を有効化しない。FR-019、FR-045が成立しない旨を提示する |
| `UnassignedDeviceChannel` が未設定 | 台帳外デバイスが台帳のチャンネルへ入り得る | 出力は有効化する。誤検知で出力が抑止され得る旨を警告として1回記録する。束縛検証（7.1）が実害を防ぐため、fail closedにはしない |
| 上記以外 | 能力充足 | 束縛検証へ進む |

不足がある場合は、不足している能力と、それが無い場合に成立しない要件のIDを名指しでログへ記録する（10.4）。

## 9. エラーと復旧

| 条件 | 動作 | 復旧 |
|---|---|---|
| EDI未起動・通信断 | `Unavailable` としてゲームを継続し、ログを集約 | EDI復帰後に束縛を再検証し、最新desired stateへ同期 |
| 出力の束縛が成立しない（デバイス未接続、チャンネル相違、バリアント相違、未準備） | 当該出力だけを `Suppressed` とし、不成立の条件を表示。他の出力は継続 | 確認期間内に成立すれば自動で有効化。期間経過後はEDI側の設定を修正してゲーム再起動 |
| 出力IDのチャンネルに台帳外のデバイスが所属 | 当該出力を `Suppressed` とし、混入デバイス名を表示 | EDIでデバイスのチャンネル割り当てを修正して再検証 |
| `schemaVersion` が非対応 | 出力を無効化し、検出した版と要求する版、移行手順の参照を表示 | 12.4の手順で移行 |
| マッピング構文不正、台帳の重複・欠落 | 出力を無効化し、ファイルと検証箇所を表示 | 設定修正後に再読込 |
| 重複トリガーキー | 出力を無効化する | 重複を解消して再読込 |
| 未登録トリガー | カタログへ追記し、再生しない | オーサリングGUIで作成・保存後、次回発生から再生 |
| 段階配列を列挙できない | 観測できた段階だけをカタログへ追記し、列挙不能の理由を記録 | 該当演出へ到達して観測を追加 |
| 段階の状態通知を購読できない | 理由を記録してAnimator観測へ縮退し、`stageId` を `default` としない | 購読可能なゲームビルドで再収集 |
| セッション書込失敗 | ゲームと既存再生は継続し、通常ログと可能ならJSONLへ欠番・未書込数を記録 | 書込可能になった新セッションで収集再開 |
| カタログ書込失敗 | 直前のカタログを保持し、失敗を記録。部分書き込みを残さない | 書込可能になった時点で再統合 |
| オーサリングGUIのポート使用中 | GUIを無効化し、ゲームとデバイス制御は継続。使用中ポートを表示 | ポート設定変更後に再起動 |
| `.funscript` 保存失敗またはEDIの再走査失敗 | `mappings.json` を更新せず、GUIとログへ理由を提示。未登録のまま再生しない | 原因解消後にGUIから再保存 |
| ループ長不一致 | 保存時に検証エラーを提示し、承認なしには保存しない | 波形を修正、または差異を承認して記録 |
| ギャラリー・バリアント欠落 | 対象アクションを再生せずエラー。EDIは代替バリアントへ退避しない | EDIアセット追加後に定義を再検証 |
| ギャラリーが対象外の出力へ指定されている | マッピング読み込み時に設定エラー。実行時に検出した場合は当該出力へ送らず警告 | バリアントを追加するか、`outputs` から外す |
| ゲームフック失敗 | 該当フックを無効化し、ゲームを継続 | 対応ゲームビルド用フックへ更新 |
| 古い非同期応答 | 保持中のトリガー同一性と一致しなければ破棄（4.3の性質2） | 最新desired stateを維持 |
| 7.4の設定が有効でないEDI | `StrictVariantResolution` または `StopClearsFiller` が無効ならデバイス出力を有効化しない。`UnassignedDeviceChannel` が未設定なら警告のみで継続。不足している能力と成立しない要件IDを提示 | `Edi/EdiConfig.json` を修正してEDIを再起動 |
| `GET /Edi/Info` が存在しない | 7.4未適用のEDIと判断し、デバイス出力を有効化せず、必要なEDIの版を提示 | 7.4を適用したEDIをビルドして配置 |
| EDIへ到達できない | `Unavailable` としてバックオフ再試行。能力不足として扱わない | EDI起動後に能力確認と束縛検証へ進む |
| 再走査要求の失敗 | ゲームと既存再生は継続し、警告を記録。新しいギャラリーはEDIが認識しないため再生されない | EDI復帰後に再走査を再要求 |

## 10. 非機能要件

### 10.1 性能

- ゲームフックからHTTP完了を待ってはならない。
- 同じ状態のポーリングごとにHTTP要求または同内容ログを生成してはならない。
- セッションログはトリガー遷移と変化したテキストだけを記録し、フレーム単位のレコードを出力してはならない。1回のゲームセッションのログ量が、演出の発生回数ではなくプレイ時間に比例して増大してはならない。
- 段階遷移の検出は、可能な場合ゲーム側の状態通知の購読で行い、毎フレームのAnimatorおよびTransform走査を行わない。
- 収集ワーカーには設定可能な上限を設ける。上限到達時はゲームをブロックせず収集を停止し、破棄範囲と件数を明示する。
- オーサリングGUIの要求処理がゲームのフレーム処理を遅延させてはならない。
- 性能試験では、EDIの応答遅延中およびGUI操作中もゲームの更新が停止しないことを確認する。

### 10.2 安全性とセキュリティ

- EDI接続はループバックに限定する。
- オーサリングGUIの待ち受けもループバックに限定する。GUIは認証を持たないため、ループバック限定が唯一の到達制御である。
- MODは秘密情報、個人情報、ゲーム外の入力内容を送信しない。
- ログはテレメトリとして外部送信せず、ローカルに保存する。
- 無効な設定や未登録トリガーではfail closedとし、デバイスを推測動作させない。
- MODは波形を推測生成しない。再生されるのはユーザーが作成し保存した `.funscript` だけである。
- ゲーム終了時のStopはbest effortであり、最終的な物理停止機能はEDIおよびデバイス側にも必要である。

### 10.3 互換性と保守性

- 対応ゲームビルドをマッピングファイルまたは同梱メタデータに記録する。
- 異なるゲームビルドを検出した場合は警告し、網羅性確認なしに「対応済み」と表示してはならない。
- トリガーカタログはビルド別に分離し、ビルド間で自動的に流用しない。
- EDI API呼び出し、ゲームフック、マッピング解決、状態調停、オーサリングサーバを別コンポーネントとしてテスト可能にする。
- ファイル形式には `schemaVersion` を持たせ、未知のメジャー版は読み込まない。

### 10.4 可観測性

- ログレベルごとに、起動情報、マッピング検証、束縛検証、状態遷移、通信障害、未知識別子、GUI操作を区別する。
- 状態遷移のログは出力IDを含み、`Silent` と `Inactive` と `Suppressed` を区別できる形式とする。「デバイスが動いていない」理由をログだけで判別できなければならない。
- 束縛検証の結果は、出力ごとに期待値と実測値の両方を記録する。抑止した出力については、不成立だった条件を明示する。
- 起動ログに、`GET /Edi/Info` が返したEDIの版と、7.4のフラグの実効値を記録する。不足がある場合は、成立しなくなる要件のIDを添える。
- 通常ログは状態変化だけを記録し、毎フレーム出力しない。
- セッション収集は常時有効とする。フレーム単位のデータは収集しない。
- 各セッションの遷移件数、カタログ追加件数、欠番、書込高水位、GUIからの保存成否と出力パスを終了時に要約する。

## 12. リポジトリ成果物と運用

### 12.1 リポジトリ常備成果物

- BepInEx IL2CPPプラグイン。
- オーサリングGUIの静的アセット。
- 対応ゲームビルドを明記したマッピングファイル。
- ビルド・セッション別の追記専用JSONL、ビルド別トリガーカタログ、派生網羅性レポート、保存マニフェスト。
- EDI用ギャラリー定義（`Definitions.csv`）、同梱 `.funscript`、オーサリングGUIで作成した `.funscript` 一式。
- 台帳の既定3出力に対応するEDI設定例。デバイス名、チャンネル、バリアントの対応と、7.4の設定（`StrictVariantResolution`、`StopClearsFiller`、`UnassignedDeviceChannel`）を含む。
- 7.4の改訂を適用したEDIのビルド成果物と、そのSHA-256。
- EDI起動順、Intiface Central接続、GUI利用手順、ログ採取、無効化手順。
- ハードウェアあり・なし両方の受け入れ試験記録。

### 12.2 導入順序

1. 7.4の改訂を適用したEDIをビルドし、`Edi/Edi.exe` へ配置する。SHA-256をリポジトリ文書へ記録する。
2. `Edi/EdiConfig.json` に7.4の設定（`StrictVariantResolution`、`StopClearsFiller`、`UnassignedDeviceChannel`）を追加して有効化する。`UnassignedDeviceChannel` の値は `Channels` にも加える。他のゲーム構成の `EdiConfig.json` には追加しない。
3. 対応するBepInEx IL2CPPをゲームへ導入する。
4. MODプラグインとマッピングファイルを所定位置へ配置する。
5. EDIへギャラリーと `Definitions.csv` を配置する。対象外バリアントのファイルを置かない。
6. EDIで台帳の各出力IDと同名のチャンネルを作成し、台帳が指名するデバイスへ、そのチャンネルとバリアントを1対1で割り当てる。1つのチャンネルに複数デバイスを所属させない。`EdiConfig.json` の `Channels` を編集した場合は、EDIでギャラリーフォルダを選択し直す。EDIがチャンネル集合を作るのはゲーム選択時だけで、再起動では保存済みの選択が復元されるだけであり、再走査（7.4 E3）もチャンネルを再構成しない。
7. Intiface Central、EDI、ゲームの順に起動する。
8. 起動ログで、7.4のフラグが全て有効であること、および全出力の束縛が成立したことを確認する。不足があれば該当箇所を修正して再起動する。
9. ギャラリーと通常プレイを一巡してトリガーカタログを蓄積する。
10. オーサリングGUIをブラウザで開き、段階ごとに `.funscript` を作成・試聴・保存する。
11. 診断ログとEDI定義検証を確認してからデバイスあり試験を行う。

### 12.3 ロールバック

MODプラグインと同梱設定を無効化または除去すれば、ゲーム本体はEDI連動なしで起動できなければならない。セーブデータおよびゲームアセットを変更する方式は禁止する。

7.4の改訂は2段階で差し戻せる。

1. **設定の無効化。** `Edi/EdiConfig.json` の `StrictVariantResolution` と `StopClearsFiller` を `false` にし、`UnassignedDeviceChannel` を外すと、EDIは改訂前と同じ挙動に戻る。バイナリの差し替えは不要である。この状態ではMODが7.4.3によりデバイス出力を有効化しないため、ゲームはEDI連動なしで進行する。
2. **バイナリの差し戻し。** 改訂前のEDIバイナリ（表紙のSHA-256）は保管し、改訂そのものに問題が生じた場合に差し戻せるようにする。この状態では `GET /Edi/Info` が404を返し、MODは7.4未適用と判定する。

いずれの場合もゲーム本体とセーブデータへの影響はない。

### 12.4 移行

`schemaVersion` 1 のマッピングファイルは読み込まない。次の手順で手動移行する。

順序には理由がある。静止アセットの削除は、`StrictVariantResolution` を有効化したあとに行う。順序を逆にすると、その間だけ誤配送が代替バリアントの再生として現れ、移行作業中に別デバイスの波形が実機で動く。

1. 7.4を適用したEDIを配置し、`Edi/EdiConfig.json` へ `StrictVariantResolution`、`StopClearsFiller`、`UnassignedDeviceChannel` を追加して有効化する。`UnassignedDeviceChannel` の値を `Channels` にも加える。
2. EDIのデバイス設定を12.2の手順6へ更新する。出力IDごとのチャンネルを作り、デバイスを1対1で割り当てる。
3. `mappings.json` に `outputs` 台帳を追加する。既定は4.2の3出力。
4. `defaultFillers` のキーを出力IDへ置き換える。旧 `breast` の値は `breast-left` と `breast-right` の両方へ複写する。
5. `events[].gallery` と `events[].channels` を `events[].outputs` へ変換する。旧 `main` は `{ "id": "main", "gallery": 旧gallery }`、旧 `breast` は `breast-left` と `breast-right` の2要素へ展開する。
6. `statusRules[].channel` と `statusRules[].fillerGallery` を `statusRules[].outputs` へ変換する。旧 `breast` は2要素へ展開する。
7. `Definitions.csv` の全エントリの `Type` を `gallery` にする。`Loop` は変更しない。
8. `schemaVersion` を `2` にする。
9. 対象外バリアントの静止アセット（`a10-main/filler-breast.funscript`、`a10-main/filler-breast-swollen.funscript`、`ufo-left/filler-main.funscript`、`ufo-left/filler-main-parasite.funscript`、`ufo-right/filler-main.funscript`、`ufo-right/filler-main-parasite.funscript`）を削除する。
10. MODを起動し、能力確認の通過、全出力の束縛成立、AC-045（静止波形の不在）を確認する。

## 14. 前提、延期事項、残存リスク

### 14.1 明示的な前提

- A10ピストンSAはEDI上でピストン対応デバイスとして認識される。
- U.F.O TWの左右要素はEDI上で別デバイスまたは別アクチュエータとして、異なるチャンネルと異なるバリアントを割り当てられる。
- EDIが `GET /Devices` で返すデバイス名は、同一構成の再接続をまたいで安定している。名前が一意化などで変化した場合は束縛検証が不成立を報告する。
- 配置する `Edi/Edi.exe` は表紙のソース正本からビルドされ、7.4の改訂を含む。
- 対象トリガーのアニメーション識別子、再生位置、クリップ長、ループ可否をBepInEx IL2CPPから安定して観測できる。
- ギャラリーの段階配列をゲーム側から列挙できる。実機で未確認であり、列挙できない場合は観測による追記へ縮退する。
- 拘束シーケンスの段階遷移をゲーム側の状態通知として購読できる。実機で未確認であり、購読できない場合はAnimator観測へ縮退する。
- `膨乳` のゲーム内識別子は常時収集で一意に取得できる。
- ユーザーは対象段階に対して `.funscript` を作成する意思と時間を持つ。

### 14.2 延期事項

- 左右で異なるギャラリー名を指定した場合の同時開始保証。
- 波形の自動生成および自動補完。
- ゲーム内UIおよびホットキー。
- 他デバイスの正式サポート。
- リモートEDI接続。
- 複数ユーザー間での `.funscript` 共有配布フロー。
