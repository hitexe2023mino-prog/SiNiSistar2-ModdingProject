## 1. 概要

### 1.1 背景と問題

[SPEC003](SPEC003.md) は堕落と絶頂回数を、[SPEC005](SPEC005.md) は淫紋の段階進行を、いずれも `community.sinisistar2.pleasure` の随伴ファイルとプラグイン内部状態としてのみ保持している。これらの値はゲーム内UI・ログ・随伴ファイルの生JSONを介してしか確認できず、プレイ中にプレイヤーが自分の堕落や絶頂回数の推移を眺める手段がない。

[SPEC001](SPEC001.md) はすでに、ゲームを起動したままブラウザで閲覧・操作できるループバック限定のローカルHTTP GUI（funscriptオーサリングGUI）を実装しており、本仕様が必要とする「ゲーム外ブラウザで動くGUIをMODから配信する」という構成要素の先例と実装パターンをすでに持つ。

加えて、「どの敵に最も絶頂させられたか」「どのデバフを何回受けたか」という内訳は、現在どの仕様にも存在しない新しい集計軸である。プラグインは状態異常の付与経路（`AbnormalList.AddAbnormal`）と拘束相手の敵識別子の解決を既に観測・実装しているため（SPEC003 FR-244、5.3.1）、新しい観測点を追加せずに内訳を積み上げられる（2.3、付録A参照）。

### 1.2 目的

- プレイ中のセーブデータについて、堕落・絶頂回数を含む統計情報をブラウザで閲覧できるようにする。
- 絶頂回数（現在値）に加えて、セーブデータ内で最も多く絶頂させた敵（アクター）の名前を表示する。
- 受けたデバフ（状態異常）の回数を、種類ごとに表示する。
- ページを開いたままプレイする用途を想定し、ポーリングによって表示を追随させる。
- 統計情報のうちセーブデータへ永続化すべき値は、随伴ファイルへ保存し、セーブ・ロードをまたいで保持する。
- 画面デザインは中世ファンタジーの日記帳をモチーフにする。
- 既存のMOD間非依存方針（SPEC001 4.1、SPEC003 4.1、SPEC005 2.3）を維持し、新規プラグインを追加しない。

### 1.3 成功条件

1. `community.sinisistar2.pleasure` が動作している間、ループバック限定のHTTPで統計画面が配信され、ブラウザで閲覧できる。
2. 画面に、堕落の現在値と上限、絶頂回数の現在値（および設定されていれば絶頂限界）が表示される。
3. 画面に、そのセーブデータでこれまでに1回でも絶頂させた敵がいる場合、最も絶頂させた回数が多い敵の表示名が表示される。1件も絶頂していない場合はその旨が示される。
4. 画面に、受けたデバフの回数が種類ごとに表示される。
5. ゲームをプレイしながらページを開いていると、堕落・絶頂回数・デバフ内訳・最多絶頂アクターの表示が、ポーリングにより数秒程度の遅延で更新される。
6. 堕落・絶頂回数（現在値）は既存どおりSPEC003の規則で保存・復元される。アクター別絶頂内訳とデバフ種別回数は随伴ファイルに保存され、セーブデータのロード後に保存時点の値へ復元される。
7. 画面のデザインが中世ファンタジーの日記帳を基調とした配色・書体で構成されている。
8. 統計画面はゲーム本体の進行やフレーム処理を妨げない。HTTPサーバーの待受失敗時もMOD本体の機能（堕落・絶頂の計算）は継続する。
9. 統計画面はゲーム状態を変更する操作を一切提供しない（読み取り専用）。
10. SPEC001・SPEC002・SPEC004・SPEC005 が同時に動作している状態で、いずれの動作も停止しない。

## 2. スコープ

### 2.1 対象

- `community.sinisistar2.pleasure` への機能追加として実装する統計集計とHTTP配信。
- アクター別絶頂回数の集計と、随伴ファイルへの永続化（新規フィールド）。
- デバフ種別回数の集計と、随伴ファイルへの永続化（新規フィールド）。
- 随伴ファイルのスキーマ更新（`schemaVersion` 5 → 6）。
- ループバック限定のローカルHTTPで配信する読み取り専用の統計画面（HTML/CSS/JS、外部CDN不使用）。
- ポーリングによる準リアルタイム更新。
- ゲーム内のキー操作による、既定ブラウザでの統計画面の起動（表示先はゲーム外ブラウザのまま。5.5、DEC-608）。
- BepInEx `ConfigEntry` による統計サーバーのアドレス・ポート・有効無効・起動キーの設定。
- 統計サーバーの待受失敗時の安全な縮退（統計機能だけを無効化し、MOD本体は継続）。

### 2.2 非対象

- 新規BepInExプラグインの追加。実装先は既存の `community.sinisistar2.pleasure` に限る（DEC-601）。
- 統計画面からのゲーム状態の変更・操作。読み取り専用であり、SPEC001オーサリングGUIのような試聴・保存・再走査要求は提供しない。
- SPEC001・SPEC002・SPEC004由来の統計（EDI出力状態、難易度介入回数、出現敵の分布など）の集計・表示。将来の拡張候補として12章に記録するが、本仕様の対象外とする。
- 堕落・絶頂回数・淫紋段階など、SPEC003・SPEC005が定義する値そのものの計算規則・増減規則・上限・致死化条件の変更。
- ゲーム内UI・設定画面・オーバーレイとしての統計の**描画**。統計画面はSPEC001と同様にゲーム外ブラウザで動作する。ゲーム内キーで行えるのはそのブラウザを**開くこと**だけであり、ゲーム内には何も描かない（DEC-608）。
- 過去の推移をたどれる時系列グラフ・履歴チャート。表示するのは現在の集計値のみ。
- 本MOD導入前に書かれたセーブ・随伴ファイルへの遡及集計。新規カウンターは本仕様導入後の発生分から積み上げる。
- ゲームのセーブデータファイル、`GameAssembly.dll`、`global-metadata.dat`、ゲームアセットの書き換え。
- リモート端末からの統計画面の利用。SPEC001 2.2と同じ理由でループバックに限る。

### 2.3 前提と制約

- `community.sinisistar2.pleasure` は既に `AbnormalList.AddAbnormal`（2オーバーロード）と `AddOrRemoveAbnormal` をパッチ済みであり（SPEC003 FR-244 の観測経路）、状態異常が**実際に付与された**瞬間を、付与元（被弾・アイテム・イベント）を問わず観測できる。同一フレーム内の重複報告を1回へ畳む機構も既存である。デバフ種別回数の集計はこの既存の観測点を再利用し、新しいHarmonyパッチを追加しない。
- `DamageManager.OneDamage` で読める `DamageParameter.m_AbnormalTypes` は攻撃が付与を**宣言した**種別であり、実際に付与されたかどうかとは一致しない（付与確率があり、SPEC002 はその確率を操作する）。本仕様のデバフ種別回数はこの宣言値を集計に用いない（DEC-606）。
- 敵の識別は SPEC003 5.3.1 が定める敵識別子の解決順序（拘束相手からの解決）をそのまま用いる。識別子が `None`（未解決）の場合は敵を名指しできないため、アクター別内訳では「不明」として別枠に集計し、「最も絶頂させたアクター」の判定対象には含めない（FR-604）。
- 敵の表示名は `SiNiSistar2.Pleasure.Plugin.BinderIdentity` が用いる `LocalizeManager.GetLcText` 経路（`DisplayEnemyNameID`）で解決する。ローカライズが取得できない場合は敵識別子の生値を表示名として使う。
- 随伴ファイル（`SidecarDocument`、現行スキーマ5）はセーブスロット単位で堕落・絶頂回数などを保持する（SPEC003 5.9）。本仕様が追加するアクター別絶頂回数とデバフ種別回数も同じ随伴ファイルに同じ粒度（セーブスロット単位）で保存する。
- HTTP配信は SPEC001 の `AuthoringServer`（`HttpListener`、ループバック限定、FR-035相当の検証）と同じ設計パターンを踏襲する。ソースコードとしては独立実装とし、`Edi.Core` への参照は追加しない（MOD間非依存方針、SPEC001 4.1）。
- SPEC001のオーサリングGUIはHTTPポーリング（ライブ判定窓 約3秒、`LivePollWindow`）でリアルタイム性を実現しており、本仕様もプッシュ配信（WebSocket/SSE）を新規導入せず同じポーリング方式を踏襲する。
- 統計画面はゲーム実行中かつプラグイン読み込み中だけ到達可能である。ゲーム未起動時にURLへアクセスした場合の応答はSPEC001と同様（接続不可）でよい。

## 3. 用語

SPEC003・SPEC005の用語（堕落、絶頂、絶頂回数、絶頂限界、随伴ファイル、敵識別子、表示名）をそのまま用いる。本仕様の追加用語は次のとおり。

| 用語 | 定義 |
|---|---|
| プレイ統計画面 | 本MODがループバック限定のローカルHTTPで配信する、読み取り専用の統計閲覧画面。 |
| アクター別絶頂回数 | セーブデータ単位で、敵識別子ごとに積み上げた絶頂回数の生涯累計。絶頂回数（SPEC003、セーブポイントでリセットされる現在値）とは別の値である（4.4、DEC-602）。 |
| デバフ種別回数 | セーブデータ単位で、プレイヤーへ付与された状態異常（`AbnormalType`）の種類ごとに積み上げた生涯累計。 |
| 生涯累計 | セーブデータが存在する限り減少しない積算値。堕落と同じ性質を持つ（4.4、DEC-602）。 |
| 統計スナップショット | 統計画面がポーリングごとに取得する、その時点の集計値一式。 |

## 4. 設計

### 4.1 全体構成

```
BepInEx (IL2CPP)
  └ community.sinisistar2.pleasure
      ├ PleasurePlugin (BasePlugin)          既存 + 統計サーバーの起動・停止を追加
      ├ Harmonyパッチ群                      既存（新規パッチは追加しない）
      ├ PleasureOverlay (MonoBehaviour)      既存（インゲーム演出。本仕様は変更しない）
      ├ StatsServer (新規)                    ループバック限定HTTPで統計画面とAPIを配信
      ├ StatsPageLauncher (新規)              ゲーム内キーで既定ブラウザに統計画面を開く
      └ SiNiSistar2.Pleasure.Core
          ├ SidecarDocument                  既存（schemaVersion 6へ拡張）
          ├ ClimaxLedger / CorruptionTrack   既存（変更なし）
          ├ ActorClimaxLedger (新規)          敵識別子ごとの絶頂回数を生涯累計で保持
          ├ DebuffCounters (新規)             AbnormalTypeごとの回数を生涯累計で保持
          └ StatsSnapshot (新規)              統計画面へ返す集計結果の組み立て
```

`ActorClimaxLedger` と `DebuffCounters` は `ClimaxLedger`・`CorruptionTrack` と同じ層（ゲーム参照なしの `Core`）に置き、時刻や乱数に依存しない純粋な集計として単体テストの対象にする。ゲーム値の取得と表示名解決は `Plugin` 側（`PleasurePlugin`、既存の `BinderIdentity`）が担う。

### 4.2 集計の流れ

```
状態異常の付与成立（AbnormalList.AddAbnormal / AddOrRemoveAbnormal、既存のパッチ）
  └─ 新規: プレイヤーへ実際に付与された AbnormalType の種別ごとに
             DebuffCounters に +1（同一フレーム内の重複報告は既存機構で1回に畳む）
             付与元（被弾・アイテム・イベント）は問わない

被弾解決（OneDamage、既存の観測点）
  └─ 既存: 性的/非性的判定 → 快楽・堕落・HP無効化（SPEC003、変更なし）
             ※デバフ種別回数の集計には用いない（宣言値であるため。2.3、DEC-606）

絶頂成立（既存の ClimaxLedger.Record() 呼び出し地点、SPEC003）
  ├─ 既存: ClimaxLedger.Count +1、堕落 +増分、演出（変更なし）
  └─ 新規: その時点で解決済みの敵識別子について ActorClimaxLedger に +1
             敵識別子が None の場合は「不明」枠に +1 し、最多アクター判定からは除外する
```

デバフ種別回数は、快楽の上昇要因かどうか（性的/非性的）を問わず、また付与元が被弾・アイテム・イベントのいずれであるかを問わず、プレイヤーへ**実際に付与された** `AbnormalType` を種別として数える（DEC-606）。攻撃が宣言したが抵抗判定などで付与に至らなかった種別は数えない。同一の付与イベントが複数経路から重複報告された場合は、既存のフレーム単位の畳み込みにより1回として数える（DEC-603）。

### 4.3 永続化

`SidecarDocument` を schemaVersion 6 へ拡張し、次のフィールドを追加する。

| フィールド | 型 | 内容 |
|---|---|---|
| `actorClimaxCounts` | `{ actorId: string, count: int }[]` | アクター別絶頂回数の生涯累計。`actorId` が敵識別子。未解決分は予約識別子 `"unknown"` に集計する |
| `debuffCounts` | `{ abnormalType: string, count: int, displayName?: string }[]` | デバフ種別回数の生涯累計。`abnormalType` は `AbnormalType` 列挙子名。`displayName` は付与時に捕捉したゲーム側の表記名（4.6.1）。省略可 |

読み込みは既存の後方互換規則（SPEC003 5.9、`SidecarDocument.Parse`）に従う。schemaVersion 5以前のファイルはこれらのフィールドを持たないため、空配列として扱い、そこから積み上げを開始する。schemaVersion 6のファイルを、本仕様導入前のMODで読み込んだ場合は既存の規則により拒否される（`SchemaVersion > CurrentSchemaVersion`）。これは新規リスクではなく、随伴ファイルのスキーマ管理が既に持つ挙動である（12章）。

アクター別絶頂回数とデバフ種別回数は、堕落と同じく**セーブポイントのアクティベートでもリセットしない**（DEC-602）。絶頂回数（`ClimaxLedger.Count`）はSPEC003どおりリセットされる現在値のままとし、アクター別絶頂回数の合計値と絶頂回数（現在値）は一致しないことがある。これは意図した挙動であり、統計画面は両者を別の指標として並べて表示する（4.5）。

### 4.4 集計値の意味の分離

| 値 | リセット | 保存 | 出典 |
|---|---|---|---|
| 絶頂回数（現在値） | セーブポイントでリセット（SPEC003） | する | 既存 `ClimaxLedger` |
| アクター別絶頂回数 | しない（生涯累計） | する（新規） | 新規 `ActorClimaxLedger` |
| デバフ種別回数 | しない（生涯累計） | する（新規） | 新規 `DebuffCounters` |
| 堕落 | しない（生涯累計） | する（既存） | 既存 `CorruptionTrack` |

### 4.5 HTTP API

`StatsServer` は SPEC001 `AuthoringServer` と同じ制約（ループバック限定、`http` スキームのみ、FR-035相当の検証）で次のエンドポイントを配信する。

| メソッド/パス | 内容 |
|---|---|
| `GET /` | 統計画面本体（自己完結のHTML。CSS/JSはインライン、外部CDNへは接続しない） |
| `GET /api/stats` | 統計スナップショットのJSON |

`GET /api/stats` のレスポンス例（値は例）。

```json
{
  "corruption": { "value": 42.5, "cap": 100 },
  "climax": { "count": 3, "limit": 12 },
  "topActor": { "actorId": "enemy.worm_large", "displayName": "大口のワーム", "count": 7 },
  "actorClimaxCounts": [
    { "actorId": "enemy.worm_large", "displayName": "大口のワーム", "count": 7 },
    { "actorId": "unknown", "displayName": null, "count": 1 }
  ],
  "debuffCounts": [
    { "abnormalType": "Breast", "displayName": "膨乳", "count": 15 },
    { "abnormalType": "Parasite", "displayName": "寄生", "count": 4 }
  ],
  "generatedAt": "2026-08-10T12:34:56Z"
}
```

`topActor` は `actorClimaxCounts` から `actorId != "unknown"` の要素のうち `count` が最大の1件を選ぶ。1件もない場合は `null` とし、画面側は「まだ絶頂させた敵がいません」のように表示する。同数首位が複数ある場合は `actorId` の文字列順で先頭のものを選ぶ（決定的な表示のための取り決めであり、ゲーム的な意味は持たない、DEC-604）。

統計画面のJSは `GET /api/stats` を数秒間隔（既定3秒、SPEC001の `LivePollWindow` と同じ考え方）でポーリングし、値が変化した箇所だけ更新する。プッシュ配信は導入しない（4.3節の前提）。

### 4.5.1 ゲーム内からの起動

統計画面はゲーム外ブラウザで動作するため、URLへ到達する手段が必要になる。起動ログのURLを手で打ち込むことは、統計を見たくなる瞬間（新しい敵に絶頂させられた直後、ゲームが前面にある状態）の導線として成立しない。

SPEC001 は同じ問題を `AuthoringGuiLauncher`（FR-061）で既に解いている。設定可能なキー名を `UnityEngine.KeyCode` として解釈し、IMGUIのKeyDownイベントで受け、`Process.Start(url) { UseShellExecute = true }` で既定ブラウザへ渡す。本仕様はこの構成をそのまま踏襲する。ソースは独立実装とし、`Edi.Plugin` を参照しない（MOD間非依存、2.3）。

ゲーム内には何も描かない。キーが行うのはブラウザを開くことだけであり、統計の描画先はブラウザのままである（DEC-608）。

キーの既定値は `F1` とする。同一ゲームフォルダの各MODは1つのキーボードを調停なしに共有しており、既定値が衝突すると後から押された機能が「壊れている」ように見える。本仕様策定時点の割り当ては次のとおりで、空いている機能キーは `F1` だけである。

| キー | 使用者 |
|---|---|
| `F2`, `F4`, `F7`〜`F11` | 本MOD（SPEC003/SPEC005 のデバッグ画面・操作） |
| `F3`, `F5` | SPEC004 敵ランダム出現MOD（デバッグパネル、HUD） |
| `F6` | SPEC001 EDI連動MOD（オーサリングGUI起動、FR-061） |
| `F12` | Steam スクリーンショット |

この割り当ては将来変わり得るため、既定値の衝突は自動テストで検出する（AC-616）。

### 4.6 デザイン

中世ファンタジーの日記帳をモチーフとする。羊皮紙調の背景、インクを思わせる見出し・罫線、手書き風または装飾的なセリフ体を用いる。フォント・画像は自己完結（Base64埋め込みまたは同梱ファイル）とし、外部CDN・Webフォントへは接続しない（オフライン動作前提、SPEC001と同じ制約を踏襲）。テーマは固定の1種とし、ライト/ダークの自動切り替えは対象外とする（単一ユーザーのローカル閲覧であり、ゲーム外ブラウザのテーマ設定と独立している）。

画面の見出し・ラベルは日本語固定とする。敵の表示名とデバフの表示名は、ゲームのローカライズ（`LocalizeManager.GetLcText`）から取得してゲームの言語設定に従い、取得できない場合は識別子・列挙子名の生値で代替する（DEC-607）。デバフ名の取得経路は4.6.1に定める。

#### 4.6.1 デバフ表示名の取得経路

デバフの表示名を `AbnormalType` の列挙子名から導出してはならない。対象ビルドの実測（A-603、2026-08-10）により、ゲームのローカライズキーは列挙子名と機械的に対応しないことが確定している。

- 71 個の `AbnormalType` のうち、`ID_Ab_<列挙子名>` が完全一致で存在するのは 37 個だけである。
- 残り 34 個のうち、キーの綴りは少なくとも3系統に分かれる。`Parasite` → `ID_Ab_ParasiteLv1`（区切りなし）、`LustMarkCurse` → `ID_Ab_LustMarkCurse_Lv1`（アンダースコア）、`Spore` → `ID_Ab_Spore1`（`Lv` を持たない）。
- `Lustfull`、`MindControl`、`WetNurse`、`MotherBody`、`Assimilation`、`Mutation` などは `ID_Ab_*` キーを一切持たない。
- `ParasiteLv13` は `Parasite` のレベル13ではなく独立した `AbnormalType` である。名前からレベルを推定してはならない。
- 表示名はレベル依存である。したがって「型に対する名前」は原理的に一意に定まらない。

正本は、付与された状態異常が保持する `AbnormalData.AbnormalNameID`（`LocalizeID`）である。これはゲーム自身が表示に用いる値であり、レベルを織り込んでいる。ただし**対象に付与されている間しか読めない**（未装着のテンプレートは `None` を返す。SPEC003 付録A A-28）。

したがって取得は次の順で行う。

1. **付与時に捕捉する。** 既存の `AbnormalList.AddAbnormal` postfix（集計と同じ観測点、4.2）で `GetAbnormalData(type).AbnormalNameID` を解決し、回数とともに保持・永続化する。レベル付き状態異常では最後に捕捉した名前を採用する（プレイヤーが直近に見た表記であるため）。
2. **完全一致キーによる補完。** 捕捉済みの名前がない種別についてのみ、`ID_Ab_<列挙子名>` がそのまま存在する場合に限り解決する。綴りの推測は行わない。これは名前保存前に書かれたサイドカーから復元した場合の救済である。
3. **いずれも得られない場合は列挙子名の生値**を表示する（FR-613）。

| 論点 | 採用 | 採用しなかった案 | 理由 |

## 6. データとインターフェース

- **データモデル**: `SidecarDocument`（schemaVersion 6）に `actorClimaxCounts: {actorId, count}[]`、`debuffCounts: {abnormalType, count}[]` を追加する。両配列とも `count` は非負整数、キー（`actorId` / `abnormalType`）はファイル内で一意。
- **ライフサイクル**: セーブロード時に随伴ファイルから復元、セーブ時に随伴ファイルへ原子的に書き込む（既存の `OnAfterLoadMainSaveData` / `OnAfterSaveMainSaveData` 経路、SPEC003 4.4を踏襲）。プレイ中の増分はメモリ上の `ActorClimaxLedger` / `DebuffCounters` に保持し、次回セーブ時に書き出す。
- **API**: `GET /api/stats` がJSONスナップショットを返す（4.5）。書き込み系エンドポイントは存在しない。
- **画面**: `GET /` が自己完結HTML/CSS/JSを返す。外部依存なし。
- **移行**: schemaVersion 5→6は既存の後方互換規則（新フィールドは欠落時に空扱い）に従う。マイグレーションスクリプトは不要。

## 7. エラーと復旧

| 失敗条件 | 提示・挙動 |
|---|---|
| 統計サーバーのポート待受に失敗（ポート競合等） | 起動ログに警告を記録し、統計サーバーを無効化する。MOD本体（堕落・絶頂計算）は継続する（FR-611）。起動キーは何も開かず、理由を記録する（FR-615） |
| ブラウザの起動に失敗（既定ブラウザ未設定等） | 警告を1行記録するだけとし、ゲームを妨げない。URLは配信され続けており、手動で開ける（FR-615） |
| 起動キーの設定名が `KeyCode` として解釈できない | 警告を記録し、キーを無効として扱う。黙って無効化すると「機能が壊れている」と読めるため理由を示す（FR-616） |
| 敵の表示名がローカライズから取得できない | 敵識別子の生値をそのまま表示名として使う（2.3） |
| ゲーム未起動時にブラウザからアクセスされた | 接続不可（SPEC001と同様、特別なフォールバックページは持たない） |
| 随伴ファイルのスキーマが本MODより新しい | 既存規則どおり読み込まず上書きもしない（SPEC003 5.9、FR-225） |
| ポーリング中にAPIが一時的に応答しない | 画面は直前のスナップショットを表示したまま次回ポーリングを待つ。エラーで画面をクリアしない |

## 8. 非機能要件

- **性能**: 集計はO(1)のカウンタ加算であり、被弾処理・絶頂処理のフレーム時間に計測可能な影響を与えない。
- **可用性**: 統計サーバーはプラグイン読み込み中のみ稼働する。停止・再起動はゲームのMOD有効化/無効化に連動する。
- **セキュリティ**: SPEC001と同じ信頼モデル（ループバック限定、認証なし）。ループバック以外からの到達は設定エラーとして拒否する（FR-606）。
- **互換性**: SPEC001・SPEC002・SPEC004・SPEC005と同一ゲームルートで共存する。他MODのHTTPサーバー（SPEC001オーサリングGUI）とはポートを分離する。
- **可観測性**: 統計サーバーの起動・停止・待受失敗をログへ記録する。

## 10. リリースと運用

- `community.sinisistar2.pleasure` の通常のリリースサイクルに含めて配布する。専用のロールアウト手順は不要。
- 統計サーバーは既定で有効とし、`ConfigEntry` で無効化できる。無効化した場合はSPEC003・SPEC005の既存挙動のみが残る。
- ロールバック（MODのダウングレード）を行う場合、schemaVersion 6で書かれた随伴ファイルは旧バージョンのMODから読み込めない（既存のスキーマ管理規則どおり）。ダウングレード手順は12章に記載する。
- 監視・アラートは既存のBepInExログ運用に準じる。専用の監視は設けない。

## 12. 前提・延期事項・リスク

**承認済みの前提**

- デバフ種別回数は性的/非性的を問わず、プレイヤーへ**実際に付与された**全 `AbnormalType` を対象とし、付与元も問わない（4.7、DEC-606、利用者決定 2026-08-10）。
- 画面の見出しは日本語固定、敵名・デバフ名はゲームのローカライズに従う（DEC-607、利用者決定 2026-08-10）。
- 敵識別子が解決できない絶頂は「不明」枠に集計し、最多アクター判定から除外する（FR-604）。
- 統計画面は単一テーマ（中世ファンタジーの日記帳）のみを提供し、ブラウザのライト/ダーク設定には追随しない（4.6）。
- 統計サーバーの既定アドレス `http://127.0.0.1:5602/` は検証前の暫定値であり、A-602 の実測で確定する（FR-610）。

**延期事項**

- SPEC001・SPEC002・SPEC004由来の統計（EDI再生状況、難易度介入回数、出現分布など）の表示。必要になった場合は本仕様のAPIを拡張するか、別途仕様化する。
- 統計の時系列グラフ・履歴表示。
- 統計データのエクスポート機能。

**残存リスクと軽減策**

- schemaVersion 6の随伴ファイルは、本仕様導入前のMODバージョンへダウングレードすると読み込まれなくなる。これは随伴ファイルのスキーマ管理が既に持つ挙動（SPEC003 5.9）であり、本仕様固有の新しいリスクではないが、リリースノートで明示する。
- 敵識別子の解決に失敗するケース（SPEC003付録A記載の実測事項）がある場合、「不明」枠に集計が偏り、アクター別内訳の実用性が下がる可能性がある。実測（付録A）で発生頻度を確認し、必要なら識別子解決の改善はSPEC003側の課題として切り出す。
