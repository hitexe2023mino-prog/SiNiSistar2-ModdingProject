# 変更履歴

このリポジトリが抱える4つのMODの版を記録する。ゲーム同梱の `changelog.txt` は BepInEx のものであり、本書とは無関係である。

版はMOD単位で進む。各MODは互いに独立して動作し、片方だけを更新できることが利点だからである（SPEC001 の EDI連動MODとの互換維持は開発の前提でもある）。タグも `<mod>-v<version>` の形でMOD単位に付ける。

## community.sinisistar2.pleasure

### 1.2.1 — 2026-08-09

堕落が敗北・リトライ後も残る不具合と、別のセーブデータへ横断する不具合を修正した（SPEC003 A-55、FR-284）。

**原因**

原因はどちらも同じ1行である。未知の鍵（随伴ファイルの無いスロット）へ来たとき、進行中の run を無条件に引き継いでいた。これは「新しいファイルへ保存した」場合を救うための判断（A-44）だったが、未知の鍵へ到達する経路は他にもある。

- **別のセーブを読み込んだ**とき — 他の周回の堕落を継いでしまう
- **敗北から復帰した**とき — 死んでも堕落が残る

当時のログは引き継いでいるのに `no sidecar yet, starting from zero` と書いており、挙動と記述が食い違っていた。

**修正**

判定に必要なのは「鍵を知っているか」ではなく「どうやってそこへ来たか」である。3つの事実から決める純粋関数 `SlotTransition.Decide` をコアへ置いた。

- 随伴ファイルがあれば復元する
- 無い場合、スロット側が主張しているなら（ロード、敗北からの復帰）0へ戻す
- 無い場合、直前に保存が行われたなら引き継ぎ、**直ちに書き出す**（同じ鍵が二度と曖昧にならない）
- それ以外は0へ戻す

判定をコアへ出したのは、この規則を3回誤って出荷しており、逆方向の誤りが交互に起きていたためである。プラグイン側の分岐ではゲームを起動しないと確かめられない。5通りすべてをテストで固定した（DEC-264）。

**その他**

- スロットが未確定のまま敗北した場合も0へ戻す。戻る記録が存在しない
- ログが実際の判断（復元／引き継ぎ／0へ戻す）と、その結果の全値を書くようにした

### 1.2.0 — 2026-08-09

ゲーム内表記名「大口のワーム」など、一部の敵の性的・非性的攻撃を `F10` の画面から設定できなかった不具合を修正した（SPEC003 v1.2）。

**原因**

- 敵の同定に `EnemyObject.m_GalleryEnemyID` だけを使っていた。これはギャラリー登録用の欄であり、拘束してくる敵の一部は未設定のまま出荷されている。実行時ログでは `Captor 'None' sender 'EnemyMeatWorm1 (2)'` のように出ていた
- 未設定の敵はすべて `None` という1行を共有していた。したがって**1体を `Sexual` にすると未同定の敵すべてが `Sexual` になり**、個別の宣言はどれも効かなかった。`GaID_MeatWorm1` の行は存在するが実行時に一致せず、死に行だった

**修正（FR-280〜283）**

- 拘束相手を `m_GalleryEnemyID` → `m_EnemyID` → 正規化したオブジェクト名（`obj:` 接頭辞）の順で名指す。`(Clone)` と ` (2)` は識別子から除く
- オブジェクト名が `Root` や `Base` のような構造名の場合は識別子にせず、コンポーネント型名（`obj:StoneEye` など）を使う。このビルドでは拘束判定が全キャラクターの `Root` にぶら下がっており、居合わせた拘束者どうしが1行を共有してしまう
- 拘束相手を `Bind.Binder`（`IBinder`）から取る。`Bind.BinderEnemy` は型が `EnemyObject` で、`ParasiteTentacle`・`ParasiteBullet`・`StoneEye` のように `EnemyObject` でない拘束者では空になり、それらの拘束は「拘束相手が居ない」ものとして扱われていた（レビュー指摘による追加修正、SPEC003 CHG-017）
- `None` は識別子として扱わない。引かず、書かず、既存の `None` 行は読み込み時に破棄する。宣言を持っていた場合は引き継げなかった旨を1回記録する。同定できない拘束相手は SPEC003 5.3 のとおり状態異常判定へ進む
- 編集画面の一覧を `GalleryEnemyID` と `EnemyID` の全件（各108件、`None` 除く）＋拘束で発見した `obj:` 行にした。接尾辞が共通するのは66件だけで、どちらか一方では42件が遭遇するまで名指せない
- 拘束時に `DisplayEnemyNameID` からゲーム内表記名を取得してカタログに保存し、一覧と「Holding you now」に併記する。名前規約による静的な対応付けは `EnmID_` で63/108しか当たらないため採っていない

**互換性**

- `schemaVersion` は `1` のまま。v1.1 までに設定した `GaID_` 行は鍵も意味も変わらず、そのまま効き続ける。移行作業は不要
- カタログに任意フィールド `displayName` が増える。あわせて、書かれていた `Setting`（`kind` の数値表現）の出力をやめ、日本語をエスケープせずそのまま書くようにした。SPEC003 6.2 のフィールド表と一致する

**診断**

- `[probe] A-53: captor '...' was identified by its ...` が、どの欄で同定できたかと表示名を1回だけ記録する。順3（オブジェクト名）まで落ちる敵が多いかどうかはこれで分かる

### 1.1.1 — 2026-08-09

セーブポイント（像）のダイアログが開いた瞬間に自動で閉じ、セーブもレベルアップもできない不具合を修正した。あわせて、アイテム使用イベントを不安定にし得た観測パッチを撤去した。

- 同じく `UniTask` を返す `InventoryHandler.PlayItemEvent` の観測 postfix を撤去した。アイテムイベントの停止・スキップ（ランダムなフリーズの一因）になり得たためである。アイテム消費の観測は `RemoveItem`（void 返し）が引き続き担う
- 教訓を DEC-259 として記録した: この実行環境では void 返しのメソッドだけをパッチ対象にする

### 1.1.0 — 2026-08-09

拘束中の敗北条件の置き換え方を改訂した（SPEC003 v1.1）。v1.0 は「HPが `0` へ達することだけを止める」形で、HPは `1` で停止していた。実プレイでは拘束中もHPが削られ続け、限界到達後の生死はHPの残量が決めていた。切り離しが完了していなかった。

**性的攻撃をHPから切り離した（5.1、FR-203〜206、DEC-256）**

- 拘束中に性的と判定された被弾は、HPを1点も減らさない。抑止するのはHPの減算だけで、被弾の成立・ダメージ表示・被弾演出・状態異常の付与・MPの消費は従来どおり
- 判別は既存の `Sexual` / `NonSexual` / `Auto` をそのまま被弾ごとに使う。`Sexual` の敵は何をしてもHPを削らず、`Auto` の敵は攻撃ごとに分かれる
- **非性的な攻撃、毒などのスリップダメージ、環境ダメージには介入しない。** 拘束中でもHPは尽き得るし、尽きれば絶頂回数と無関係にゲームオーバーになる
- `StatusCondition.RemainHp1Msv` への寄与は撤去した（FR-277）

**絶頂限界の到達をその場の致死にした（5.5、FR-215、FR-216、DEC-257）**

- 絶頂が成立して回数が限界に達した瞬間に、HPの残量を問わずHPを `0` にする。敵の次の一撃を待たない
- ゲームオーバー処理そのものは呼ばない。HPを `0` にするところまでがMODの仕事であり、死亡判定・演出・リトライ・ペナルティはゲームの経路が走る（DEC-209 を維持）
- 発火は絶頂の成立時のみ。毎フレームの判定にすると、限界以上のまま保存したセーブをロードした瞬間に死ぬ（DEC-258）

**設定**

- `Survival.SuppressHp0WhileBound` を廃止し、`Survival.SuppressSexualHpDamage` へ置き換えた。旧キーが残っていれば起動時に1回その旨を記録する
- 既定値がゲームの挙動を変えなくなった。`SuppressSexualHpDamage` は既定で真だが、`PleasureGainPerHit` が `0` の間は抑止も働かない。快楽が上がらないのにHPも減らない状態を作らないためである（FR-278）
- 撤回した `FR-260`（耐える時間の抽選、搾乳の開始キー）ほか、実体を失った要件・判断・実測記録を仕様書から取り除き、[`SPEC003-withdrawn.md`](specifications/SPEC003-withdrawn.md) へ非規範の履歴として分離した

**実機で確定すること**

- A-50 — `BattleMainParameter.DontSub` が減算を止めるか。止めなければ減った分を書き戻す経路へ自動で倒れる
- A-51 — `HP.SubAll` でHPが `0` になり、ゲーム自身の死亡判定が拾うか。効かなければ `SetCurrentValue(0)` → `Lelia.RequestCommonDead` の順に降りる

どちらも効いた手段が `[probe]` 行に出る。

### EDI本体改訂 E7（Edi.exe） — 2026-08-09

A10ピストンだけが数分間動かなくなる不安定動作を修正した（SPEC001 7.4.2 E7）。MODのDLLは変更していない。

**原因**

Buttplug 4.0.0 の `ButtplugMessage.GetName` は、メッセージ型のメタデータを静的な `Dictionary` へロックなしで初回書き込みする。EDIはデバイスごとの再生タスクから並行に送信するため、複数デバイスが同時に動き出す初回解決でこの辞書が破損する。破損後は該当メッセージ型の送信（実機ではピストンの `LinearAsync`）が `InvalidOperationException` でプロセス再起動まで失敗し続け、他のデバイスは動き続けるため「A10とUFOTWのタイミングがずれる・不安定」として体感される。2026-08-09 の `Edilog20260809.txt` 21:28〜21:33 に、3デバイス同時開始直後からピストンのみが26回連続失敗する形で記録されている。

**修正**

`ButtplugProvider` の初期化時に、Buttplugアセンブリ内の全メッセージ型を単一スレッドで解決してキャッシュを埋める（`ButtplugMessageMetadataPrewarm`）。以後の稼働中はキャッシュへの書き込みが発生せず、不変の `Dictionary` への並行読み取りは安全である。挙動の変更はなく、設定も持たない。

- ビルド: `N:\Git\repository\Edi` から `scripts/Publish-Windows.ps1` で生成し `Edi/Edi.exe` へ配置
- 配置した `Edi.exe` SHA-256: `D5B47F31442D598B881E10C104FAF1DA7CB82D6601F25FA6BDDF12434C50178D`
- 直前のバイナリは `Edi/Edi.exe.bak-pre-spec001-e7` として保管（ロールバック用）
- 回帰テスト: `Edi.Core.Tests/Devices/ButtplugMessageMetadataPrewarmTests`（並行1.6万回の解決で破損しないこと、`LinearCmd`/`RotateCmd`/`StopDeviceCmd` が事前解決済みであること）。全137テスト合格
- 適用は次回の `Edi.exe` 起動から。実行中のプロセスは旧バイナリのまま動作する

### 1.2.0 — 2026-08-09

同じ波形を複数の段階で再生できるようにした（SPEC001 CHG-039、FR-062、FR-063）。

**背景**

- 拘束が始まった瞬間にプレイヤーが待機していたか、歩いていたか、落下していたかで、ゲームは別のイベントを選ぶ。実行時ログでは同じ敵に対して `Idle_Broken`、`Idle_Injured`、`Walk2`、`Walk_Injured`、`Jump_Fall_Loop` が別々の未登録トリガーとして現れる
- ところが画面上の動きはほぼ共通である。段階ごとに同じ波形を描き直すと、修正のたびに全てを直す必要があり、片方だけ直し忘れた状態を検出する手段がない

**追加（GUI）**

- 「この波形を他の段階へ…」で適用先を複数選び、**共有（リンク）**または**複製（コピー）**を選べる。既定は共有
- 共有は `.funscript` を増やさない。適用先のトリガーが元の段階のギャラリー名を指すだけであり、以後その波形を編集すると共有している全段階に反映される
- 共有中の段階は一覧に「共有」バッジが付き、編集画面に共有先の一覧と警告が出る。1段階だけ直したつもりの編集が他へ波及することを、編集の前に知れる
- 「リンク解除」で、その段階専用の波形として書き出せる。残りの段階は共有していた波形を保持する
- 適用先のクリップ長がループとして合わない場合は、保存時と同じくループ長差異として承認を求める。既に自前の波形を持つ段階へ適用する場合も、その波形が再生されなくなることを承認の対象にする
- 未再生の段階と `unidentified-binder` の段階は、保存と同じ理由で適用先に出さない（FR-060）

**敗北（GO）がトリガーにならない不具合の修正（SPEC001 CHG-040、FR-064）**

- 沼のボスに敗北してもEDIが何も再生しない、という報告を受けてカタログを確認したところ、`game-over` の11件はすべて `actorId=lelia` で、`Dungeon_Swamp_Boss` の3件（`Damage3_Wall` 0.73秒、`Damage3_Wall_Down` 0.68秒、`Idle_Injured` 2.32秒）はいずれも**被弾クリップ**だった。同じ敵の敗北takeはギャラリーに `GaID_SwampLeech_Adult/Go_End1` 5.85秒として登録されている。長く続く演出そのものはトリガーになっておらず、演出の間にプレイヤーのアニメータが移り変わるたびに別の鍵が生まれ、再生の開始と停止が繰り返されていた
- 観測条件を `Lelia.IsHP0` からゲーム自身の死亡状態機械 `Lelia.LeliaDeadState`（`Live` / `HP0` / `GameOver`）へ移した。`IsHP0` はHPについての値であり、ゲームが敗北と決めたあとに走る段階を含まない
- 敗北を**拘束より先に**判定するようにした。拘束されたまま敗北する経路では、拘束の判定が先だと演出の間ずっと `hold` のトリガーが続き、敗北は一度も観測されなかった
- トリガー鍵を段階の開始時に確定し、段階（`HP0` → `GameOver`）が変わるまで保持する。1回の敗北が1つのトリガーになる。`stageId` は状態名なので、2段階を別々に作成できる
- 敗北演出がプレイヤーのアニメータで再生されない敵では、`animationId` を状態名としてカタログへ残す。読めないことを理由に観測を落とすと、6.2.1の順5と同じく「何も起きない」としか見えなくなる
- 既存の `game-over` 行11件は新しい鍵で作り直される。当該contextの `.funscript` は未作成のため移行作業は不要

**内部**

- GUIが編集・試聴・保存の対象とするギャラリーを、鍵から導出した名前ではなく `mappings.json` が名指すギャラリーにした（FR-063）。共有中の段階を編集したときに、実際には再生されない別ファイルを書いてしまうことがない
- 再生側は元から `outputs[].gallery` を読むだけなので、再生経路と `mappings.json` の形式は変更していない。既存の設定はそのまま動く

### 1.1.0 — 2026-08-09

拘束イベントを取りこぼす不具合と、別々の敵が同じトリガー鍵を共有する不具合を修正した（SPEC001 CHG-037）。

**取りこぼし（FR-059）**

- 拘束の観測条件が `lelia.Bind.BinderEnemy` が非 null であることだった。`BinderEnemy` の型は `EnemyObject` だが、拘束の契約は `IBinder` であり、`ParasiteTentacle`・`ParasiteBullet`・`StoneEye` は `EnemyObject` を継承せずに拘束する。これらの拘束では**トリガーが1件も出ず**、再生もカタログ追記も未登録警告も起きなかった（「拘束されたのに黄色文字が出ない」）
- 観測の前提条件から拘束者を外した。拘束者を名指せない場合は `actorId` を `unidentified-binder` として観測を残す。観測されない事象は診断の手がかりがないが、名前の付かない観測はカタログに1行残る

**トリガー鍵（FR-058）**

- `actorId` を `m_GalleryEnemyID` → `m_EnemyID` → `obj:<正規化オブジェクト名>` の順で解決するようにした。拘束者は `Bind.Binder` から取り、`Bind.BinderEnemy` はその部分集合として扱う
- `None` を `actorId` に使わなくなった。利用者のトリガーカタログでは別々の拘束6件が `hold/None/...` に潰れており、片方のために作った `.funscript` がもう片方で再生される状態だった
- `game-over` の `actorId` も同じ解決に揃えた。拘束者が居ない場合にのみ `lelia` になる

**鍵の共有を波形の共有にしない（FR-060）**

- `actorId` が `unidentified-binder` のトリガーは `mapped` にできない。オーサリングGUIは保存を拒否し、再生側は `mappings.json` に手書きされていても解決しない。**記録は残すが再生はしない**
- 拘束者を名指せなかった場合の警告文を「funscript を作れば再生される」ではなく「同定に失敗した」に変えた。前者は実行できない助言だった
- オブジェクト名が `Root` や `Base` のような構造名だった場合も `actorId` にしない。このビルドでは拘束判定が全キャラクターの `Root` にぶら下がっており、居合わせた拘束者どうしが同じ鍵を共有してしまう。その場合はコンポーネント型名（`obj:StoneEye` など）を使う

**オーサリングGUIをゲーム内から開けるようにした（FR-061）**

- `F6` で既定のブラウザからGUIを開く。それまでは起動ログのURLを手で入力するしかなかった。キーは `Authoring.OpenGuiKey` で変更でき、空にすれば無効になる。`F7`〜`F11` は快楽MODの画面が使っているため充てていない
- `Authoring.OpenGuiOnStart`（既定 無効）で起動時に自動で開ける。既定を無効にしたのは、ゲームの起動はGUIを求める操作ではないためである
- 起動ログにキーとURLを併記する。ブラウザが開けなくても警告1行にとどめ、ゲームと他の機構は継続する

**互換性**

- 既存カタログの `hold` 行21件は新しい鍵で作り直される。`.funscript` は未作成のため移行は不要
- マッピングの `schemaVersion` は変更なし
- 設定に `Authoring.OpenGuiKey` と `Authoring.OpenGuiOnStart` が増える

## community.sinisistar2.spawn

### 0.1.0

SPEC004 v1.2 の実装。まだ版を切っていない。エリア毎の出現調整（5.2）、停滞ペナルティ・奇襲の追加スポーン（5.3）、ギミック複製（5.4、既定無効）、ミミック疑似宝箱（5.5、既定無効）、診断モード。

実機検証の手段として可観測性HUD（5.8）とデバッグ操作（5.9）を同梱した。本MODの事象は確率・待ち時間・画面外で構成されるため、ログだけでは「介入しなかった」と「介入が見えなかった」をプレイ中に区別できず、受け入れ条件の過半が判定不能だった。

- `F5` でHUDを `Off` / `Compact` / `Full` に循環。エリア、倍率、停滞の進捗と残り秒数、追加出現の消費と上限、出現位置の候補数、疑似宝箱の決着状況を表示する。既定は `Off` で通常プレイでは何も描画しない
- `F3` でデバッグ操作パネル。追加出現・奇襲の強制、疑似宝箱の配置、抽選の当たり／外れ固定、エリア再抽選、診断出力、停滞の早送り。数字段・テンキーの双方を受け付ける
- `[Debug] DebugCommandsEnabled` が既定無効で、有効化するまでパネルは状態表示のみ。無効のまま数字キーを押した場合は、無視された旨と有効化手順（設定キー、ファイル名、パネルを開き直すこと）をパネルとログに提示する。無反応のまま黙るのは「無効」ではなく「故障」に見えるため（FR-334）
- **操作はマウスのクリックで行う。** パネルは各操作をボタンとして描画する。数字キーは近道として併存する（FR-341、DEC-319）。ボタン操作のため、パネル開放中に限りカーソルの表示を保証し、閉じたときに元へ戻す（FR-342）
- 有効化はパネル最上段のスイッチをクリックする。設定ファイルの編集も再起動も不要で、選択は設定へ保存される（FR-337、DEC-318）
- **有効化キー `0` は有効化専用にした。** 当初はトグルだったが、操作が正当な理由で何も起こさなかったとき（出現位置なし）、利用者は有効化キーを再度押す。実機の1セッションで、その押下が5回とも道具を止めていた。無効化はスイッチのクリックからのみ行う（FR-343、DEC-320）
- パネルを開いた時点でも設定を読み直す。BepInEx は設定ファイルを監視しないため、これが無いと有効化のたびに再起動が必要だった（FR-335、DEC-317）
- HUDは画面右上に描画する。左上はプレイヤーの立ち絵とゲームのステータス表示があり、観測対象そのものを隠していた（FR-338）

**前提が崩れたため出現源を作り直した（SPEC004 v1.5）**

実機の診断JSONにより、本作の通常エリアは `EnemySpawner` を用いず、敵を `EnemyObject` の実体としてシーンへ直接配置していることが判明した。`Road_n1_0` はスポナー 0 に対し `Zombie×7`・`ZombieTomb×1`。シーンの型ヒストグラム231件に `EnemySpawner` も `EnemyPool` も現れない。当初の 5.2／5.3 はスポナー前提だったため、普通のエリアでは全機構が対象ゼロで空振りしていた。

- 出現源を「スポナーのプール、無ければ**そのシーンに実在する敵の複製**」へ改訂した。複製元は作者がそのエリアに置いた敵そのものなので、「エリアに対応した敵」の保証は変わらず、シーン外からのロードも行わない（DEC-302 改訂）
- 出現位置も「スポナーの位置集合、無ければ**シーンに実在する敵の位置**」へ改訂した。MODが座標を発明しない原則は維持している（DEC-303 改訂）
- 複製の単位は、複製元を含む最上位の祖先であって配下に他の敵を含まないもの。コンポーネント単体では当たり判定・演出・AIが欠ける
- ボスと自身の識別子を持たない部位は複製しない
- 複製個体は名前を変えて階層パスを複製元と異ならせる。ゲームは敵の状態をパスで保存するため、衝突すると複製元の記録を壊し得る（付録A A-16 で実測する）
- v1.0 の 4.5 で「直接 Instantiate は採らない」と却下していた案を採用へ転じた。却下の前提は「プールという代替がある」ことだったが、それが成立しなかった

**複製個体の初期化を実機で確定した（付録A A-17）**

`Instantiate` しただけの複製はゲームが存在を知らないオブジェクトであり、動かず、倒せなかった。必要な初期化は次の4つで、いずれも void 返しである。

```
ObjectManager.SetUpSiNiObject → SetUpHP → StartRunning → StartSpawnProcess
```

- `SetUpHP` を欠くと `IsLiving=False` のままで、被弾も死亡判定も成立しない
- **`StartTask` は呼んではならない。** ゲーム自身が呼んでおり、二重呼び出しは状態機械へ `An item with the same key has already been added. Key: Ready` を投げる。登録が途中で中断するため、攻撃はできるのに歩けない個体ができる
- `StartTask` は `UniTask` を返すため、この例外は非同期に表面化し、呼び出しを囲んだ try/catch を素通りして「成功」と記録されていた。快楽MODが DEC-259 で「void 返しのメソッドだけをパッチする」と記録したのと同じ危険が、呼び出し側にも当てはまる
- `ForbiddenSurfaceTests.UniTaskReturningMembersAreNeverCalled` が、`UniTask` を返す既知のメンバーへの呼び出しをビルド時に禁止する

配置は複製元の位置で生成してから `Teleport(target, isFitGround: true)` で移動する。座標の測定点（`EnemyObject` の transform）と配置点（複製の根）が別階層でずれていた欠陥も併せて修正した。

**実機での初回使用で判明した欠陥を修正した**

- **スポナーが1つも見つかっていなかった。** `FindObjectsOfType` の既定は非アクティブなオブジェクトを除外するが、本作はスポナーを到達まで無効化して置いている。実エリアで `spawners=0` となり、出現調整・追加出現・疑似宝箱のすべてが対象ゼロで空振りしていた。`includeInactive: true` を全走査へ適用した（FR-339、付録A A-13）
- `Full` 表示にシーン内のスポナー数を追加し、0 の場合は `no EnemySpawner in this scene` と明示する。「機構が動かない」と「対象が無い」は別の状態であり、区別できなければ原因に辿り着けない（FR-340）
- デバッグ操作が短絡するのは待ち時間と確率だけで、上限・除外エリア・拘束中の禁止・出現位置の条件は迂回しない。停滞90秒を待たずに済むことと、上限を無視できることは別の要求である
- 描画は IMGUI に限り、ゲームの Canvas・UIオブジェクト・`Time.timeScale` に触れない。ホットキーは `Event.current` から読む。対象ビルドのゲーム本体は legacy `KeyCode` を使わないため、競合はMOD間でのみ起きる
- 既定キーは `F5`（HUD）と `F3`（デバッグパネル）。`F6` は EDI のオーサリングGUI、`F7`〜`F11` は快楽MOD、`F12` は Steam のスクリーンショットが占有しており、`F4` は `Alt+F4` と隣接するため避けた。この占有表は `HotkeyCollisionTests` がビルド時に検証する

付録A の実測（A-2、A-9〜A-12 ほか）は未実施で、手順は `docs/testing/SPEC004-test-scenarios.md` にある。
